## ০. এই নথির উদ্দেশ্য

`পরিকল্পনা/` ফোল্ডারের **চারটি** নথি একে অন্যের প্রায় চার গুণ দীর্ঘ এবং একে অন্যের সাথে
**বিরোধিতামূলক**। কোনো একটি নথি যদি সরাসরি অনুসরণ করা হতো, তাহলে কাজ পরস্পরকে
নাকচ করে দিত। এই মাস্টার প্ল্যান চারটি নথিকে একত্রে ফেলে:

1. তাদের মধ্যে থেকে **সমস্ত অনন্যসাপন্ন কাজ বের করে** (কোনো কিছু বাদ পড়বে না),
2. পরস্পরের **বিরোধ সমাধান** করে একটি অভিন্ন নীতি ঠিক করে,
3. বাস্তব **কোডবেসের বর্তমান অবস্থার সাথে মিলিয়ে** যাচাই করে,
4. এবং একটি **এক্সিকিউশন-অর্ডারড সিরিজ** সাজায় যা সত্যিই বাস্তবায়নযোগ্য।

**নীতি:** পরিকল্পনার লক্ষ্য হলো নথির স্বপ্ন নয়, **কোডের বাস্তবতা**। যেখানে নথি ভুল,
সেখানে কোডই প্রামাণিক। যেখানে কোড ভুল, সেখানে নথির লক্ষ্য ঠিক।

> **বিল্ড "ক্রস-কম্পাইলেশন" আসলে কোড-জেনারেশন নয়।**
> `nil build linux/windows/macos/android` — সবগুলোই `GOOS=... go build ./cmd/nil-runner`
> দিয়ে Go রানার বাইল্ড করে, তারপর `.nilax` বান্ডেলটি **বাইট-কনক্যাটেনেট** করে।
> নীলাং-এর নিজস্ব কোন কোড-জেনারেটর, অ্যাসেম্ব্লার বা লিংকার নেই।

এটি একটি সঠিক সিদ্ধান্ত (দ্রুত ও নির্ভরযোগ্য), কিন্তু এটি **মোবাইল অ্যাপের জন্য যথেষ্ট নয়** —
কারণ Android/iOS-এ প্রতিটি অ্যাপের প্রকৃত ইনস্টল-সাইজ ১৫–২৫ MB (Go runtime সহ), যা
স্টোর-সীমা ও স্টার্টআপ-টাইমের দিক থেকে অগ্রহণযোগ্য নয়। **AOT কোড-জেনারেশন ফরজরি।**

### ২.১ ⚔️ বিরোধ: নিজস্ব GPU রেন্ডারার নাকি নেটিভ UI অ্যাডাপ্টার?

- **সফটওয়্যার রাস্টারাইজার থেকে যাবে** — কিন্তু টেস্ট/গোল্ডেন/IDE-প্রিভিউয়ের

### ২.২ ⚔️ বিরোধ: প্রথমে LLVM নাকি প্রথমে ভাষার শক্তি?

| নথি | অবস্ধান |
|---|---|
| `পরিকল্পনা.md` অগ্রাধিকার ১ | "**LLVM ব্যাকএন্ড. এটি সব কাজের আগে করুন।**" |
| `nilang_mobile_roadmap_bn.md` §১৮.১ (P0) | ভাষা/রানটাইম সেমান্টিকস, `.nilax` ভার্সনিং, native host ব্রিজ, UI অ্যাডাপ্টার, Android বিল্ড |
| ভুল ১ | "সব feature একসঙ্গে শুরু করা" |

**📌 সিদ্ধান্ত (ADR-0002):** **LLVM-এর আগে ভাষার কোর (L0–L3)।**

LLVM emitter-এর ইনপুট হলো MIR। আজকের MIR-এ `for`, `struct`, `match`, generics — কোনোটিই
নেই; `if`-এর else-শাখা হারায়। এই অবস্থায় LLVM emitter বানালে তা যে ভাষাটিকে কম্পাইল করবে
তা আজকের ০.১ সাবসেটের চেয়ে বেশি নয় — অর্থাৎ **অপ্রয়োজনীয় পুনরায়-লেখা**।

সঠিক ক্রম: `L0 → L1 → L2 → L3 (MIR ক্যাননিক্যাল) → L4 (LLVM)`।
`পরিকল্পনা.md`-এর অগ্রাধিকার ১ **অক্ষুণ্ণ**, কিন্তু তার **অবস্থান ৫ম**, ১ম নয়।

### ২.৩ ⚔️ বিরোধ: একটি ভারী রানটাইম নাকি সরু ব্রিজ?

| নথি | অবস্ধান |
|---|---|
| `nilang_mobile_roadmap_bn.md` §২৪ | ব্রিজকে ছোট রাখো, thread policy, value conversion, ABI স্থায়িত্ব |
| বাস্তবতা | আজ রানটাইম = Go-কম্পাইলড ২৫MB বাইনারি |

**📌 সিদ্ধান্ত (ADR-0003):** **দুই-স্তরের ডিসপ্যাচ।**
`libnilang_core.so` (ছোট, GC+স্ট্রিং+বাইটকোড VM, ≈২–৪ MB) ← এটাই মোবাইলে যাবে।
পূর্ণ `nil-runner` (২৫ MB) শুধু ডেস্কটপ ও CI-তে থাকবে। C ABI → Rust/Go নেটিভ কোর।

### ২.৪ ⚔️ বিরোধ: WASM কি উৎপাদন-পথ?

**📌 সিদ্ধান্ত (ADR-0004):** WASM **সমর্থিত লক্ষ্য**, কিন্তু **সেকেন্ডারি**।
আজকের WASM emitter (লুপ/কন্ডিশনাল ছাড়া) প্রযোজ্য নয়। L7 সম্পন্ন না হওয়া পর্যন্ত
`nil build wasm` থেকে "Experimental" লেবেল সরবে না। L7 শেষে সরবে।

### ২.৫ বিরোধ নয়, কিন্তু স্পষ্টীকরণ: "৬০ FPS" দাবি

### ADR-0007: `for`, `match`, struct ও enum — lowering, নতুন opcode নয়

**সিদ্ধান্ত:** এই চারটি কনস্ট্রাক্টের কোনোটিই নতুন opcode পায় না। একটি lowering পাস (`compiler/lower`) ব্যাকএন্ড দেখার আগেই সেগুলো ডিসুগার করে — `for` → `while`, `match` → `if`/`else` চেইন, struct literal → hash literal, enum value → `variant`/`payload` keyed hash।

**কারণ:** প্রতিটি কনস্ট্রাক্ট নিজে থেকে দুই ইঞ্জিনে বাস্তবায়ন করলে সেগুলো মুক্তভাবে বিচ্যুত হতে পারত, আর প্রতিটির জন্য আলাদা করে কনফরম্যান্স টেস্ট লাগত। একবার lowering করলে দুই ইঞ্জিন একই কোড চালায় — কারণ সেট একটিই আছে। এটি `for`-এর জন্য L1-এ ধরা পড়া, এবং `match`-এর জন্য একই নীতি।

**দাম:** struct একটি keyed collection, তাই `u["name"]` ও কাজ করে এবং একই key-এর প্লেইন hash একই struct pattern মেনে নেয়। Struct পরিচয় স্ট্যাটিকভাবে বাচাই হয়, যেখানে ব্যাখ্যা অসংশকেত নয়। Enum value-ও একইভাবে hash, যাতে `match` একই if-চেইনে বসে।

### ADR-0008: বেসইক এনজিন বাউন্ডারিতে অতিক্রম করা বুলিয়ান

**সিদ্ধান্ত:** truthiness, `!` ও `==` টাইপ-ও-মান দিয়ে তুলনা করে, কখনো pointer identity দিয়ে নয়। `object.TRUE/FALSE/NULL` একটাই instance, কিন্তু তুলনাগুলো তার উপর নির্ভর করে না।

**কারণ:** একটি Go builtin যে বুলিয়ান ফেরত দেয় তা `*object.Boolean`, গ্রহণকারী প্যাকেজের `True`/`False` সিঙ্গেলটন নয়। pointer identity দিয়ে তুলনা করলে `if (isOk(x)) { ... } else { ... }` `--vm`-এ সবসময় প্রথম শাখা নিত, যখন evaluator ঠিক ছিল। `!`-এ উল্টো ভুল, `==`-এ আবার ভুল।

**কারণ আরও গভীর:** যে কোনো Go বস্তু যেকোনো জায়গা থেকে তৈরি হতে পারে। সঠিকতা যেন সেট থেকে নির্ভর করে না, তা-ই নিয়ম।

### ADR-0009: ব্যর্থ builtin প্রোগ্রাম থামায়

**সিদ্ধান্ত:** `callBuiltin` তার ফেরতাফরা যাচাই করে; error object হলে VM থামে। প্রতি ইনস্ট্রাকশনে নয়।

**কারণ:** builtin ব্যর্থতা *ফেরত দিয়ে* জানায়, কিছু raise করে না। evaluator প্রতিটি `Eval` থেকে মান প্রোপাগেট করে বলে থেমে যায়। VM error object push করে এগিয়ে যেত — ফলে `assert(false, "x")` `--vm`-এ নো-অপ ছিল। `ERROR_MODEL.md §4.5` দুই ইঞ্জিনকে একই প্রোগ্রামে ব্যর্থ হতে বাধ্য করে।

**দাম:** বিভাগযোগ্য `RuntimeError` বিভাগ নিয়ে যায়; বিভাগহীন `Error`-এর বার্তা অপরিবর্তিত থাকে, কারণ VM-এ নতুন বিভাগ বানালে দুই ইঞ্জিন একই ভুলের জন্য ভিন্ন লেখা দেখাত।

### ADR-0010: `export` অপস্থিতি = ফাইল-স্তরের, ঘোষণা-স্তরের নয়

**সিদ্ধান্ত:** যে ফাইলে একটি `export`-ও নেই, সে **সব কিছু** export করে। যে ফাইলে `export` আছে, সে শুধু যা চিহ্নিত তাই export করে।

**কারণ:** অন্য নিয়ম — "চিহ্নিত না = private" — ভাষা শুরু হওয়ার আগে লেখা **প্রতিটি** module ভেঙে দিত। এখন যেকোনো একটি `export` লিখে মডিউল strict visibility-তে ঢোকে।

**কারণ আরও গভীর:** এটি একটি অস্বাভাবিক নিয়ম, তাই এটিকে সরাসরি লিখে রাখা দরকার। লুকানো নিয়ম একদিন অন্য কিছু হয়ে যায়।

**দাম:** দুই ধরনের module একই বিল্ডে থাকে। একজন পড়তে চাইলে তাকে প্রথমে দেখতে হবে module-এ `export` আছে কি না।

### ADR-0011: ইমপোর্ট করা নাম না থাকলে নীরবে null নয়, ব্যর্থ

**সিদ্ধান্ত:** `import { x } from "./m.nil"`-এ `m.nil` `x` export না করলে error — bind না করে runtime-এ পরে ব্যর্থ হওয়ার বদলে।

**কারণ:** আগের আচরণ কিছুই bind করত না, তাই প্রোগ্রাম পরে যে লাইনে ওই নাম পড়ত তার ওপর ভেঙে যেত। শুধু private নামের জন্য এটা সম্পূর্ণ ভুল ভুলের দিকে ইঙ্গিত করত।

**সম্প্রসারণ:** ব্যর্থতা দুই ইঞ্জিনেই। evaluator রানটাইমে বলে (`bindModuleToEnv`), bytecode compiler কম্পাইলে (`E0303`) — একটি visibility নিয়ম এক ইঞ্জিনে enforce করা মানে enforce করা নয়। দুটোতেই এখন সব অনুপস্থিত নাম একসাথে বলা হয়, যাতে একটি সমস্যা মেরামত করতে দুইবার কম্পাইল না লাগে।

### ADR-0012: ইমপোর্ট করা মডিউল-ও lower হয়

**সিদ্ধান্ত:** module যেহেতু চলে, তাই top-level প্রোগ্রামের মতোই lowering pass-এর ভেতরে যায় — দুই ইঞ্জিনেই।

**কারণ:** ছিল না, এবং কোনো যুক্তিসহ কারণ ছিল না: importing প্রোগ্রাম lower হতো, module হতো না। ফলে module-এ `for`/`match`/`struct`/`enum`/`while let` থাকলে backend এমন node পেত যা সে নিতেই চায় না, আর সেটাকে "internal error" বলে রিপোর্ট করত।

**প্রকাশিত হয়েছে:** `export struct` দিয়ে একটি টেস্ট লিখতে গিয়ে। এটি এমন বাগ যা ভাষার নিজস্ব standard library-তে বাগ রিপোর্ট হওয়ার জন্য অপেক্ষা করছিল।

### ADR-0013: `impl`-এর কোনো method table নেই

**সিদ্ধান্ত:** `impl` কোনো dispatch table, vtable বা per-object type tag যোগ করে না। প্রতিটি method একটি সাধারণ top-level ফাংশনে পরিণত হয়, নামটি এমন যা ডেভেলপার লিখতে পারে না, আর একটি method call তাকে সেই ফাংশনে rewrite হয় — receiver প্রথম আর্গুমেন্ট হিসেবে।

**কারণ:** তিনটি কাজই এখান থেকে আসে। প্রথম, কোনো ইঞ্জিনেরই বদলাতে হয় না — তারা ইতিমধ্যে ফাংশন কল করে, তাই method কীভাবে কাজ করে তা দুজনই বিচ্যুত হতে পারে না। দ্বিতীয়, run-time খরচ ও per-object হিসাব নেই। তৃতীয়, receiver-এর **স্ট্যাটিক** টাইপই implementation বাছাই করে — যা trait-এর মূল কথা। Dynamic টাইপে resolve করলে সেটি অন্য একটি ভাষা, আর কোনো resolve না করলে একটি নির্ণয়যোগ্য ভুল crash হয়ে যেত।

**কীভাবে:** rewrite-এর জন্য receiver-এর টাইপ জানতে হয়, যা শুধু checker জানে। তাই checker সেটি tree-তে না লিখে পাশে রাখে, আর lowering সেটি পড়ে। Tree-তে লিখলে formatter generated নামটি দেখাত — কারণ formatter একই program পড়ে।

**প্রসারিত:** ADR-0007-এর নীতি। `for` ও `match`-এর মতোই, একটি বাস্তবায়ন মানে দুই ইঞ্জিন একই কোড চালায়।

**দাম:** static method (`Type.new()`) ও generic trait এখনো নেই। static method-এর জন্য namespace-এর একটি রূপ দরকার যা ভাষার ব্যাকরণে নেই, আর generic-এর জন্য এমন টাইপ সিস্টেম দরকার যা তা constrain করতে পারে। দুটোই L2।

### ADR-0014: `x.k` আর `x[k]` আলাদা instruction

**সিদ্ধান্ত:** নতুন `OpGetField` — `x.k`-এর জন্য; `OpIndex` — `x[k]`-এর জন্য। Dot access-এ member না থাকলে VM ব্যর্থ হয়, indexing-এ key না থাকলে null।

**কারণ:** দুটো আলাদা প্রশ্ন। Indexing জিজ্ঞেস করে "এই key-তে কী আছে", আর না থাকা key-এর উত্তর null — এটাই lookup miss-এর অর্থ। Dot access চায় নামে member, আর না থাকা member হলো টাইপো, অসম্পন্ন refactor, নাকি parenthesis-এর দরকার এমন একটি call। যেকোনোটাতেই নীরবে null দিলে ব্যর্থতা সেই লাইনে চলে যায় যেখানে value ব্যবহার হয় — মানে ভুলের কাছেও নয়।

**প্রকাশিত হয়েছে:** trait-এর পরীক্ষা করতে গিয়ে। এটি আগের থেকেই থাকা **ক্রস-ইঞ্জিন বিচ্যুতি** ছিল: `h.nosuch`-এ evaluator ব্যর্থ হতো, VM নীরবে null দিত।

### ADR-0015: `??` ও `?.` if/else-এ lower হয়

**সিদ্ধান্ত:** দুটো operator-ই hidden local-এ receiver বাঁধার পর `if`/`else`-এ ডিসুগার হয়। কোনো নতুন opcode নেই।

**কারণ:** ADR-0007-এর নীতি — একটি বাস্তবায়ন মানে দুই ইঞ্জিন একই কোড চালায়, তাই operator-এর অর্থ নিয়ে তারা বিচ্যুত হতে পারে না।

**দুটি নিয়ম, যেগুলো ভুল হওয়া সহজ:**

1. **receiver একবারই মূল্যায়িত হয়।** `if (a == null) { null } else { a.b }` `a`-কে দুবার মূল্যায়ন করে — side effect থাকলে ভুল, ব্যয়বহুল হলে অপচয়। `match`-এর subject বাঁধার কারণও একই।
2. **`?.` পুরো chain guard করে, নিজের ধাপটা নয়।** `o?.i.v`-এ `o` null হলে পুরো expression-ই null। শুধু `o.i` guard করলে `.v` null-এর উপর পড়ার চেষ্টা করত — যা এই নিয়মটাই ঠেকায়।

**বিশেষ:** `a?.b(args)` একটিমাত্র কনস্ট্রাক্ট হিসেবে lower হয়, calleacে নামিয়ে তারপর call করে নয়। কারণ calleacে নামালে empty-তে null এসে সেটাতে call হতো — operator-টির মানে উল্টো।

**প্রসারিত:** `isNull` builtin দুই ইঞ্জিনের জন্যই প্রয়োজন, তাই যোগ হয়েছে এবং ডেভেলপারও ব্যবহার করতে পারে।

### ADR-0016: Unlowered node backend-এ গেলে নীরবে নয়, ব্যর্থ হয়

**সিদ্ধান্ত:** compiler ও evaluator-এ `CoalesceExpression`, `SafeAccessExpression`, `MatchExpression`-এর জন্য স্পষ্ট "reached without being lowered" ত্রুটি আছে।

**কারণ:** guard ছাড়া compiler কোনো instruction emit করত না, তাই VM stack underflow করত; evaluator nil ফেরত দিয়ে চলতে থাকত, তাই **ভুল উত্তর** দিত। দুটো ফলাফলই অশুভ, আর দ্বিতীয়টি আরও খারাপ — একটি ভুল উত্তর পড়ে কেউ বুঝতে পারে না কোথায় ভুল হয়েছে।

**প্রকাশিত হয়েছে:** `?.`/`??` লেখার সময়। এটিই আসলে ধরিয়ে দিয়েছিল আসল সমস্যাটা: `a ?? b ? c : d`-এ lowering-এ `IfExpression`-এর কোনো case না থাকায় condition কখনো lower হতো না।

### ADR-0017: Composite target-এর assignability একটি জায়গায়

**সিদ্ধান্ত:** `?T` ও `A | B` target-এর assignability একটি ফাংশনে থাকে, যা প্রতিটি concrete টাইপ ডাকে।

**কারণ:** প্রতিটি টাইপের নিজস্ব করা ছিল শুধু `PrimitiveType`-এ। বাকিরা দুটোই ফাঁক ছিল — যার ফলে একটি union annotation লেখা হতো, গ্রহণ হতো, এবং উপেক্ষা হতো।

**কেন একটি ফাংশন:** নিয়মটি বিস্তারিত দিলে সেটাই ঘটে যায় যে নিয়মটি আংশিকভাবে বাস্তবায়িত থাকে। `?Address` একটি এমন টাইপ হয়ে গিয়েছিল যেখানে কিছুই রাখা যেত না — আর optional ফিল্ডই `?.`-এর জন্য সাধারণতম জিনিস, তাই সেই ফাঁকটি `?.`-কে নিজেই অর্থহীন করে দিয়েছিল।

**প্রসারিত:** ADR-0007 ও ADR-0013-এর একই ধাঁচ — যেটা বারবার একবারই বাস্তবায়ন করা হয়, সেটাই দুই ইঞ্জিনকে এক করে রাখে।

### ADR-0018: জেনেরিক্স erased, monomorphised নয়

**সিদ্ধান্ত:** কোনো monomorphisation নেই। id একবারই compile হয়, আর call site সাধারণ value-ই পাঠায়। Type parameter শুধু checker-এর কাজ।

**কারণ:** দুই ইঞ্জিন তখনই অপরিবর্তিত থাকে — তারা ইতিমধ্যে ফাংশন কল করে, তাই generic ফাংশন কীভাবে কাজ করে তা নিয়ে তারা বিচ্যুত হতে পারে না। Run-time খরচও নেই।

**কীভাবে:** declaration-এর ভেতরে T একটি 	ypes.TypeVar। এটি declared-type lookup-এর **আগে** resolve হয়, কারণ checker-এর ইচ্ছাকৃতভাবে অমীকৃত একটি নাম আর চেনা-ব্যর্থ একটি নাম — বিপরীত। Parse যেকোনো অজানা নামকে empty struct বানায়; সেটা T-এর জায়গায় বসলে T কিছুর সাথেই সমান হতো না এবং প্রতিটি generic ফাংশন E0502 পেত।

**Call site-এর ক্রম:** প্রথমে bind, তারপর substitute, তারপর যাচাই। Argument-কে *unbound* signature-এর বিপরীতে যাচাই করলে Int একটি নগণ্য T-এর বিপরীতে গিয়ে যেত — অর্থাৎ ঠিক বা ভুল, যে কোনোভাবেই ফলাফল call-টি সম্পর্কে কিছুই বলত না।

**Array ও List একটি টাইপ:** প্রতিটি নথিতেই Array<T> লেখা, আর checker array literal থেকে List<T> বের করে। আলাদা রাখলে n size<T>(items: Array<T>) size([1, 2]) বাতিল করত — অর্থাৎ ভাষার যে একমাত্র array তৈরি করে তার উপরেই কাজ করে না এমন একটি generic ফাংশন।

**দাম (সীমা):** inference **structural, unification নয়**। এটি generic type, optional ও union-এর ভেতরে দেখে; function type-এর parameter list-এ ঢোকে না, body-ও দেখে না। ফলে parameter-এ না-থাকা কোনো variable bind হয় না এবং Any হয়ে যায় — n empty<T>() -> Array<T>-এ let xs: Array<Int> = empty(); গ্রহণ হয়।

**এই সীমা কেন টেস্ট করা হয়েছে:** শুধু যা কাজ করে তার টেস্ট থাকলে সীমা নিজে থেকেই সরে যেত। TestGenericBoundaryIsWhereItIs সেটিকে আটকে রাখে। সংকীর্ণ করতে হলে return type body থেকে infer করতে হবে — অনেক বড় কাজ।

### ADR-0019: numeric width আলাদা টাইপ, Int-এ alias নয়

**সিদ্ধান্ত:** i8..u64, 32, 64 প্রত্যেকে আলাদা PrimitiveType। Int-এর সাথে বা নিজেদের মধ্যে কোনো implicit নেই।

**কারণ:** যে width কিছু বদলায় না, সে কোনো width-এর চেয়েও খারাপ — কারণ ডেভেলপার এটি লিখে যুক্তিসঙ্গতভাবে বিশ্বাস করেন range যাচাই হচ্ছে। Alias করে রাখলে let x: i8 = 300; compile করত।

**একমাত্র ছাড়:** integer **literal** context থেকে width নেয় ও range মেনে নেয়। let x: u8 = 5 গ্রহণ, 300 E0110। এটি coercion নয় — literal-এর নিজস্ব width নেই ঘর ঘর। কিন্তু Int **ভেরিয়েবল** কখনো width হয় না; সেটানার জন্য কেউ যে রূপান্তর লিখেনি।

**Arithmetic width ধরে রাখে:** u8 + u8 হলো u8, আর পাশের bare literal ওই width গ্রহণ করে — তাই x + 1 u8 থাকে। বাকি সব Int-এ widen হয়, যা ভাষার প্রতিটি width-এর চেয়েও চওড়া, তাই উত্তর কখনো খুব সরু হতে পারে না।

**যা বাস্তবায়িত নয়:** run-time narrowing। let a: u8 = 200; let b: u8 = a + a; 400 থাকে। ধরতে হলে দুই ইঞ্জিনেই narrowing instruction দরকার, আর কখনো কখনো firing করা একটি check না-চেকের চেয়ে খারাপ। তাই এটি compile-time বলে লেখা আছে।

**প্রভাব:** দুটি কার্যকর উদাহরণের state idx: i32/state count: i32 আর একটি UI পরীক্ষা ভেঙেছিল — literal narrowing কেবল let-এ ছিল। checkAssignable তৈরি করে চারটি সাইটে একই নিয়ম আনা হয়েছে; এটাই ঠিক সেই প্যাটার্ন যেখানে নিয়ম চারবার লেখা থাকে আর চারবার নিজেকে ভিন্ন করে।

### ADR-0020: narrowing builtin নিজের টাইপ বলে

**সিদ্ধান্ত:** Ok, Err, Some, unwrap, unwrapOr নিবন্ধিত Any নয়, বরং argument থেকে যে টাইপ বের হয় সেটি ফেরত দেয়।

**কারণ:** এই পাঁচটি *ইতিমধ্যে* হিসাব করে কোন payload আছে — কেউ নতুন নিয়ম যোগ করেনি, শুধু বলা বন্ধ ছিল। unwrap(r)-এর টাইপ না থাকায় তার পরের প্রতিটি মান অযাচাই থাকত, আর একটি প্রোগ্রাম error payload-কে success value হিসেবে পড়তেও পারত।

**Result-এর error দিক Any থাকে:** সব Err না পড়া একটি checker সবচেয়ে সরু error টাইপ বের করতে পারে না, আর অনুমান করলে সঠিক প্রোগ্রাম ব্যর্থ হতো।

### ADR-0021: Result ও Optional-এর দুই রূপের bridge

**সিদ্ধান্ত:** Result<T,E> এবং Optional<T> প্রতিটির একটি dedicated Go টাইপ **এবং** একটি generic spelling আছে। Annotation একটায় resolve হয়, value আরেকটায় তৈরি হয়, তাই দুই রূপের মধ্যে positional bridge আছে।

**কারণ:** bridge ছাড়া let r: Result<Int, String> = Ok(5) এমন দুই জিনিসের তুলনা করে যেগুলো বার্তায় হুবহু একই আর tree-তে ভিন্ন। ভুলের বার্তা তখন পাঠককে ভুল জায়গায় পাঠায়।

**প্রসারিত:** ADR-0017-এর একই ধাঁচ — যে ধরনের জিনিস দুই রূপে থাকে, সেটাকে এক জায়গায় মেলানো ছাড়া সেটা মিলবে না।

### ADR-0022: MIR temporary একটি নাম, stack-এর অবস্থান নয়

**সিদ্ধান্ত:** প্রতিটি MIR temporary-এর একটি slot থাকে (`OpSetLocal`/`OpSetGlobal`), এবং `emitOperand` সেটি পড়ে।

**কারণ:** VM-এর operand stack একটি stack; MIR temporary একটি SSA-ধাঁচের *নাম*, যা সেই expression-কে push করার পরেও বেঁচে থাকে। `_t0 = load n; _t1 = _t0 > 3` দুটি মান stack-এ ঠেলে, আর `_t0` পড়তে গেলে প্রথমটিই বোঝাতে হয়। "stack-এ যা আছে" পড়া ঠিক একবার কাজ করে — ঠিক পরের instruction-এ — এরপে সবসময় ভুল।

**প্রভাব:** `LoadVarInst`-ও `Dest` লেখে। সেটি বাদ পড়লে সব temp খালি slot পড়ত, যা "uninitialized variable" দিয়ে ধরা পড়ে — আর প্রথম ভুলটা temp ধারণার পাল্টা মনে হত, তাই ঠিক করতে দুই ধাপ লাগে।

### ADR-0023: select একটি instruction, branch-ও phi নয়

**সিদ্ধান্ত:** `cond ? a : b` → `SelectInst{Cond, True, False}`, যা bytecode emitter jump-over-the-arm-এ বিস্তার করে।

**কারণ:** ternary একটি *expression* — তার মান কেউ ব্যবহার করে। branch মান দেয় শুধু merge block-এর phi-র মাধ্যমে, যা statement-এর জন্য সঠিক আকার (সেখানে merge বিন্দু আগে থেকেই আছে)।

**দুই শাখাই এক instruction-এ থাকলে সেগুলো দৃশ্যমান থাকে।** আগের lowering-এ ternary-কে এমন binary operator দিয়ে উত্তর দেওয়া হতো যার right operand শুধু consequence — alternative block তৈরি হতো, তারপর ফেলে দেওয়া হতো, আর emit হওয়া IR পড়ত `_t2 = _t1 ? "big"`, `n > 3`-এর জন্যও `n <= 3`-এর জন্যও। দুই শাখা নামায় এমন select ভুলভাবে print করাই যায় না, তাই ক্ষতি IR-তেই দেখা যায়, অনেক পরে ভুল উত্তর হিসেবে নয়।

### ADR-0024: HIR ফেলে দেওয়া নোডকে নাম দেওয়া হয়, nil ফেরত নয়

**সিদ্ধান্ত:** অনুবাদ নেই এমন AST নোড nil দেয় না — নাম ও গণনা `unhandled`-এ জমা হয়, এবং একটি র‍্যাচেট টেস্ট সেই তালিকাকে লিখিত তালিকার সাথে মেলায়।

**কারণ:** nil একটি বৈধ খালি অনুবাদের সাথে চেনা যায় না, তাই নীরবে বন্ধ হয়ে গিয়ে যাওয়া construct আর কখনোই না-বিদ্যমান construct দেখতে হুবহু এক। যে ফাঁক রেখে দিয়েছিল L3.1 — else শাখা — ঠিক এই অদৃশ্যতার উদাহরণ।

**প্রস্তাবিত, অসম্পূর্ণ:** র‍্যাচেট এখন ১২টি feature-এর ফাঁক নামায় (for, while let, break, continue, export, struct, enum, type, trait, ?., ??, task/await)। এগুলোর অনুবাদ L3.2-এর বাকি কাজ। টেস্টটি শূন্য ফাঁক দাবি করে না — এমন টেস্ট সবসময় ব্যর্থ হতো, আর সবসময়-ব্যর্থ টেস্ট কেউ পড়ে না।

**যা ঘটেছে:** র‍্যাচেট নিজেই প্রথম চালেই দুটি ভুল দাবি ধরেছিল — import ও impl আসলে অনুবাদিত, ফাঁক তালিকা থেকে সরানো হয়েছে। এটাই instrument-এর কাজ করার প্রমাণ।

### ADR-0025: requires এখনও parse হয় না

**সিজ্ঞাপন:** L3.2-এর coverage জোতে ধরা পড়ে যে `fn f(a: Int) -> Int requires a > 0 { ... }` parse-ই হয় না — parser একটি quoted capability নাম চায়।

**কেন এখানে:** L1.11-এ requires সম্পন্ন হিসেবে চিহ্নিত ছিল, কিন্তু HIR/MIR স্তরে পৌঁছানোর আগেই এটি ভাঙে। সেই চিহ্ন ভুল ছিল; এখানে লেখা হচ্ছে যাতে পরের ধাপে ধরা পড়ে।

**ফলাফল:** main পাথে requires কাজ করে কি না যাচাই করা এখন বাকি — এটি L3.2-এর সাথে বন্ধ করা উচিত।

### ADR-0026: backend lowered program compile করে, parsed program নয়

**সিদ্ধান্ত:** `cmd/nil/backend_program.go` — প্রতিটি backend `Result.Lowered` পড়ে, `Result.Program` নয়। চুক্তিটি এখন একটি ফাংশনে।

**কারণ:** `Result.Lowered`-এর নিজস্ব ডকুমেন্টেই লেখা ছিল "backends must compile Lowered, never Program", আর তিনটি call site সেটা ভাঙছিল। কিছুই ব্যর্থ হয়নি — প্রোগ্রামগুলো শুধু আলাদা আচরণ করেছিল, আর সেটা একটি coverage test ছাড়া কেউ ধরতে পারেনি।

L3.2-এর পুরো খরচ এটাই ছিল। unlowered tree পেলে HIR পথ `for`, `match`, `struct`, `trait`, `?.`, `??`-এর মুখোমুখি হতো — যেগুলো lowering pass `while` loop, `if` chain আর call-ে desugar করে — আর এর একটিও জন্য কেউ ছিল না। তাই প্রতিটির জন্য HIR-এ **আলাদা implementation** বানাতে হতো, যা ঠিক সেই duplication যা এই চুক্তি ঠেকাতে।

**ফলাফল:** একটি লাইনে ছয়টি construct বন্ধ। বাকি ছয়টির জন্য নতুন HIR নোড: `BlockExpr`, `TypeDeclStmt`, `LoopControlStmt`, `TaskExpr`, `AwaitExpr`, এবং `FnLit.Name`।

**প্রস্তাবিত, অসম্পূর্ণ:** `FnLit.Name` কখনোই পড়া হতো না, তাই প্রতিটি ফাংশন HIR-এ `fn()` হয়ে যেত — দুটি ফাংশন IR-তে আলাদা করা যেত না। coverage test এটি ধরেছে, কারণ claim-টা নিজেই ছিল না।

### ADR-0027: declaration তথ্য, শূন্য নয়

**সিদ্ধান্ত:** `struct`, `enum`, `type`, `trait`, `export` প্রত্যেকই `TypeDeclStmt`-এ থামে — instruction না জমিয়ে।

**কারণ:** run-time-এর কোনো struct দরকার নেই, কারণ field স্থিরভাবে যাচাই হয় এবং তার value সাধারণ map। কিন্তু run-time-এর যা দরকার নেই, তা ফেলে দেওয়ার জন্য সমান নয়: ফেলা নোড report করা যায় না, print করা যায় না, আর "এই প্রোগ্রাম কী ঘোষণা করে?" — প্রশ্নটাই অনুত্তরযোগ্য থাকে না। ভাষা সার্ভারের প্রথম প্রশ্ন সেটিই।

**তাই ঘোষণা তথ্য হিসেবে থাকে, আর কিছু emit করে না।** Backend উপেক্ষা করে — যা তারই করার কাজ — আর যার দরকার তার কাছে পড়ার মতো থাকে।

### ADR-0028: optimizer প্রতিটি node পুনর্গঠন করলে প্রতিটি field কপি করে

**সিজ্ঞাপন:** `nil hir` প্রতিটি named function কে `fn()` দেখাত, অথচ optimization-এর আগের HIR-তে নাম ঠিক থাকত।

**কারণ:** `optimizeExpression`-এর `FnLit` case node **পুনর্গঠন** করে (`return &FnLit{...}`), আর `Name` field কপি করত ভুলে গিয়েছিল। বাদ পড়া field ব্যর্থতা তৈরি করে না — এটি ৯৯% সঠিক একটি node তৈরি করে, আর বাকি ১% সম্পূর্ণ অন্য জায়গায় দেখা যায়।

**কেন সন্দেহ হয়নি:** পার্থক্য কেবল optimizer চালানোর পর দেখা যায়, তাই মনে হয় folding logic-এ দোষ — আসলে দোষ একটি বাদ পড়া field-এ।

**প্রসারিত:** `TestTheOptimizerPreservesNodeIdentity` এই শ্রেণির বাগের জন্য। assertion optimized text-এ, কারণ বাদ পড়া field সেখানেই দৃশ্যমান। আজকার মুহূর্তে `FnLit`-ই একমাত্র ছিল — বাকি সব node সব field অক্ষত রাখে — নতুন case যোগ হলে নতুন টেস্ট লাগবে না, শুধু field কপি করতে হবে।

### ADR-0029: literal একটি call নয়, instruction

**সিদ্ধান্ত:** `AggregateInst` — `OpArray n` ও `OpHash 2n`, ভুয়া builtin নয়।

**কারণ:** lowering `call array(1, 2, 3)` ও `call map("k", 7)` emit করত, যেগুলো নাম VM-এ নেই। ফলে list বা map literal-যুক্ত **প্রতিটি** প্রোগ্রাম `undefined function array in MIR call` দিয়ে ব্যর্থ হতো।

একটি literal কিছুকে call করে না, এবং একে call লিখলে এমন একটি ফাংশন বানানো হয় যা প্রতিটি backend-কে শেখাতে হতো — VM-এর সাথে সম্পর্ক নেই এমন একটি obligation, যা প্রতিটি backend-এ আবার পরিশোধ করতে হতো। Instruction হলো প্রতিটি backend-এ একই বাক্য।

### ADR-0030: তিন ইঞ্জিন, একটি মাপকাঠি

**সিদ্ধান্ত:** `TestThreeEnginesAgree` — একই প্রোগ্রাম evaluator, direct compiler ও MIR emitter-এ চালিয়ে তিনটির একই উত্তর দাবি।

**কারণ:** অন্য কোনো backend-এর সাথে কখনো মতবিৎমতা হয়নি, সেটা মানে নয় সে মিলেছে — না পরীক্ষিত। চারটি বাগ MIR-এর লেখা পড়ে কখনোই ধরা পড়ত না: `_t2 = call array(1, 2, 3)` মাঝে মাঝে যুক্তিসঙ্গত instruction-এর মতো দেখায়; কেবল চালালে বলাই যায় সেই ফাংশন নেই।

**যা ধরা পড়ল:** subscript ও field access কোনো opcode-ই emit করত না — দুই operand stack-এ এড়িয়ে যেত, ফলে **index-টাই** destination-এ যেত। অর্থাৎ `xs[1]` → `1`, `m["k"]` → `"k"`। উত্তরের আকৃতি ঠিক, প্রশ্নটা ভুল।

**আরও:** builtin call-এ argument আগে, callee পরে push হতো, তাই প্রতিটি builtin ব্যর্থ হতো এমন বার্তায় যা argument-এর নাম ধরে, ক্রমের নয় — ফলে বার্তা থেকে বাগটি চেনা যায়নি।

### ADR-0031: MIR পথ নির্বাচনযোগ্য, default নয়

**সিদ্ধান্ত:** `--backend=mir` পথটি চালু; default থাকে পুরনো direct compiler।

**কারণ:** চারটি বাগ ভাষার core-এর। module, import, `task`/`await`, component ও capability তুলনার বাইরে আছে। একটি পরীক্ষিত পথকে আংশিক-পরীক্ষিত পথে বদলানো ঠিক সেই duplication-এর চেয়ে খারাপ বিনিময়, যা L3.4 বাতিল করতে এসেছিল।

**গেট:** পূর্ণ স্যুট কনফরম্যান্স — flag নয়।

### ADR-0032: optimizer-এর "dead" অপরিচিত instruction-এর চেয়ে বিপজ্জনক

**সিজ্ঞাপন:** নতুন instruction যোগ করার পর DCE তার operand গুনতে পারেনি, ফলে সেই instruction-এর পড়া সব temporary "dead" ঘোষিত হয়ে মুছে গিয়েছিল — instruction-টি নিজে টেকে।

**কারণ:** DCE জিজ্ঞেস করে "এটা কী পড়ে?" — এবং switch-এ না-চেনা কিছুর উত্তর ধরে "কিছু না"। এই ডিফল্ট সতর্ক নয়: অপরিচিত instruction কিছুই পড়ে না বলে গণ্য হয়, তাই তার পড়া প্রতিটি temporary-ই মারা যায়।

**ফল:** ভেতরে সামঞ্জস্যপূর্ণ কিন্তু ভুল উত্তর দেওয়া একটি প্রোগ্রাম। `SelectInst` ও `AggregateInst` দুটোই switch-এ অনুপস্থিত ছিল, আর লক্ষণ ছিল একটি `??` যার guard মুছে গিয়েছিল — যার ফলে কেউ লেখেনি এমন একটা slot পড়া হচ্ছিল।

**প্রস্তাবিত:** `TestDeadCodeEliminationKeepsEveryOperandKind` প্রতিটি instruction-এর একটি case তৈরি করে এবং তার নিজস্ব পড়া temporary কে বেঁচে থাকতে বাধ্য করে।

### ADR-0033: hoist করা যায় না, যখন নামটি কোনো nested loop ব্যবহার করে

**সিজ্ঞাপন:** `let j = 0; while j < 3 { ... j = j + 1 }` — উপরের loop থেকে `let j = 0` বেরিয়ে গিয়ে reset একবার হচ্ছিল, ফলে inner loop একবারই চলছিল। ৯-এর বদলে গণনা হচ্ছিল ৩।

**কারণ:** প্রথম নিয়ম (`written`-এর সাথে মানের নামের সেট হঈন) ধরে নেয় না — কারণ binding-এর *অবস্থানে* কোনো statement `j` লেখে না; লেখে এর পরের inner loop। শুধু পরেরটি দেখলেই বোঝা যায়।

**নিয়ম:** শুধু *loop* একটি binding খায় — কারণ loop বদলে দেয় তার counter কখন reset হবে। একটি সাধারণ পড়া হয় না: hoist-এর পরেও binding scope-এ থাকে।

**নীরবতা:** ভুল hoist ভাঙে না, সংকেত দেয় না — শুধু একটি সংখ্যা দেয়, একবার, এমন প্রোগ্রামে যেটি ঠিকই মনে হয়েছিল। তাই `TestHoistingKeepsLoopAnswersCorrect` আছে, যা loop-কে চালিয়ে **উত্তর** দাবি করে, কেবল আকার নয়।

### ADR-0034: বেঞ্চমার্ক মাপা হয়, দাবি করা হয় না

**সিদ্ধান্ত:** `TestMeasureOptimisationGain` সাতবার চালিয়ে **সবচেয়ে দ্রুত**টি রাখে এবং ফলাফল ছাপে — pass/fail শর্ত নয়।

**কারণ:** এত ছোট প্রোগ্রামের একবারের রান মেশিনের অন্য কাজের দ্বারা প্রভাবিত: একটি GC pause, একটি scheduler tick। একবার মাপলে এই optimizer টানা দুই চালে +৩০% মন্দ এবং +৩০% দ্রুত দুটোই দেখিয়েছিল — যা মাপার চেয়ে বড়, তাই একবারের সংখ্যা অনুপস্থিত সংখ্যার চেয়েও খারাপ।

**সর্বনিম্ন কেন:** রানে যা *যোগ* হয় তা সরিয়ে দেয়, যা রান করে তা নয়। দুটি সর্বনিম্নের পার্থক্য দুটি প্রোগ্রামের পার্থক্য।

**প্রকৃত ফল:** repeated-computation loop-এ **+৩৯% থেকে +৪৪%**, gate পূরণ। অন্য দুটো benchmark-এ সামান্য — এবং সেটাই সত্যিগত: সেগুলোতে hoist বা GVN-এর কাজ নেই।

### ADR-0035: টেক্সট LLVM IR, C++ binding নয়

**সিদ্ধান্ত:** MIR থেকে টেক্সট LLVM IR (`.ll`) emit হয়; `clang` তা থেকে বাইনারি বানায়।

**কারণ:** LLVM-এর C++ API-তে binding নিলে কম্পাইলার একটি LLVM সংস্করণ, একটি C++ টুলচেইন ও একটি প্ল্যাটফর্মের লাইব্রেরি convention-এ বাঁধা হতো। আটটি টার্গেটে বিল্ড করা একটি ভাষা কম্পাইলারে এই সীমাবদ্ধতা চায় না — বিল্ড করা মেশিনে চায়।

টেক্সট একটি নথিভুক্ত আদান-বিনিময় বিন্যাস। `clang`, `llc`, `lli` — সব পড়তে পারে।

### ADR-0036: `clang` যথেষ্ট, `llc` ঐচ্ছিক

**সিজ্ঞাপন:** এই মেশিনে `clang 22.1.8` আছে কিন্তু **`llc` নেই** — বর্তমান সরকারি Windows LLVM ইনস্টলারে `llc` কম্পাইলার ডেভেলপমেন্ট প্যাকেজে পড়ে, end-user প্যাকেজে নয়।

**কারণ:** `clang` `.ll` পড়ে এক ধাপে লিংকও করে। `llc` অবজেক্ট ফাইলে থেমে যায়, তারপর দ্বিতীয় invocation ও C runtime-এর object তালিকা লাগে।

**ফলাফল:** `llc`-কে আবশ্যক ধরলে এমন মেশিনে "toolchain নেই" বলা হতো যেখানে চমৎকার কম্পাইলার আছে — সবচেয়ে বিভ্রান্তিকর উত্তর, কারণ সেটি মিথ্যা।

### ADR-0037: গণিত একটি runtime call, LLVM instruction নয়

**সিদ্ধান্ত:** `+`/`-`/`*`/`/`/`%` runtime-এর ফাংশনে যায়।

**কারণ:** একটি Nilang `Int` একটি tagged value — boxed number, inline ছোট integer, বা pointer হতে পারে; একই `i64`-এ `Bool`, `String`, list বা map-ও থাকে। দুইটি এর উপর `add i64` একটি সংখ্যা দেয়, যা ভাষার `+`-এর অর্থ নয়: ভাষার `+` দুই স্ট্রিংয় জোড়া লাগায়, আর স্ট্রিং ও integer-এ ত্রুটি।

সরাসরি `add` runtime-এর tagging বুঝতে হতো — অর্থাৎ interpreter ও VM-র পাশে **`+`-এর আরেকটি ব্যাখ্যা** তৈরি হতো।

### ADR-0038: প্রতিটি ভেরিয়েবল একটি `alloca`

**সিদ্ধান্ত:** MIR-এর প্রতিটি ভেরিয়েবল entry block-এ `alloca` পায়।

**কারণ:** সবচেয়ে সরল সঠিক মেমরি মডেল, এবং ইচ্ছাকৃতভাবে দ্রুততম নয়: প্রতিটি slot-এর নাম ও ঠিকানা থাকে, তাই মান branch-এর সমন্বয় করার বদলে নামে পড়া-লেখা হয়। LLVM-এর `mem2reg` এক ধাপেই এগুলো register-এ উন্নীত করে — তাই এটি "স্পষ্টভাবে সঠিক"-এর দাম, একবার একটি জানা অপটিমাইজেশন ধাপে দেওয়া।

### ADR-0039: select দুই শাখাই branch-এর আগে মূল্যায়ন করে

**সিদ্যুত:** `cond ? a : b`-এর দুই arm-ই branch-এর আগে emit হয়; `phi` শুধু তাদের নাম করে।

**কারণ:** LLVM প্রতিটি `phi`-কে তার block-এর **শুরুতে** চায়। তাই arm-এর মান branch-এর পরে তৈরি হলে লেবেল ও `phi`-এর মাঝে একটি constant পড়ে — যা LLVM গ্রহণ করে না ("PHI nodes not grouped at top of basic block")।

অ-নেওয়া শাখা মূল্যায়ন করার ব্যয় একটি বাতিল হওয়া call, যা `instcombine` সরায় — LLVM-যা না গ্রহণ করে তার চেয়ে সস্তা।

### ADR-0040: emitter-এর পাঁচটি বাগ clang-ই ধরিয়েছে

| বাগ | ত্রুটি |
|---|---|
| `store`-এ value-তে type token নেই | literal কাজ করে, computed value করে না — "expected value token" |
| `copy` opcode নেই | "expected instruction opcode" |
| প্রথম block `entry` নামের হতে হয় | "expected instruction opcode" |
| local নাম unique হতে হয় | "multiple definition of local value" |
| `phi` block-এর শুরুতে | "PHI nodes not grouped at top" |

**কেন এগুলো লেখার সময় বোঝা যায়নি:** প্রতিটির বার্তা **ব্যবহারের দিকে** দেখায় — `store`-এর বদলে constant-এর, `call`-এর বদলে name-এর। পাঁচটিই এমন একটি সাধারণ রূপ: **যে জিনিসটি প্রথম ভাঙে সেটি সঠিক ছিল, আর যেটি ভাঙে সেটি সাধারণ দেখায়।**

তাই দুই ধরনের পরীক্ষা আছে: emitted **text**-এর উপর (যেখানে forward reference ধরা পড়ে), এবং **clang-এর** কাছে জিজ্ঞেস করে (যেখানে বাকিগুলো ধরা পড়ে)। দুটোই দরকার ছিল — একটি ছাড়া অন্যটি অসম্পূর্ণ।

## ৯. L4 — LLVM ব্যাকএন্ড: সম্পন্ন কাজের বিবরণ

L4-এর কাজ ছিল একটি backend বানানো যা শুধু তৈরি হয় না, বরং **অন্য দুই engine-এর হুবহু একই উত্তর** দেয়। সেই কাজের সবচেয়ে কঠিন অংশ ছিল কোড লেখা নয় — ছিল তিন প্রকার ব্যাগ ধরা, যেগুলো পরীক্ষা ছাড়া কখনো ধরা পড়ত না।

### ৯.১ তিন-ইঞ্জিন গেট

`tests/conformance/threeengines_test.go` এখন একই ২৪৫টি কেস **তিনটি** ইঞ্জিনে চালায় — interpreter, VM, এবং compiled। শুরুতে তিনটির মধ্যে **০টি** কেস তুলনা হতো; এখন **১০৪টি**।

গেটের নীতি: যে skip-এর কারণ প্রজেক্ট লিখেনি, সেটি **ব্যর্থতা**। তাই skip-এর প্রতিটি কারণ লিখিত এবং পরীক্ষা করা।

### ৯.২ যে ব্যাগগুলো তিন ইঞ্জিনের তুলনা ছাড়া কখনো ধরা পড়ত না

| সংখ্যা | ব্যাগ | কোথায় |
|---|---|---|
| ১ | `a[1] = 9` HIR-এ পৌঁছাতেই না — `lowerStatement`-এর switch-এ ঐ node-এর কেস ছিল না, আর ঐ switch-এ `nil` মানে "কিছু নয়" | `compiler/hir/lower.go` |
| ২ | `if` উভয় শাখা থেকে `return` করলে merge block অপ্রাপ্য, তবু MIR তার মান রেখে দিত — `ret i64 %t2` যেখানে `%t2` কোথাও define নয় | `compiler/mir/lower.go` |
| ৩ | ফাংশনের body expression-এ শেষ হলে সেটাই ফাংশনের মান — কিন্তু দুই path-ই (`FnLit`, component) nil ফেরত দিত | `compiler/mir/lower.go` |
| ৪ | `"1" == 1` সত্য হওয়ার কথা (interpreter `Inspect()` তুলনা করে), কিন্তু runtime-এ string-এর পাশে অ-স্ট্রিংয়ের কোনো নিয়ম ছিল না | `runtime/core/src/value.c` |
| ৫ | দুই boolean-এর মধ্যে `==` — `nil_int_cmp` শুধু সংখ্যা চিনতো | `runtime/core/src/value.c` |
| ৬ | `null == null` — nil কোনো তুলনাতেই ছিল না | `runtime/core/src/value.c` |
| ৭ | তালিকার সীমার বাইরে **পড়া** nil দিত, কিন্তু **লেখা** ভুলও নয় — দুটোই ভিন্ন প্রশ্ন | `runtime/core/src/collections.c` |

**১ নম্বরটি সবচেয়ে বিপজ্জনক ছিল।** `a[1] = 9` compile হতো, চলতো, আর লিখতাম **না** — পরের পড়তে আগের মান ফিরত। কোনো ত্রুটি ছিল না। শুধু interpreter আর VM সঠিক ছিল কারণ তারা AST হাঁটে; HIR পথের কাজ ছিল না।

### ৯.৩ যে ব্যাগগুলো clang-ই ধরিয়েছিল

| বাগ | ত্রুটি |
|---|---|
| call-এর argument-এ type token নেই | "invalid type for function argument" — `%kint0`-এর দিকে caret, যা সম্পূর্ণ সাধারণ দেখায় |
| parameter-এর নাম `%arg0`, কিন্তু signature-এ নাম নেই | "use of undefined value '%arg0'" |
| দুই block-এ একই temp | "multiple definition of local value" |

**প্রথমটির কারণ সবচেয়ে অদ্ভুত:** LLVM-এর text parser একটি call-এর argument-কে `type value` জোড়া হিসেবে পড়ে — `call i64 @f(%x)` **অবৈধ**, `call i64 @f(i64 %x)` বৈধ। লিখতে গিয়ে এটা মনে হয়নি, কারণ text দেখতে সম্পূর্ণ সাধারণ।

### ৯.৪ দুটি সিদ্ধান্ত যেগুলো ইচ্ছাকৃতভাবে ছেড়ে দেওয়া হয়েছে

**`nil_set_field` বাতিল করা হয়েছে।** Member-এ লেখা আর subscript-এ লেখা একই runtime function হওয়ার কথা ছিল, যাতে `m.name = 1`-এর ভুল বার্তা আসে। কিন্তু parser `m.name = v`-কে আগেই subscript-এ রূপান্তর করে দেয়, তাই MIR-এ পৌঁছানোর আগেই পার্থক্যটি মুছে যায়। একটি flag রাখলে সেটি **সবসময় false** হতো — অর্থাৎ IR যা জানে না তার একটি মিথ্যা দাবি। read-পাশে পার্থক্য টেকে আছে (`nil_get_field` আলাদা, কারণ সেখানে parser মুছে দেয়নি); একটি অসমতা একটি সবসময়-মিথ্যা field-এর চেয়ে ভালো।

**`nil_len` বানানো হয়নি।** `len` একটি নির্দিষ্ট builtin নয় — এটি যা পায় তার ধরনের উপর নির্ভর করে। `nil_array_len`-এর সাথে মিলিয়ে দিলে string-এর দৈর্ঘ্য শূন্য হতো আর অনুপস্থিত key-এরও, কিছু না বলেই। যতক্ষণ না সঠিক ফাংশনটি আছে, call-টি **নামসহ প্রত্যাখ্যান** করা হয় — ভুল উত্তরের চেয়ে অনেক ভালো।

### ADR-0046: তিন ইঞ্জিনের সমানতা হলো গেট, কোড review নয়

একটি backend সঠিক বলে দাবি করা যায় না যতক্ষণ তা **অন্য দুটি engine-এর হুবহু একই উত্তর** দেয় না। কারণ দুটি ইঞ্জিন ভুল হলে সেটি দুজনের একই ভুল, আর সেটি দুজনেই লুকানো থাকে।

এই কাজে গেটটি ছয়টি অমিল ধরেছে, যার প্রতিটিই একটি নীরব ব্যাগ ছিল — কোনোটিই compile ব্যর্থতা বা runtime crash দিয়ে বেরোয়নি। সবগুলোই তিন ধরনের পরীক্ষা ছাড়া শূন্য: unit test, লিখিত IR-এর পাঠ, এবং শুধু এক engine চালানো।

**পরিণাম:** গেট বন্ধ না করেই প্রতিটি bug-এর পরে চালানো হয়েছে। শেষ অবস্থায় ১০৪/২৪৫ তুলনা, **০টি অমিল**, **০টি অপ্রত্যাশিত skip**।

### ADR-0047: পার্থক্য তিন ধরনের, এবং প্রতিটির নিজস্ব ধরনের পরীক্ষা দরকার

এই কাজে প্রতিটি ব্যাগের ধরন আলাদা ছিল, এবং কোনো একটি পরীক্ষা-পদ্ধতি একাও ধরতে পারত না:

| ধরন | কী ধরে | কোন পরীক্ষা |
|---|---|---|
| **নীরব ব্যাগ** (কিছুই ব্যর্থ হয় না) | ইঞ্জিন তিনটিই চলে, উত্তর আলাদা | তিন-ইঞ্জিন গেট |
| **ভুল IR** (text সঠিক দেখায়) | assembler অস্বীকার করে | emitted text-এর forward-reference scan |
| **প্রত্যাশিত অস্বীকার** (gap আছে) | backend নিজেই বলে কী পারে না | skip-এর কারণ লিখিত থাকতে হবে |

তিনটিই দরকার ছিল। একটি ছাড়া অন্যটি অসম্পূর্ণ: গেট ছাড়া IR-এর ব্যাগ ধরা পড়ে না, text-scan ছাড়া runtime-এর ব্যাগ ধরা পড়ে না, আর skip-এর কারণ না লিখলে অসম্পূর্ণতা লুকানো থাকে।

### ADR-0048: যা backend পারে না তা **নামসহ** অস্বীকার করা হয়

আগে একটি অজানা callee সরাসরি `@nil.Some`-এ emit হতো, আর assembler বলত "use of undefined value" — যা একটি code-generation বাগের মতো শোনায়, আসলে তিন ধাপ আগের `Some` ধরে।

এখন emitter বলে: **`llvm: no lowering for a call to X: it is not a function this module defines and not a builtin with a runtime function`**।

কারণ: একটি লিখিত skip হলো এমন ফাঁক যা কেউ বন্ধ করতে পারে। আর একটি assembler বার্তা যা দেখতে সাধারণ লাইনের দিকে তীর দেখায়, সেটি হলো এমন ফাঁক যা শূন্য থেকে ডায়াগনস্টিক করতে হয়।

**পাশাপাশি একটি সীমা:** builtin তখনই তালিকাভুক্ত হয় যখন runtime-এ তার **ঠিক** অর্থের ফাংশন আছে — কাছাকাছি নয়। `push` নতুন list ফেরত দেয় কিন্তু `nil_array_set` জায়গায় পরিবর্তন করে; সেটুকু মিলিয়ে দিলে এমন প্রোগ্রাম হতো যা compile করে, চলে, আর alias করে।

### ADR-0049: তালিকার সীমার বাইরে **পড়া** nil, **লেখা** ত্রুটি

এটি interpreter-এর নিয়ম, এখানে নতুন কিছু নয় — কিন্তু লেখা উচিত, কারণ এটি অস্বাভাবিক।

- **পড়া** একটি প্রশ্ন: "অবস্থান ১০-এ কী আছে?" — তিনটির তালিকার উত্তর "কিছু নেই", যা ইতিমধ্যেই nil-এর অর্থ। এটি অনুপস্থিত map key-এর উত্তরও, তাই miss-সম্ভব যেকোনো lookup-এ আলাদা করে check লাগে না।
- **লেখা** সম্ভব নয়: অবস্থান ১০-এ কোনো slot নেই। নীরবে বাড়ালে প্রোগ্রাম যে পড়তে পারে তার দৈর্ঘ্য বদলে যেত, আর প্রত্যাখার করলে সোজা বলা হয় যে প্রোগ্রামটি ভুল। এটি ভুল, এবং থেমে গেলেই সে জানতে পারে।

`nil_array_get` — primitive — এখনো ত্রুটি দেয়, কারণ সেটাকে যে অস্তিত্ব অবাস্তব জিজ্ঞেস করে তার উত্তর জানা দরকার। ভাষার subscript operator আগে check করে।

### ADR-0050: string-এর পাশে অ-স্ট্রিং তুলনা হয় **লেখিত পাঠে**

`"1" == 1` সত্য। এটি অদ্ভুত লাগে, যতক্ষণ না লক্ষ্য করা যায় একই নিয়ম `1 == "1"`, `"2.5" == 2.5` আর `"true" == true` — সবকিছু সত্য করে, এবং সেটি সামঞ্জস্যপূর্ণ ও যাচাইযোগ্য।

এটি **interpreter-এর** নিয়ম, এবং যে কারণে সেটি অনুসরণ করতে হয়: ভাষার পর্যবেক্ষিত আচরণ interpreter-ই সংজ্ঞায়িত করে।

runtime-এ কারণটি এক বাক্যে: **যে জিনিসটি একটি অপারেটরের কাছে যায় তার ধরন কোনো কিছু পরীক্ষা করেনি**, তাই runtime-ই জানে সে কী। `+`-এর যুক্তিই একই (ADR-0037)।

### ADR-0051: nil সমানতার প্রশ্নের উত্তর, কারণ ভাষার প্রতিটি lookup nil দিতে পারে

`x == null` ভাষার সাধারণ পরীক্ষা — এটাই একটি lookup কিছু পেয়েছে কি না জিজ্ঞেস করার উপায়। missing key, তালিকার সীমার বাইরে পড়া, না-থাকা member — সবাই nil ফেরত দিতে পারে।

তাই nil-কে type error করলে ভাষার সবচেয়ে সাধারণ পরীক্ষাটিই অউত্তরযোগ্য হতো না।

এটি আলাদা case নয়: interpreter-এর যে কোনো case-এ না পড়া জোড়া `operator ==` ছেকে পড়ে, যা pointer identity — আর দুই null একই pointer।

### ADR-0052: দুই block-এ লেখা একটি temp `phi` দিয়ে যোগ হয়

দুই `if` শাখা একই MIR temp-এ লেখে — এটাই **একটি** মানের দুই লেখা। প্রতিটিতে `%t1 = add i64 ...` emit করলে একই নাম দুইবার define হয়, আর LLVM "multiple definition of local value" বলে — যে লাইনটি সম্পূর্ণ সাধারণ দেখায়।

তাই প্রতিটি block নিজস্ব নামে লেখে (`%t1.bb_then`), আর merge block `phi` দিয়ে যোগ করে।

**একটি বিষয় `phi` পায় না:** একটি MIR **ভেরিয়েবল** slot, temp নয় — তার একটি `alloca` আছে এবং প্রতিটি block সেই একই ঠিকানা পড়ে-লেখে। প্রতি block-এ `phi` দিলে সেটি সঠিক এবং অর্থহীন: alloca-ই block ঠিক করে দেয়, তার উপর `phi` যা ঠিক করা তার উপর যা ঠিক করা।

### ADR-0053: প্রতিটি ফাংশন `i64` ফেরত দেয় — `main`-ও

শুধু entry-র `i64` ফেরত দেওয়ার কথা ছিল, কারণ সেটিই একমাত্র জায়গা যেখানে প্রোগ্রামের উত্তর বাইরে যায়।

কিন্তু `void` ফেরত দেওয়া এমন module বানায় যেখানে call-এর ফল **undefined**: LLVM গ্রহণ করে, linker গ্রহণ করে, আর প্রোগ্রাম register-এ যা পড়ে পায় সেটাই পড়ে।

একটি স্বাক্ষর সবার জন্য। কোনো caller-কে undefined কিছু দেওয়া যায় না — এটিই লাভ।

(`main` ছাড়া: সেটা C-এর entry, C তাকে `int` ফেরত দিতে বলে।)

### ADR-0054: নামাঙা ফাংশন সরাসরি call হয়; শুধু যদি module সেটা **নিশ্চিত** করে

প্রতিটি call runtime-এর মড়া call-এর মধ্য দিয়ে যাওয়া ভুল ছিল, দুই কারণে: callee কখনো callable value-তে পরিণত হয়নি, এবং arguments একটি Nilang array হিসেবে যাচ্ছিল।

কিন্তু শুধু "module-এ নাম আছে" যথেষ্ট নয় — `emitCall`-এ একটি map lookup করে যাচাই করে, কারণ অজানা নাম সরাসরি call করলে assembler-এর কাছে এমন module যায় যেটি অস্বীকার করে এবং কিছুই বলে না কেন।

সরাসরি call-ই দ্রুতটাও, আর এটাই সেই কারণ যার জন্য compile করা হয়।

### ADR-0055: runtime ABI-র একটি পরীক্ষা, header যা পুনর্বিল্পিত হয়েছিল

`runtime/core/include/nil.h` একটি ভুল PowerShell অভিযোরণে ধ্বংস হয়ে গিয়েছিল — git-এ ছিল না, তাই পুনরুদ্ধার করা যায়নি।

এটা ঘটে যাওয়ার কারণটা লেখার দিকে নয়, **করার** দিকে: বাংলা ও em-dash-সহ বহু-লাইনের string replace এডিটকে চিঁড়িয়ে দিয়েছিল।

`nil.h` পুনর্বিল্পনা করা হয়েছিল `.c` ফাইলের definition, `nil_internal.h`, এবং emitter-এর ABI table — তিনটি মিলিয়ে প্রতিটি signature-ই। পুনর্বিল্পনার পরেই প্রথম সংকলনে চারটি অসঙ্গতি ধরা পড়ল, এবং সেগুলো এক এক করে ঠিক করতে হয়।

**যা এই থেকে শেখা গেল:** `TestEveryRuntimeSymbolIsDeclaredAndMatchesItsHeader` — যা আগে থেকেই ছিল — কয়েক ঘণ্টার মধ্যেই ধরল যে ABI table-এ একটি `nil_set_field` entry বাকি ছিল, header-এ নেই। **ABI-র পরীক্ষা তখনই কাজ করে যখন header ভুল হয়, কারণ তখনই তার সবচেয়ে বেশি দরকার।**

## ১০. L5 — C FFI স্তর: সম্পন্ন কাজের বিবরণ

L5-এর নয়টি কাজের মধ্যে **L5.1 (`extern` ঘোষণা)** ও **L5.3 (মান রূপান্তর)** সম্পন্ন। বাকিগুলো নিচে।

এই কাজের সবচেয়ে শিক্ষণীয় বিষয় ছিল এটি: **ঘোষণা করা যত সহজ, তত সহজে ভুল উত্তর দেওয়া।**

### ১০.১ যা তৈরি হয়েছে

```
extern "C" fn triple(n: Int) -> Int;
```

একটি সম্পূর্ণ চক্র: parser → AST → HIR → MIR → LLVM IR → runtime রূপান্তর → link → চলমান বাইনারি।

```
$ nil build --aot
বিল্ড সম্পন্ন: build/ffidemo.exe

$ ./build/ffidemo.exe
49                          // triple(14) + half(14)
```

### ১০.২ যে প্রশ্নটি ছিল না, আর সেটিই ছিল কাজের বেশিরভাগ

প্রথমে ভাবা হয়েছিল ঘোষণাটি যথেষ্ট। পাঁচটি রাউন্ড-ট্রিপ কেসই ভুল উত্তর দিয়েছিল:

| প্রোগ্রাম | C পেয়েছে | ফিরে এসেছে | ছাপল |
|---|---|---|---|
| `nilffi_answer()` | — | `42` | **`true`** |
| `nilffi_negative()` | — | `-7` | **`false`** |
| `nilffi_large()` | — | `8589934592` | **`null`** |
| `nilffi_double(21)` | `171` | `342` | **`null`** |

কারণ: **একটি Nilang মান একটি ট্যাগযুক্ত শব্দ** — তিনটি বিট বলে এটি কী, বাকিটা payload। C-তে এমন প্রথা নেই। C `int64_t` হলো 64 বিট সংখ্যা, আর কিছু নয়।

`42`-এর নিচের তিনটি বিট `010` = **`NIL_TAG_TRUE`**। `-7`-এর `001` = **`NIL_TAG_FALSE`**। `2^33`-এর `000` = **`NIL_TAG_NIL`**।

কোনোটিই ব্যর্থ হয়নি, কোনোটিই crash করেনি — **প্রতিটিই সঠিকভাবে compile হয়েছে, link হয়েছে এবং চলেছে। শুধু উত্তর ভুল।**

এটাই বিপজ্জনকতম ব্যর্থতার আকার: এটি প্রতিটি পরীক্ষা বাঁচে যায় যা উত্তর দেখে না।

### ১০.৩ প্রতিটি মান রূপান্তর হয়, কোনো ব্যতিক্রম ছাড়া

| Nilang | C-তে যায় |
|---|---|
| `Int` | `int64_t` |
| `Float` | `double` |
| `Bool` | `int` (0/1) |
| `Byte` | `uint8_t` |

রূপান্তর **runtime-এ** (`nil_int_unbox` / `nil_int_box`), backend-এ নয়। কারণ representation একটি runtime-এর বিষয়, আর backend-এ লেখা রূপান্তন হতো "একটি integer কী" — এর **দ্বিতীয়** বাস্তবায়ন, যেটি প্রথমবার representation বদলালে নিঃশব্দে সরে যেত।

### ১০.৪ যা **ইচ্ছাকৃতভাবে** অসম্পূর্ণ রাখা হয়েছে

`String` crossing-এ নেই। এটা L5.4-এর কাজ, এবং এখন থাকা কারণটা বোঝা দরকার:

একটি string যায় **pointer এবং length** — দুটো আর্গুমেন্ট বাইরে, দুটো ভিতরে। এটা বাস্তব কাজ।

তার চেয়েও বড় কারণ: **সম্ভাব্য রূপান্তনই এখানে সবচেয়ে খারাপ ফলাফল।** ভুল রূপান্তনে module assemble হয়, linker resolve করে, আর প্রোগ্রাম pointer থেকে length পড়ে — **build-এ নয়, ডেটায় ব্যর্থ হয়।**

তাই অসম্পূর্ণতা **নামসহ অস্বীকার** হিসেবে প্রকাশ পায়:

```
llvm: no crossing for "String": extern "strlen" takes it at parameter 1,
      and no conversion to or from C is defined for it
      (defined crossings: Int, Float, Bool and Byte)
```

L5.4 আসলে এটি মেরামত হবে একটি সম্পাদনায়; আর তার আগে লেখা প্রতিটি প্রোগ্রাম বিকাল-জুড়ে ভুল থেকে বাঁচবে।

### ১০.৫ ঘোষণা বলে **কী**, `nil.json` বলে **কোথায়**

`extern "C" fn sin(x: Float) -> Float;` বলে "আমার `sin` দরকার"। কিন্তু `sin` Linux-এ `libm`-এ, Windows-এ C runtime-এ, macOS-এ `libSystem`-এ — **এক ঘোষণা থেকে তিনটি উত্তর**, এবং linker-ই জানে কোনটি।

তাই দুটো আলাদা: প্রোগ্রাম বলে কী লাগবে, প্রজেক্ট বলে এটা কোথায়:

```json
{ "build": { "c_sources": ["c"], "libraries": ["m"] } }
```

### ১০.৬ এই কাজে পাওয়া তিনটি অপ্রত্যাশিত বাগ

| বাগ | কোথায় | ফলাফল |
|---|---|---|
| **`nil build` কখনো link করত না** | `cmd/nil/build.go` | AOT backend ছিল, কিন্তু `nil` CLI-তে কোথাও ডাকা হতো না |
| **cache-hit পথ FFI object বাদ দিত** | `compiler/nilcore` | **দ্বিতীয়** build-এ প্রতিটি `extern` call link ব্যর্থ হতো |
| **`nil.json`-এ BOM গ্রহণ হতো না** | `pkg/config` | Windows-এর যেকোনো টুলে লেখা প্রজেক্ট config পড়া যেত না |

**তিনটিই লুকানো ছিল।** প্রথমটি ধরা পড়ে কারণ L5.1-এর পরীক্ষা CLI দিয়ে চালানো হয়েছিল; বাকি দুটি ধরা পড়েছে যখন ধাপের প্রথম কাজগুলো চলছিল।

### ADR-0056: FFI-র রূপান্তর runtime-এ, backend-এ নয়

একটি Nilang মান একটি ট্যাগযুক্ত শব্দ। সেটা **runtime-এর representation** — একটি backend-এর সিদ্ধান্ত নয়।

তাই প্রতিটি রূপান্তর runtime-এর দুটি ফাংশন: `nil_int_unbox` (বাইরে) ও `nil_int_box` (ভিতরে)।

**কেন backend-এ নয়:** backend-এ লেখা রূপান্তন হতো "একটি integer কী"-এর দ্বিতীয় বাস্তবায়ন। দুটি প্রথমবার representation বদলালে নিঃশব্দে সরে যেত — যে ধরনের বাগ এই কাজের শুরু থেকেই ধরা পড়ছে।

### ADR-0057: `String` FFI-তে নেই, এবং নামসহ প্রত্যাখ্যান করা হয়

একটি string যায় pointer ও length — **দুটো** আর্গুমেন্ট বাইরে, দুটো ভিতরে। সেটা বাস্তব কাজ, সেটা L5.4।

কেন তার আগে রাখা হলো না: **সম্ভাব্য রূপান্তনই সবচেয়ে খারাপ ফলাফল।** ভুল রূপান্তনে program compile হয়, link হয়, চলে, আর ভুল উত্তর দেয় — build-এ ব্যর্থতা নয়, ডেটায়।

**নীতিটি:** অসম্পূর্ণ FFI-কে নিরাপদে ছাড়া যায় — যদি প্রতিটি অনুপস্থিত জিনিস **নামসহ** প্রত্যাখ্যান হয়।

### ADR-0058: `extern` একটি নরম keyword

`extern "C" fn ...` একটি ঘোষণা; `let extern = 1` একটি সাধারণ বাইন্ডিং।

দুটি পৃথক করতে keyword-এর পরে একটি **string** লাগে — সেটাই যথেষ্ট। শব্দটি সংরক্ষণ করলে একটি ব্যবহারযোগ্য নাম চলে যেত, আর parser-এর কোনো উপযোগী ছাড়াই।

প্রকল্পের `type`, `pure`, `unsafe`, `requires` — সবাই একই যুক্তিতে নরম।

### ADR-0059: একটি backend যা কেউ ডাকতে পারে না, backend নয়

`compiler/aot` লেখা ছিল, পরীক্ষিত ছিল, সঠিক ছিল — এবং **`nil` CLI-তে কোথাও ডাকা হতো না**। `nil build` `.ll` ফাইল লিখত, আর সেখানেই থেমে যেত।

L5.1 শেষ করার জন্য `nil build --aot` যোগ করা হয়েছে, যা native executable তৈরি করে এবং `nil.json`-এর `libraries` ও `c_sources` পড়ে।

**কারণটি সাধারণ:** L4-এর `L4.10` "AOT linker" সম্পন্ন হিসেবে চিহ্নিত ছিল। linker কাজ করত, কিন্তু কেউ তাকে ডাকত না। পরীক্ষায় ধরা পড়ে না, কারণ পরীক্ষাও সরাসরি ডাকে।

### ADR-0060: `nil.json`-এর BOM এখন গ্রহণযোগ্য

Windows-এর প্রতিটি টুল UTF-8 BOM লেখে: PowerShell-এর `Out-File`, `Set-Content -Encoding utf8`, পুরোনো Visual Studio, বেশিরভাগ editor-এর "save with encoding"।

`encoding/json` প্রথম অচেনা বাইটে থেমে যায়, তাই এমন প্রতিটি `nil.json` প্রত্যাখ্যাত হতো — এবং ত্রুটিটি ছিল `invalid character '﻿'`, যা কেউ ইচ্ছাকৃত টাই করেনি।

lexer আগেই BOM এড়িয়ে যায়। **একই প্রকল্পের দুটি reader-এর একই ধারণা থাকা উচিত** যে BOM কী।

### ADR-0061: `nil build --aot` একটি ফ্ল্যাগ, আলাদা কমান্ড নয়

Native executable তৈরি করা মানেই build করা। আলাদা একটি শব্দ হলে একই pipeline-এর দুটি কমান্ড, দুটি options সেট — এবং কম ব্যবহৃতটিই আজ ভাঙবে।

পাশাপাশি: `--dir` AOT পথে আলাদাভাবে পড়া হয়, কারণ সেই argument loop তখনো চলেনি। এটা ছাড়া `build --aot --dir x` **কারেন্ট ডিরেক্টরিতেই** build করত — যা সফল হয় এবং ভুল জায়গায় লেখে, যা ব্যর্থতার চেয়েও খারাপ।

### ADR-0062: FFI-র নাম `nilffi_`, runtime-এর নয়

`nil_int_new` ব্যবহার করা runtime ব্যবহার করা; `nil_int_unbox` ব্যবহার করা **সীমানা পার করা**। দুটি পড়ার সময় আলাদা রকম জিনিস, আর stack trace-এ সেটা আলাদা থাকা উচিত।

`runtime/ffi/` আলাদা directory, `nilffi.h` আলাদা header। `nilcore/include`-এর কোনো কিছুই `nilffi.h`-এ পৌঁছাতে পারে না — এই বিভাজনই সেটিকে বাস্তব করে, একটা convention নয়।

### ADR-0063: একটি কলব্যাক closure object, bare pointer নয়

একটি function সব closure নয়। যে function কিছু capture করে, তার captures heap-এ থাকে এবং collector সেগুলো ফিরিয়ে নিতে পারে।

একটি bare pointer নিজে থেকে কিছু বোঝায় না যে তার কী দরকার — তাই কেউ সেগুলো alive রাখতে পারে না, আর কলব্যাক ঘণ্টাখান পরে যখন ডাকা হয় তখন freed memory পড়ে।

তাই closure object: function pointer + captures, আর **C যতক্ষণ ধরে রাখে ততক্ষণ pin করা**।

Collector কিছু move করে না (ADR-0041) — তাই C-এর কাছে থাকা pointer যতক্ষণ object আছে ততক্ষণ valid। C মাত্র একটি word রাখে এবং collector-কে কখনো জানায় না।

### ADR-0064: pin শেষ হয় `nil_callback_release`-এ, আর তার আগে নয়

- **আগে** release = ব্যবহার-পরে-মুক্তি, যার জন্য একটি ডাকা হয়নি এমন কলের জন্য অপেক্ষা করছে।
- **ভুলে** release = leak; memory নষ্ট হয়, প্রোগ্রাম চলতে থাকে।
- **দুইবার** release, বা callback নয় এমন কিছু release = **উপেক্ষা করা হয়, কারণ ঘটনা নয়**।

দুইবার release করা C কোডের ভুল হতে পারে, কিন্তু তার জন্য প্রোগ্রাম থামানো তার চেয়ে খারাপ অবস্থায় রেখে দেয়।

### ADR-0065: একটি কলব্যাক দুটি মান হিসেবে পার হয়, একটি নয়

একটি C function pointer-এর কোনো context নেই, আর একটি কলব্যাককে জানতে হয় **কোন** Nilang function-টি সে।

Context দেওয়ার দুটি উপায়: pointer-এর পাশে পাঠানো — যা এটি — অথবা প্রতি কলব্যাকের জন্য নতুন machine code তৈরি করা যাতে pointer নিজেই context বহন করে।

**প্রথমটি একটি ফাংশন ও একটি লিখিত convention। দ্বিতীয়টি executable-memory allocator এবং প্রতি architecture-এ আলাদা।**

এবং সবচেয়ে ভালো কারণ: trampoline-এর ঠিকানা একটি **compile-time constant**। C নাম লিখেই `nil_callback_trampoline` ব্যবহার করতে পারে, কিছু ডেকে ঠিকানা জানতে হয় না। **ABI-তে কোথাও function-pointer মান নেই**, এবং কিছুই integer-এর মধ্যে round trip করার উপর নির্ভর করে না — যা C তে নিশ্চিত নয়।

### ADR-0066: প্রতি function-এর জন্য একটি adapter, একটি shared নয়

একটি compiled Nilang function হলো `i64 @nil.f(i64, i64)` — arguments register-এ, ক্রমে। একটি closure আহ্বান হয় `i64 (*)(NilValue *args, int64_t)` — array ও count।

**দুটি signature মেলে না।** একটি pointer রেখে অন্যভাবে call করলেই প্রতিটি কলব্যাক `0` ফেরত দিত — callee একটি argument count পড়ছিল যেখানে C একটি pointer দিয়েছিল।

তাই value হিসেবে ব্যবহৃত প্রতিটি function-এর জন্য একটি **shim** তৈরি হয়, array থেকে arguments বের করে এগিয়ে দেয়।

**Adapter কিছু রূপান্তর করে না** — কারণ দরকার নেই। Array-এর arguments আগে থেকেই Nilang value, আর ফলাফলও তাই। যে shim রূপান্তর করত, তাকে প্রতিটি parameter-এর ধরন দরকার হতো — যা MIR একটি সাধারণ function-এর জন্য বহন করে না — এবং যে shim অনুমান করত, সে `3`-কে **ট্যাগযুক্ত** `3` বানাত, যা সম্পূর্ণ অন্য সংখ্যা।

### ADR-0067: arity closure-এর সাথে যায়

Function pointer নিজের signature নিয়ে কিছু বলে না। তাই arity-ই **একমাত্র** রেকর্ড যে C কতগুলো argument পাঠাবে।

ভুল সংখ্যায় ডাকা হলে answer nil আর একটি ত্রুটি রেকর্ড হয় — C-এর argument array-এর **শেষের বাইরে** পড়ার বদলে।

গণনাটি function-এর নিজের parameter list থেকে আসে, closure তৈরির জায়গায়। অন্য কিছু হলে signature বদলালে দ্বিতীয় একটি জায়গা হতো, আর দুটো ঠিক সেই মুহূর্তে অসম্মত হতো।

### ADR-0068: function-as-value হলো slot পড়া নয়, function-কে reference করা

`let apply = twice; apply(21);` আগে `_t = load twice` হতো, আর emitter ব্যর্থ হতো `loading "twice", which has no slot` — **যে নাম variable নয়, সেটি variable হিসেবে পড়া হচ্ছিল।**

সংশোধনটি MIR-এ, emitter-এ নয়: emitter একটি `VarOperand` আর একটি load দেখে বুঝতে পারে না প্রোগ্রামটি কোনটি বোঝিয়েছে, কারণ সেগুলো আলাদা instruction যা একই নাম বহন করে।

ফলাফল: একটি function **নামানো যেত, কিন্তু ব্যবহার করা যেত না** — value তৈরি হতো, আর কেউ তার কিছু করতে পারত না।

### ADR-0069: indirect call-এ একটি array, variadic call নয়

Function value-কে ডাকা হয় arguments একটি Nilang array-তে রেখে `nil_call` দিয়ে।

প্রতিটি indirect call-এ খরচ বাড়ে — একটি allocation ও প্রতি argument-এ একটি store। এবং এটি **একটি** calling convention কেনার জন্য, দুটির জন্য নয়: একটি C-side variadic call runtime ও compiler-এর মধ্যে দ্বিতীয় convention হতো, আর দুটো প্রথমবার যেকোনো একটি বদলালেই সরে যেত।

**সুবিধা:** indirect call গুরুত্বপূর্ণ হয়ে উঠলে `nil_call`-ই একমাত্র জায়গা দ্রুত করার জন্য, কারণ array তৈরি হয় শুধু সেখানেই।

### ADR-0070: FFI-র নিজের কোডে tagged value সরকৃতি ভুল ছিল

এই কাজের সবচেয়ে বিশেষ বাগ, এবং এটি ব্যবহারকারীর কোডে নয় — **FFI-র নিজের** কোডে।

`emitIndirectCall` `nil_int_new(len(args))` দিয়ে গণনা পাঠাচ্ছিল, যা একটি **ট্যাগযুক্ত** মান ফেরত দেয়: `1` সংরক্ষিত হয় `11` হিসেবে। `nil_array_new` তার যা পায় তাকে element সংখ্যা ধরে — তাই **একটি element-এর array এগারোটি element হয়ে গেল**, আর বড় গণনা এমন বড় allocation-এ গিয়ে পৌঁছাত যা ব্যর্থ হতো:

```
nilang: out of memory allocating an array
```

যে প্রোগ্রাম একটি element চেয়েছিল।

**যেখানে একটি tagged value একটি সাধারণ সংখ্যা চায় — ঠিক এখানেই এই FFI কাজ করে।** এবং সেটি ছিল এই FFI-র নিজের কোডে, যা তার বিরুদ্ধে সবচেয়ে কম যাচাই করা হয়েছিল।

### ADR-0071: যে অস্বীকার ভুল জিনিসের নাম বলে, সেটি নিজেই বাগ

`emitCall` একটি প্রত্যাখ্যান করত — কিন্তু **ভুল জিনিসের** নাম বলে:

- একটি **foreign** call প্রত্যাখ্যাত হতো, কারণ foreign নাম module-এর function নয়। ফলে `extern "C" fn sin(...)` ঘোষণা করা যেত কিন্তু কখনো ডাকা যেত না।
- একটি **function value**-এর মাধ্যমে call প্রত্যাখ্যাত হতো, কারণ নামটি একটি variable। ফলে closure তৈরি হতো, কিন্তু কেউ তাকে ডাকতে পারত না।

দুটোই "সঠিক" প্রত্যাখ্যান ভুল জিনিসের। **একটি প্রত্যাখ্যান কী নেই তা নাম বলে — ভুল জিনিসের নাম বলা পাঠককে সেই construct-এর পেছনে পাঠায় যেটি আছে এবং কাজ করছে।**

### ADR-0072: কোনো struct-ই ফেরত ফেরত হবে না — string-ও না

L5.4 শুরুতে `nil_string_unbox` একটি struct ফেরত দিত:

```c
NilFFIString nil_string_unbox(NilValue value);
```

এটি লিঙ্ক হতো, সবকিছু সবুজ দেখাতো, এবং **প্রতিটি string-এর দৈর্ঘ্য শূন্য** ফেরত দিত।

কারণটা ব্যবহারকারীর কোডে নয় — **ABI-তে**। কোনো নির্দিষ্ট আকারের struct ফেরত আসবে register-এ নাকি একটি hidden pointer-এর মধ্যে দিয়ে, সেটা দুই compiler-এর মধ্যে **ভাগ করা কোনো convention নেই**:

| compiler | triple | `{ptr, i64}` ফেরত |
|---|---|---|
| clang | `x86_64-pc-windows-msvc` | `RAX:RDX`-এ |
| gcc | `x86_64-w64-mingw32` | hidden pointer, `RCX`-এ |

দুটোই নিজ নিজ ABI-র সঠিক বাস্তবায়ন। দুটোই **একই link-এ**। এবং call site-এ কোনো উপায় নেই বলতে যে কোনটি পেয়েছে।

একই তালিকায় `sizeof` ও `alignof`-ও (L5.9)। যতক্ষণ না সেগুলো একই দুই compiler-এ প্রমাণ করা হয়, একটি struct ফেরত দেওয়া মানে **একটি coin flip**।

অতএব সিদ্ধান্ত: **caller struct-টি `alloca` করে, callee তা পূরণ করে।** pointer যুক্তিটা শুধু একটি যুক্তি — struct-এর কোনো অর্থ নেই, register-এর কোনো convention জানার দরকার নেই। string বাইরে যায় দুটি argument হিসেবে (`ptr, i64`), ভিতরে আসে caller-এর struct-এর মধ্য দিয়ে, শেষে `nil_string_copy` একটি Nilang-owned string তৈরি করে।

**যে বক্তব্য একে অস্বীকার করেছিল, সেটি ভুল ছিল না — ভুল ছিল তার লক্ষ্য।** out-parameter নিয়ে আপত্তি ছিল "এটা বলতে পারে না অর্ধেকটা লেখা হয়েছে কি না"। সেটি সাধারণভাবে ঠিক, কিন্তু এখানে প্রযোজ্য নয়: `nil_string_unbox`-এর ঠিক একটি উত্তর আছে এবং ব্যর্থ হওয়ার কোনো উপায় নেই।

এটি কেবল ব্যবহারকারীর সমস্যা নয় — **নিজের টেস্ট দিয়ে ধরা পড়ে।** `TestNothingInAModuleIsReturnedAsAStruct` আজ থেকে module-এর প্রতিটি `declare`-এর দিকে দেখে এবং struct ফেরত পেলে ব্যর্থ হয়। আজকের অপরাধীদের তালিকা দেখে এমন টেস্ট লিখলে সেদিন কখনো অপরাধী যোগ হলে সেটি ধরা পড়ত না।

### ADR-0073: FFI-র ঘোষণাগুলো header-এর সাথে যাচাই হতো না

ADR-0042 থেকে একটি পরীক্ষা চলছে: emitter-এর প্রতিটি runtime ঘোষণা `nil.h`-এর সাথে মিলিয়ে দেখা হয়, এবং একটি ভিন্নতা হলে ব্যর্থতা। কারণটা ঠিক ছিল — `i1` বনাম `int` লিঙ্ককারকে ধরে না, program ভুল উত্তর দেয়।

**কিন্তু পরীক্ষাটি runtime-এর symbol দেখত, FFI-এর conversion নয়।** `nil_int_unbox`, `nil_string_unbox`, `nil_string_copy` — এগুলো প্রতি module-এ আলাদা করে জমা হয়, কোনো static তালিকায় থাকে না, তাই কোনো পরীক্ষাই সেগুলোকে header-এর সাথে মেলেনি।

পরীক্ষা করা হয়েছিল: `nil_string_unbox`-এর দ্বিতীয় parameter `int64_t` করা হলো। **পুরো স্যুট পাস করল।**

কারণ ঘোষণাটি pointer বলছিল, header integer বলছিল, আর প্রতিটি program এটি ব্যবহার করলে **link ব্যর্থ হতো** — symbol-এর নামে, আর type-এর নয়।

এখন `TestEveryFFIConversionMatchesItsHeader` অপেক্ষাগুলো **crossing table থেকে** বের করে, অর্থাৎ ঘোষণা লেখার **আসল কোড** পরীক্ষা করে। নিজস্ব তালিকা রাখলে emitter-এর সাথে সেটি একটি দ্বিতীয় অনুলিপি হয়ে যেত, যা কেউ যোগ করলেই পিছিয়ে যেত।

### ADR-0074: Go-এর `%q` LLVM-এর byte-string quoting নয়

L5.4-এর একটি টেস্ট `"a\0b"` ব্যবহার করে — string-এর মাঝে NUL থাকার ক্ষেত্রটি। emitter প্রত্যাখ্যান করল:

```
constant expression type mismatch: got type '[6 x i8]' but expected '[3 x i8]'
```

কারণ: constant-টি `fmt.Sprintf("%q", s)` দিয়ে লেখা হতো। **Go-র quoting আর LLVM-এর quoting আলাদা ভাষা।** দুটোই `\"`-এ একমত, বাকি সবে ভিন্ন:

| byte | Go `%q` | LLVM `c"..."` |
|---|---|---|
| NUL | `\x00` | `\00` |
| newline | `\n` | `\0A` |
| UTF-8 বাইট | raw | raw, অথবা `\XX` |

ফলে ঘোষিত দৈর্ঘ্য এবং লেখা বাইট **দুটি আলাদা encoder থেকে** আসছিল। ব্যাপারটা ইচ্ছাকৃত নয়: যে কোড `%q` লেখে সে ধরে নেয় Go-এর escape set সম্পূর্ণ, আর বাকি অর্ধেক LLVM-এর।

`llvmByteString` এখন বাইটগুলো নিজে লেখে, যাতে `[N x i8]`-এর সংখ্যাটি **আসলেই লেখা বাইটের** সংখ্যা হয়। প্রতিটি non-ASCII বাইট escaped, কারণ Go UTF-8 continuation বাইটকে ছেড়ে দেয় এবং LLVM তা নেয় — কিন্তু module তখন একটি editor-এ খোললে অপাঠ।

এটি FFI-এর বাগ নয়। এটি **যে কোনো** control character থাকা program-এর বাগ ছিল, এবং L5.4 শুধু প্রথম জায়গা যেখানে টেস্ট সেটি ছুঁয়েছে।

### ADR-0075: crossing struct-টা runtime-এর, caller-এর `alloca`-তে নয়

L5.4 crossing-এর জন্য caller একটা `alloca` লিখেছিল:

```llvm
%retslot = alloca %nilffi.str
call void @greet(ptr %ptr, i64 %len, ptr %retslot)
```

এটি ঠিক ছিল, যতক্ষণ না কোনো প্রোগ্রাম **লুপের ভিতরে** string-returning `extern` ডাকে।

`alloca` যে block-এ লেখা হয় সেই block-এই থাকে। লুপের body-তে লেখা `alloca` প্রতি iteration-এ একবার stack বাড়ায়, এবং কোনো কিছু তাকে ফেরত দেয় না। এক লক্ষ iteration পরে stack শেষ।

**এখানে সেটা ধরা পড়েছিল** — এবং একটি বিশেষভাবে ভালোভাবে। Windows-এ clang MSVC triple দিয়ে `__chkstk` নামে stack probe লিখে, আর mingw linker-এর সেই symbol নেই:

```
undefined reference to `__chkstk'
```

এটি **সৌভাগ্যবশত** ধরা পড়া। অন্য কোথাও এটি একটি stack overflow, ঠিক সেই input-এ যেটি stack-টা ফুরিয়ে আনে। লুপ ছোট হলে কোনো পরীক্ষা ধরতে পারে না, আর সেটাই একমাত্র জিনিস যা এটি চালু করে।

দুটো সমাধান ছিল:

| উপায় | ফলাফল |
|---|---|
| `alloca`-টা entry block-এ তুলে দেওয়া | বৃদ্ধি ঠিক, কিন্তু struct-এর lifetime আর frame-এর হয়ে যায় — scope-এর নয় |
| **struct-টাই runtime-এর scope-এ** | একটি scope, একটি lifetime, ভুল করার জন্য একটি জিনিস |

দ্বিতীয়টি নেওয়া হয়েছে। `nil_ffi_scope_open()` এখন `NilFFIString *` ফেরত দেয়, এবং generated code আর কোনো `alloca` লেখে না:

```llvm
%scope = call ptr @nil_ffi_scope_open()
call void @nil_string_unbox(i64 %arg, ptr %scope)   ; argument
call void @greet(ptr %ptr, i64 %len, ptr %scope)    ; the same struct, for the answer
%s = load %nilffi.str, ptr %scope
call void @nil_ffi_scope_close()
```

**একটি struct পুরো call-এর জন্য।** Argument আগে unbox হয়ে SSA value-এ বেরিয়ে আসে, তাই callee উত্তরের জন্য struct-টা পূরণ করার সময় আর কিছুই তার ভিতরে নেই। এটাই একটি struct-কে "call-এর জন্য একটি"-এর মতো বানায়।

### ADR-0076: buffer scope একটি stack, free list নয়

`nil_ffi_buffer` যা L5.4-এর প্রতিশ্রুতি পূরণ করে: একটি callee নিজের উত্তরটি গড়ে দিতে পারে, ছাড়ার কথা মাথায় না এনেই।

এটি কাজ করে **শুধু** scope-গুলো যদি stack হয়। scope nest করে:

```
Nilang → C (scope খোলা) → callback → একটি সম্পূর্ণ Nilang প্রোগ্রাম → আরেকটি C call (scope খোলা)
```

ভেতরের scope আগে বন্ধ হয়। একটি free list এই দুটো আলাদা করতে পারে না — ভেতরের `close` বাইরের buffer ধরে ফেলবে, এবং বাইরের ফাংশন সব ঠিকঠাক করেও freed memory-এর pointer ফেরত দেবে।

তাই প্রতিটি block আলাদা `malloc`, আর scope-এ একটি **mark**। `close` মানে "আমার খোলার পরে যা বের হয়েছে তা free করো"।

**যে ভুলটা এই পরীক্ষাটা ধরে:** `stringfixture.c`-এর `nilffi_nested` তার buffer আগে বানায়, callback ডাকে, এবং **তারপর** নিজের buffer পড়ে। উত্তরটি গুলিগুলির পরে লেখা হয়, যাতে freed হলে লক্ষণীয় হয়।

### ADR-0077: `nil_free` থাকবে না

L5.6-এর তালিকায় `nil_free` ছিল। **এটি তৈরি হবে না**, এবং কারণটি লিখে রাখা দরকার।

collector প্রতিটি `NilValue`-এর মালিক। এটি পরের sweep-এ free করে। হাতে `nil_free` থাকলে দুটো ঘটতে পারে, এবং দুটোই খারাপ:

- ভুলভাবে ডাকা হলে: allocation chain-এ একটি pointer রয়ে যায়, যা **পরের** sweep follow করে — একটি use-after-free যা অনেক পরে ঘটে এবং কিছুর নাম বলে না।
- ঠিকভাবে ডাকা হলে: collector-এর "কী reachable" বোঝার **দ্বিতীয় বাস্তবায়ন**, যা প্রথম সংঘর্ষেই সরে যাবে।

`nil_callback_release` ইতিমধ্যে এই পথে যায়: unpin করে, free করে না। L5.6 একইটাই প্রসার করে।

ফলে C-এর যে একমাত্র জিনিসটি free করার অধিকার আছে তা হলো **নিজে যা বানিয়েছে** — আর `nil_ffi_buffer` ছাড়া বানানো কিছুই runtime-এর নয়, তাই কোনো কিছুই free করতে হয় না।

### ADR-0078: header parser যা চুপচাপ কিছু বাদ দেয়, তার চেয়ে ভালো কিছু নেই

ADR-0073 একটি ফাঁক বন্ধ করেছিল: FFI-এর ঘোষণা যাচাই হতোই না। সেটি বন্ধ করতে গিয়ে দেখা গেল খাঁটি parser-ও ফাঁক ছিল।

`nil.h` পড়ার regex দুইভাবে ভুল ছিল, দুটোই চুপচাপ:

1. **pointer return মিলতো না।** `[A-Za-z0-9_ ]*\*?` — চর class-টি space খেয়ে ফেলে, তারপর star, তারপর `\s+` আর জায়গা পায় না। `void f(void)` মিলত, `NilFFIString *f(void)` মিলত না।
2. **function-pointer parameter মিলত না।** `[^)]*` function-pointer declarator-এর `)`-তে থেমে যেত।

কেউ টের পায়নি, কারণ runtime-এ **কোনো** pointer-returning ঘোষণা ছিল না, আর nested parenthesis-এর parameter-ও না। `nil_closure_new(NilValue (*function)(...))` লেখার দিন থেকে প্রতিটি ABI পরীক্ষা থেকে অদৃশ্য ছিল।

এটি একটি বিচ্যুতি নয়, **একটি শ্রেণি**: যে parser কোনো construct বাদ দেয় সে নীরব, আর নীরবতা "এমন কিছু নেই" থেকে আলাদা করা যায় না।

তাই এখন প্রতিটি header পড়ার সময় একটি যাচাই আছে: **যে প্রতিটি লাইন declaration-এর মতো *দেখায়*, তার নাম পাঠকের map-এ থাকতে হবে।** সংখ্যা গুনে নয়, নাম দিয়ে — কারণ গোনা এমন একটি সাক্ষাত্যঘটনা যা একদিন দাঁড়াবে।

### ADR-0079: crossing table `compiler/ffi`-তে, কোনো back end-এর ভিতরে নয়

L5.2 হেডার জেনারেশন শুরু করার আগে একটি প্রশ্ন: **এটি কোন table থেকে লিখবে?**

Table-টা `compiler/llvm/ffi.go`-তে ছিল। দুটো পথ ছিল:

| পথ | ফলাফল |
|---|---|
| `cheader` package `compiler/llvm` import করবে | একটি header generator, LLVM-এর উপর নির্ভরশীল — এবং সেই নির্ভরশীলতা প্রতিটি build-এ LLVM আনতে হবে |
| table-টা copy করা হবে | **দ্বিতীয় বাস্তবায়ন** "boundary-তে string কী" |

দ্বিতীয়টি এড়ানো যায় না। ADR-0073 ও `splatIn`-এর ঘটনা দেখিয়েছে: declaration আর call যেখানে আলাদা জায়গা থেকে লেখা হয়, সেখানে তারা একদিন অসম্মত হয় — আর অসম্মত হয় এমনভাবে যে **link হয় এবং ভুল উত্তর দেয়**।

তাই table-টা `compiler/ffi`-তে উঠেছে। `Crossing`-এ এখন দুটো spelling:

```go
type Crossing struct {
    LLVM  string  // declaration-এ যা লেখা হয়
    C     string  // prototype-এ যা লেখা হয়
    Unbox string
    Box   string
    Splat bool
    Params int    // একটি Nilang argument কতগুলো C argument হয়
}
```

`Params`-টা নতুন এবং দরকারি: emitter call-এর argument list লেখে, header generator prototype-এর — দুজনই **একই field** পড়ে, তাই তারা অসম্মত হতে পারে না। এটি ঠিক সেই সিদ্ধান্ত যা ADR-0073 চাইছিল, কিন্তু এবার convention-নয় — **structure**।

একটি সতর্কতা: `compiler/ffi` এখন `compiler/mir` import করে, কারণ `SignatureFor` একটি `*mir.Function` পড়ে। এটি গ্রহণযোগ্য — crossing-এর ইনপুট MIR-এর ঘোষণা, কারণ lowering-ও ওই থেকেই পড়ে।

### ADR-0080: যে নাম C ঘোষণা করতে পারে না, তা প্রত্যাখ্যান করা হয়

প্রথম generated header-টি C কম্পাইলারকে দুটি ভুল দিয়েছিল:

```
build/greeting.h:28:15: error: variable or field 'NilFFICallback' declared void
build/greeting.h:28:15: error: 'register' redeclared as different kind of symbol
```

দুটো বাগ, একটি ঘটনা থেকে:

1. **Parameter-এর নাম ছিল না।** C-তে `void register(NilFFICallback);` মানে `NilFFICallback` নামে একটি variable ঘোষণা — type নয়। এটি একটি parameter নয়, একটি **syntax error**।
2. **`register` একটি C keyword।** `extern "C" fn register(handler: fn(Int) -> Int) -> Void;` একটি বৈধ Nilang প্রোগ্রাম এবং একটি অবৈধ C function।

দুটোতেই ভুল ছিল একই জায়গায়: **C পড়ে না।**

প্রথমটির সমাধান সহজ — প্রতিটি parameter-এর নাম লেখা, Nilang-এর নাম থেকে। কিন্তু একটি string দুটো C parameter হয়, আর ঘোষণায় একটি নাম আছে। প্রথমে দুটোতেই একই নাম গেছিল, যা C প্রত্যাখ্যান করে `redefinition of parameter` — **যে বার্তাটি string-ও বলে না, দুই-argument হওয়ার কারণও বলে না**। তাই দ্বিতীয়টির নাম derived (`name` → `name_len`), আর collision হলে `argN`-এ পড়ে।

দ্বিতীয়টির সমাধান **প্রত্যাখারণ**। কারণ নামটা আমাদের নয়:

> একটি foreign function কোনো C লাইব্রেরির প্রতিষ্ঠিত symbol। প্রোগ্রাম সেটাকে **যে নামে ঘোষণা করেছে সেটাই** contract। নাম বদলে দিলে module এমন একটি symbol ডাকবে যা নেই — যা কোথাও undefined reference, আর কোথাও ভুল কিছুর সাথে নিঃশব্দে মিলে যাবে।

তাই `ffi.ValidateName` C89-এর keyword গুলো দেখে এবং **ঘোষণার জায়গাতেই** থামে। প্রত্যাখ্যানটি তিনটি জিনিস বলে: কোন function, কী কারণে, এবং **কেন নাম বদলানো যাবে না** — কারণ সবচেয়ে স্বাভাবিক পরামর্শ ("অন্য নাম ব্যবহার করুন") link ভেঙে দেয়।

### ADR-0081: header-এর নিয়মগুলো prototype-এর পাশে লেখা

একটি generated header শুধু prototype দিলে অসম্পূর্ণ। কারণ FFI-এর **প্রতিটি নিয়ম run time-এ enforce হয় এবং ভাঙলে কোনো diagnostic আসে না**:

- string NUL-terminated নয় — `strlen` ভুল উত্তর দেয়
- length **byte**-এ, character-এ নয়
- উত্তরের buffer runtime-এর, তাই `free` করবেন না
- `malloc` দিয়ে বানানো উত্তর leak করবে — কেউ free করবে না

এগুলো header-এ prototype-এর **ঠিক পাশে** লেখা। পাঠককে `nilffi.h`-এ গিয়ে নিজে জানতে হবে না, এবং ভুল করলে সে **জানবেই না** — তাই এটা decoration নয়, contract।

### ADR-0082: সংস্করণ symbol-এর **নামে**, মানে নয়

L5-এর প্রতিটি টেস্ট জিজ্ঞেস করে *"এটা কি কাজ করে?"*। L5.9 জিজ্ঞেস করে *"কাল এটা কি কাজ করবে?"* — এবং বেশিরভাগ ক্ষেত্রে উত্তর ছিল না।

কারণ: একটি compiled object **যে সংখ্যাগুলো নিয়ে তৈরি হয়েছিল সেগুলোই ধরে রাখে**। সেগুলো ভুল হলে program ভুল উত্তর দেয় — কোনো diagnostic ছাড়াই।

প্রথম ধারণা ছিল একটি run-time check:

```c
int64_t nil_ffi_version(void);
```

**এটি কাজ করে না।** একটি run-time check মানে mismatch রিপোর্ট হবে **তখনই**, যখন program ইতিমধ্যে চলছে। আর সংস্করণের mismatch-এর সবচেয়ে ভয়ংকর লক্ষণ ঠিক এটাই — program চলে, উত্তর দেয়, কেউ বুঝতে পারে না।

তাই যা হলো:

```c
void nil_ffi_abi_v1(void);   /* শরীর খালি, এবং সবসময় খালি থাকবে */
```

**সংস্করণ symbol-এর নামে**, যাতে **linker** যাচাই করে। `nil_ffi_abi_v1` আর `nil_ffi_abi_v2` আলাদা symbol — v1 object, v2-only runtime-এ **link হবে না**, আর বার্তাটা symbol-এর নাম ধরে।

দুটোই define করলে এটা পুরো ব্যবস্থাটি নষ্ট হতো — linker-এর কাজ হওয়ার কোনো জিনিসই থাকত না।

Generated code এই guard-কে ডাকে **প্রতিটি module-এ যেখানে `extern` আছে**, এবং যেখানে নেই তার কোথানো নয়:

> সব module-এ guard থাকলে সেটা এমন guard হবে যা কিছুই guard করে না। `extern`-যুক্ত module-এর সাথে কোনো runtime-এর সংস্করণ মেলানোর প্রশ্নই নেই, আর যে module কখনোই ডাকে না এমন symbol-এর জন্য link করলে সেটা যে কোনো কিছু দিয়ে satisfy হয়ে যেতে পারে — এমনকি এই runtime নয়।

দুটো কাজ বাকি রয়েছে, দুটোই ইচ্ছাকৃত: `nil_ffi_version()` run-time-এ জিজ্ঞেস করার জন্য (যেখানে guard ব্যর্থ হয়নি), এবং guard-এর **খালি শরীর** — কারণ খালি থাকলে দুই পক্ষের মধ্যে অসম্মত হওয়ার কোনো জায়গাই থাকে না।

**সংস্করণ একটি সংখ্যা, তারিখ নয়।** তারিখ প্রতিটি সংযোজনে বদলায়, আর তখন প্রতিটি সংযোজন boundary-তে কিছু না বদলেও প্রতিটি compiled object ভাঙবে।

### ADR-0083: `sizeof` একটি দাবি ছিল, এখন একটি পরীক্ষা

ADR-0072 দেখিয়েছিল দুই compiler **struct return-এর শ্রেণিবিন্যাসে** অসম্মত। তারপর এই FFI-এর **প্রতিটি** size সন্দেহজনক হয়ে গেল, আর `sizeof`-এর উত্তর কেবল একটি বিশ্বাসের মতো ছিল।

তাই এখন দুটোকে **জিজ্ঞেস করা হয়**, একই link-এ, একই header থেকে:

```
runtime: 8 8 24 8 32 8 56 8 8 8 16 8
clang:   8 8 24 8 32 8 56 8 8 8 16 8
```

দুটো probe **আলাদা compiler-এ** compile হয়, তারপর **একই program-এ** link হয়। এটাই ইচ্ছাকৃত — দুটো text file মিলিয়ে দুটো compiler-এর *মতামত* মিলিয়ে দেওয়া; কিন্তু দুটোকে একই link-এর মধ্য দিয়ে ডাকা মানে **একটি সত্যিকারের program যা দেখতে** পেত।

`sizeof`-এর বদলে `nil_ffi_sizeof` জিজ্ঞেস করা হচ্ছে, কারণ runtime-এর নিজের উত্তরই হলো যা একটি program পায় — এবং এটা runtime-কে নিজেকে যাচাই করতে বলছে, যা **সংজ্ঞা অনুযায়ীই** নিজের সাথে একমত হবে।

পাঠক যা চায় তা হলো **দুটো আলাদা compiler একই header পড়ে কী বলে**।

তুলনাটা **text হিসেবে**, parse না করে — কারণ গুরুত্বপূর্ণ হলো দুটো **একই সংখ্যা** দিয়েছে, আর পার্থক্য হলো ভিন্ন লাইন, সংখ্যা যাই হোক। এখানে একটি parser শুধু একই তথ্যের **খারাপ বার্তা** দিত।

এবং সংখ্যাগুলো একটি **লেখা প্রত্যাশার** সাথে মিলিয়ে দেখা হয়, কারণ নীরবে বদলে যাওয়া একটি পরীক্ষিত constant নীরবে না থাকার চেয়ে খারাপ।

### ADR-0084: boundary-এর পৃষ্ঠতল **ফ্রিজ** করা, এবং যা বদলালে তা লেখা উচিত

L5.9-এর গেট লেখা ছিল "`docs/spec`-এ FFI কন্ট্র্যাক্ট"। এর একটি অংশ লেখা হয়েছে (`§9.7`)।

বাকি অংশ হলো: **পৃষ্ঠতল পরিবর্তন যেন ইচ্ছাকৃত হয়।**

একটি frozen list — ২৪টি নাম, লেখা — দুই দিক থেকে যাচাই করে:

- contract-এ থাকা কিন্তু header-এ নেই: runtime প্রতিশ্রুতি রাখছে না
- header-এ থাকা কিন্তু contract-এ নেই: **কেউ কোনো প্রতিশ্রুতি দেয়নি**

দ্বিতীয়টিই বিপজ্জনক, এবং কারণটা সোজা: **যোগ করা এমন একটি পরিবর্তন যা link ব্যর্থ করতেই পারে না।** কারণ নতুন কোনো symbol কখনো resolve হয় না, তাই যে ভুলটা সবচেয়ে নিঃশব্দ সেটা ঠিক এটাই।

তাই ব্যর্থতার বার্তা দেখিয়ে দেয় **কী করতে হবে**:

```
nilffi.h exports nil_ffi_something_new, which the FFI's contract does not mention.
Adding a function is a change to the boundary: every program compiled against the
old header was built against a contract this is no longer describing.

If that is intended, add it to ffiSurfaceIsFrozen and raise NIL_FFI_ABI_VERSION
in nilffi.h.
```

**যিনি boundary বদলাচ্ছেন তিনিই সেই সিদ্ধান্ত নিচ্ছেন** যে পুরোনো header-এর বিপরীতে তৈরি program ভাঙবে। তাই তাকে সেটা **লিখতে** হবে।

আর একটি টেস্ট বলে যে তালিকাটি খালি হতে পারে না — কারণ খালি তালিকা নিয়ে "contract মান্য" বলা কিছু নয় বলার চেয়ে খারাপ।

### ADR-0085: struct যায় **pointer** দিয়ে, buffer-টা runtime-এর

প্ল্যানে লেখা ছিল "struct by value"। ADR-0072 সেটি নিষিদ্ধ করেছে, তাই প্রশ্নটা হয়: **struct কীভাবে যায়?**

উত্তর: **runtime-এর মালিকানাধীন একটি buffer-এর pointer দিয়ে**, যার প্রতিটি field `nil_get_field` দিয়ে পড়ে উপরোক্ত offset-এ `store` হয়।

**কেন buffer-টা runtime-এর** — কারণ call site-এ `alloca` লিখলে সেটা যে block-এ পড়ে সেই block-এই জায়গা হয়। লুপের body-র ভিতরে call করলে প্রতি iteration-এ stack বাড়ত, আর বাড়তে থাকত স্ট্যাক ওভারফ্লো। ADR-0075-এ একই শিক্ষা string-এর জন্য পাওয়া গিয়েছিল — এখানে সেই একই scope পুনঃব্যবহার করা হচ্ছে: **একটি call মানে একটি scope**, এক জায়গায় মুক্তি।

**কেন byte offset লেখা, আর ঘোষিত LLVM struct type নয়** — কারণ offset-গুলো আমরা যা হিসাব করেছি এবং C যা হিসাব করে; সেগুলো **লিখে** রাখলে সেটা পড়ায়। `%nil.struct.Point = type { i64, i64 }` ঘোষণা করতে হলে padding-এর নিয়ম LLVM-এর টাইপ ব্যাকরণের ভিতরে আবার লিখতে হত, আর type-এর ঘোষিত layout আর তার ভিতরের store-গুলো অসম্মত হলে সেই অসম্মতি কেউ দেখত পেত না।

`getelementptr inbounds i8, ptr %buf, i64 <offset>`-এর জন্য কোনো type লাগে না, আর যে offset ব্যবহার করা হয়েছে ঠিক সেটাই লেখা থাকে।

**এক জায়গায় scope** — struct-এর buffer আর তার string field যেখানে unbox করে, দুটো একই scope থেকে যায়। দুটো আলাদা scope মানে দুটো lifetime, আর একটা মুক্তির সুযোগ।

টেস্ট: `TestAStructIsFreedWhenTheCallReturns` — ৫০০০ iteration, outstanding গণনা করে।

### ADR-0086: struct ফেরত আসতে পারে না, এবং কারণটা **নাম** বলে দেয়

struct return দেওয়া হয়নি pointer দিয়ে — refusal।

কারণটা ownership-র প্রশ্ন: struct **return** করতে হলে runtime-কে C-এর বাইট থেকে Nilang struct বানাতে হতো, আর এখন কিছুই সেটা করে না। Pointer দিয়ে উত্তর দিলে program পেত **এমন একটি tagged word** যা এমন memory-তে দেখায় যা program-এর নিজের নয় — আর এই প্যাকেজটি যে ব্যর্থতা রোধ করার জন্য আছে, সেটাই তা।

Refusal-টা **ঘোষণার সময়**, নাম ধরে, বলে দেয় যে কোন দিকটি নেই:

```
extern "origin" returns Point, and a struct cannot cross back yet.
A struct goes *into* C as a pointer to a buffer the caller fills, and that is
one direction only.
```

দুইটি বাক্যই আসল — প্রথমটি বলে কী নেই, দ্বিতীয়টি বলে কী আছে। শুধু "struct cross করে না" বললে পাঠক ভাবত সব struct-ই বাদ, যেটা অসত্য।

টেস্ট: `TestAStructCannotComeBackYet` — শুধু refusal হওয়া যাচাই করে না, **দুইটি বাক্যই** আছে যাচাই করে।

### ADR-0087: header-এর C নাম crossing-এ **থাকে না**

প্রথম সংস্করণে typedef ছিল `Point_t`, prototype ছিল `int64_t distance(const Point *p)` — আর C বলেছিল:

```
error: unknown type name 'Point'; did you mean 'Point_t'?
```

এটি C compiler-এর দেওয়া **সবচেয়ে ভালো** বার্তা, আর সম্পূর্ণ এড়ানো যায়।

কারণ ছিল দুই জায়গায় `_t` বসানো: `writeStructTypes`-এ `+"_t"` আর `cHeaderType`-এ নয়। তিনটি `+ "_t"` রাখলে ভুলটা অনিবার্য।

এখন **`cTypeName` একাই পুরো নাম ফেরত দেয়** (`Point_t`), আর `_t` কোথাও আলাদা লেখা নেই। একটি ফাংশন যা পুরো নাম ফেরত দেয় ভুল ব্যবহার করা যায় না।

আর `Crossing.C` ইচ্ছাকৃতভাবে **`const Point *`** — ধারণাগত রূপ। `_t` একটি **header-এর সিদ্ধান্ত**, তাই সেটা এখানেই প্রয়োগ হয়; crossing-এ গেলে emitter-এর কাছে এমন একটি নাম থাকত যা সে কখনো ছাপে না।

টেস্ট: `TestTheGeneratedHeaderDeclaresTheStructItNeeds`, `TestAStringFieldIsTwoMembers` — দুটোই C ফাইল **লিখে** compile করে।

### ADR-0088: struct-এর field **নামে** পড়া হয়, অর্থে নয়

একটি Nilang struct-এর মান run time-এ একটি **hash** — layout তার ভিতরে নেই। তাই field পড়তে হয় runtime-এর নিজের accessor দিয়ে (`nil_get_field`), হিসাব দিয়ে নয়।

এর ফলে **`mir.Program`-এ struct ঘোষণাটি বেঁচে থাকতে হয়** — ঠিক কোন field, কোন ক্রমে। আগে ঘোষণা lowering-এর সময় ফেলে দেওয়া হতো, কারণ struct-এর মান একটা hash আর তাই তার আকার পুনরায় আসে না।

এখন `mir.Program.Types` সেগুলো নিয়ে যায়, আর **ঘোষণার ক্রমই layout-এর ক্রম**। এটা তথ্য সাজানোর বিষয় নয় — এটি ভুল হলে C ভুল offset-এ পড়ে।

এখানে একটি ছোট কিন্তু কঠিন সত্য: LLVM-এর parser-কে একটি **declared** function-এর argument-এর type লিখতে হয় (`call i64 @nil_get_field(i64 %t1, i64 %key18)`)। type ছাড়া `( %t1, ...)` লেখা যায় না — আর clang-এর বার্তা হয় "invalid type for function argument", যা **মানকেই** দোষী করে এবং call বা declaration-এর নামও বলে না। বাকি প্রতিটি conversion আগে থেকেই type লিখত, এই একটিই লিখত না।

### ADR-0089: একটি মিথ্যা skip সরানো একটি সত্যিকারের অমতিপূর্ণতা বের করে দিল

L5.7 শেষ করতে গিয়ে দেখা গেল conformance suite-এ `struct` নামে একটি **skip** আছে, যার কারণ লেখা: *"the emitter has no lowering for a struct literal or field"*।

কারণটি **মিথ্যা ছিল** — emitter struct literal ও field দুটোই নামায়, এবং `Point{x:3,y:4}.x` সত্যিই LLVM-এ `nil_get_field` হয়ে যায়।

তাই entry টি সরানো হলো। আর সাথে সাথে একটি **তিন ইঞ্জিনের অমতিপূর্ণতা** বেরিয়ে এলো:

```
struct P { b: Int, a: Int } P { b: 1, a: 2 };
interpreters: "{b: 1, a: 2}"
compiled:     "{a: 2, b: 1}"
```

**কারণ:** struct run time-এ একটি **hash map**, আর runtime map-কে তার নিজের hash order-এ ছাপত — যেটা তখনকার কোডে "সৎ" বলে লেখা ছিল (*"a map's print order should not be part of its identity"*।) কিন্তু `SEMANTICS.md` §১ বলে struct-ের field **ঘোষণার ক্রমে** ছাপতে হয়, আর hash literal-ও লেখা ক্রমে।

তাই runtime-এ `NilMap`-এ একটি `size_t *order` যোগ হলো — কোন key **প্রথমবার** কখন লেখা হয়েছে তার slot index। `map_grow`-এ প্রতিটি index নষ্ট হয়ে যায় (rehash সব key সরায়), তাই order **key দিয়ে** বহন করা হয়, পুরোনো slot দিয়ে নয়।

একই সাথে দুই Go engine-এ একই বাগ ছিল: `evalIndexAssign` ও VM-এর index-assign **`hash.Pairs[...]` সরাসরি** লিখত, `SetPair`-এর পাশ দিয়ে। `object.go` নিজেই লেখে *"Every mutation goes through here so that the two views cannot diverge"* — তিনটি জায়গা সেই নিয়ম ভাঙছিল।

**কেন এটি ADR:** এটি পরিকল্পনার **চতুর্থ** ফাজল, এবং আগের তিনটির গোলাপদ্ধ: ADR-0072, ADR-0073, ADR-0078। সবগুলো একই আকার — **যা যাচাই হচ্ছিল না, তা যাচাই হচ্ছিল না**।

আরও গভীর কারণটা এই: **একটি skip-এর কারণ কখনো মরে না, কারণটা শুধু বদলায় না।** যে entry লেখা হয়েছিল সেদিন সেটা সত্যি ছিল; পরে কেজ code লিখে ভুলে গেছে entry টি সরানোর। তাই টেস্ট এখন দুই কাজ করে: skip **ঘটলে** কারণ লেখা থাকে, আর কারণ **লেখা থাকলে** সেটি যাচাই হয়।

ফল: **১০৫ → ১১৩** conformance case তিন ইঞ্জিনে চলছে, শূন্য অমতিপূর্ণতা।

### ADR-0090: runtime-এর header-এর ঠিকানা `nilcore`-এর, `cmd`-এর নয়

L5.7 শেষে আসল CLI দিয়ে একটি প্রজেক্ট চালিয়ে দেখা গেল — আর FFI **কাজ করেইন**।

`nil header` লেখে `build/<নাম>.h`। `nil build --aot` কম্পাইল করে প্রজেক্টের C ফাইলগুলো। একটি সাধারণ ধাপ:

```
l57demo.h: No such file or directory
```

`-I build` পাস করা ছিল না। যোগ করার পর আরেকটি:

```
nilffi.h: No such file or directory
```

কারণ generated header নিজেই `#include "nilffi.h"` লেখে — আর সেটা `runtime/ffi/include/`-এ। **তাই এমন কোনো header নেই যা খোলা যায়।**

দুটো একই বাগ, দুই পোশাকে: **একটি include path পাস হয়নি**।

**সিদ্ধান্ত:** include path তৈরি হয় একটি ছোট ফাংশনে — `projectCIncludes(outputDir)` — এবং runtime-এর দুটো ঠিকানা **`nilcore.IncludeDir()` ও `nilcore.FFIDir()`** থেকে আসে, `cmd/nil` কোথাও লিখে না।

কারণ ঠিকানা জানার একমাত্র মালিক `nilcore` — runtime নিজেই compile করে সেখান থেকে। `cmd/nil`-এ আলাদা করে লিখলে দুটো জায়গা হতো, আর দ্বিতীয়টা আজ ভুল হলে **runtime ঠিকভাবেই বিল্ড হতো** আর প্রজেক্টের প্রতিটি C ফাইল ভাঙত — ঠিক এখন যা হয়েছিল।

প্রজেক্টের নিজের `c_flags` এর **পরে** লেগে যায়, তাই প্রজেক্ট নিজের header দিলে সেটিই পায়।

টেস্ট: generated header বানিয়ে তার প্রতিটি `#include "..."` খুঁজে বের করে, `-I` তালিকার বিপরীতে resolve করা হয় — শুধু পথ "ঠিক দেখাচ্ছে" না, **সত্যিই খোলা যায় কি না**।

**তিন ইঞ্জিন গেট ১০৫ → ১১৩**: `struct` skip-টি সরানোর ফলে (ADR-0089) — ৪টি struct case + ৩টি নতুন map-order case + ১টি hash-literal case।

**L5.4 থেকে**: ৮টি string-crossing টেস্ট প্রোগ্রাম **চালিয়ে** যাচাই করে। একটিও emitted IR দেখে বিচার করে না — কারণ struct-return-এর বাগটি IR-এ সম্পূর্ণ সঠিক ছিল।

**L5.6 থেকে**: ৭টি ownership টেস্ট, প্রতিটি ৫০০০ iteration-এর লুপে। ফাঁকটি দেখা যায় কারণ গণনা করা হয় — একটি লুপে যা leak করে তার outstanding সংখ্যা প্রতি iteration-এ বাড়ে।

**L5.6-এর সবচেয়ে বড় ফলাফল মূলত একটি উপসর্গের সরানো:** `nilffi_greeting` আর `nilffi_upper`-এ আর `static char[256]` নেই। একটি ছোট স্ট্রিং বানানোর ফাংশনের জন্য ২৫৬ বাইটের সীমা ছিল, আর কেউ লক্ষ্য করত না কারণ ছোট ইনপুটে ক্লিপ দেখা যায় না।

**L5.2 থেকে**: ৩টি header টেস্ট একটি C ফাইল **লিখে** — যা শুধু generated header include করে — তারপর সেটিকে `-Wall -Wextra -Werror` দিয়ে compile করে, Nilang প্রোগ্রামের সাথে link করে এবং **চালায়**। header-এর text পড়ে কিছু বোঝা যায় না: prototype সঠিক দেখাতে পারে আর ভুল হতে পারে, যেমন string-কে একটি pointer বানানো — সেটা compile হয়, link হয়, আর pointer থেকে length পড়ে।

**L5.9 থেকে**: ৭টি স্থায়িত্ব টেস্ট, যার মধ্যে একটি **দুটো আলাদা compiler একই link-এ** runtime-এর layout জিজ্ঞেস করে। এবং পৃষ্ঠতল frozen — header-এ একটি function যোগ করলেই টেস্ট ব্যর্থ হয় এবং **কী করতে হবে** বলে দেয়।

**L5-এর সবচেয়ে বড় শিক্ষা, চারটি ফাজল থেকে:** ADR-0072 (দুই compiler struct return-এ অসম্মত), ADR-0073 (FFI-র ঘোষণা যাচাই হতোই না), ADR-0078 (header parser চুপচাপ কিছু বাদ দেয়), আর ADR-0089 (একটি skip-এর কারণ মরে না, শুধু বদলায় না)। **চারটিই একই আকারের ব্যর্থতা — যত কিছু ধরা পড়ছিল না, তা ধরা পড়ছিল না।** প্রতিটির জন্যই এখন একটি পরীক্ষা আছে যা **না পড়া** সম্ভব না করে দেয়।

আর একটি ব্যাপার যা চারটির চেয়েও সাধারণ: **প্রতিটি ফাজলই কোথাও একটি তালিকায় লেখা ছিল না** — ফাজলটা হলো সেই তালিকাগুলো নিজেই কখনো যাচাই হতো না। তাই শেষ পর্যন্ত যা বাকি রইলো তা হলো সেই তালিকাগুলোকে নিজেদের বিপরীতে যাচাই করা, নতুন কোনো ফাজল খোঁজা নয়।

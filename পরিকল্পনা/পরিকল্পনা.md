## ১. নীলাং-এর বর্তমান অবস্থা ও স্বপ্নের মানচিত্র

### ১.১ নীলাং এখন কোথায় আছে?

নীলাং হলো একটি আধুনিক, কনকারেন্ট এবং ডিক্লারেটিভ প্রোগ্রামিং ভাষা যা Alap Framework এবং Onuron OS-এর ইকোসিস্টেমের জন্য তৈরি করা হচ্ছে। এটি গো-এর সরলতা, রাস্টের পারফরম্যান্স ও নিরাপত্তা এবং ArkTS-এর মতো ডিক্লারেটিভ UI একত্রিত করার লক্ষ্যে তৈরি।

বর্তমান অবস্থায় নীলাং-এ যা আছে:

**৬০ FPS অ্যানিমেশন ইঞ্জিন** — ৩০টিরও বেশি বিল্ট-ইন ইজিং কার্ভ (Bounce, Elastic, Cubic, Back, Quad ইত্যাদি) এবং টাইমলাইন কি-ফ্রেমিং। **GPU রেন্ডারার ফাউন্ডেশন** — simulation ও backend abstractions; বাস্তব Vulkan/Direct3D/Metal command submission এখনো চলমান কাজ।

Alap Framework-এ ইতিমধ্যে `abi/` (Stable C ABI boundary ও Cgo bridge), `cmd/nil/` (CLI), `cmd/nilc/` (bytecode compiler CLI), `cmd/nills/` (LSP daemon) সহ একটি কঙ্কাল রয়েছে। Alap হলো NilLang-চালিত একটি next-generation অ্যাপ্লিকেশন ফ্রেমওয়ার্ক।

Go-এর মতো concurrency (tasks, actors, channels) এবং **Multi-Platform Native Adapters** — Onuron (Onuron OS), Android (JNI/NDK), iOS (Metal/Swift), এবং Linux (Wayland/X11/Flatpak) সাপোর্টের পরিকল্পনা রয়েছে।

| **রানটাইম** | GC/ARC, মেমোরি মডেল, FFI | সর্বোচ্চ |

## ২. মোবাইল অ্যাপ তৈরির প্রযুক্তিগত ভিত্তি বোঝা

### ২.১ তিনটি প্ল্যাটফর্মের কম্পাইলেশন মডেল

নীলাং-কে এগিয়ে নিয়ে যেতে হলে প্রথমেই বুঝতে হবে প্রতিটি প্ল্যাটফর্ম কীভাবে কাজ করে।

**অ্যান্ড্রয়েডের ক্ষেত্রে:**
Android-এ Java বা Kotlin দিয়ে লেখা `.java` বা `.kt` ফাইল JAVAC/Kotlin compiler দিয়ে Java byte code (`.class`) তৈরি হয়। এরপর সেই `.class` ফাইল Dex compiler দ্বারা Dex byte code (`.dex`) এ রূপান্তরিত হয়ে `.apk` তৈরি হয়।

**iOS-এর ক্ষেত্রে:**
SwiftC কোডকে AST (Abstract Syntax Tree) → semantic analysis → Swift Intermediate Language (SIL) তে রূপান্তর করে। এরপর LLVM IR তৈরি হয়। সবশেষে LLVM সেটাকে assembly code এবং `.ipa` এক্সিকিউটেবলে পরিণত করে।

**LLVM-এর কেন্দ্রীয় ভূমিকা:**
LLVM হলো Swift (iOS-এর প্রধান ভাষা), Rust, Julia, Halide এবং Mojo সহ বহু জনপ্রিয় প্রোগ্রামিং ভাষার ভিত্তি।

Android ডেভেলপমেন্টও Android Native Development Kit (NDK) এর মাধ্যমে LLVM-এর উপর নির্ভর করে।

**ক্রস-প্ল্যাটফর্মের উদাহরণ (Flutter):**
Flutter Dart ভাষা ব্যবহার করে এবং Ahead-of-Time (AOT) compilation দিয়ে Dart কোডকে Android ও iOS উভয়ের জন্য native machine code-এ রূপান্তর করে। কম্পাইল করা কোড প্ল্যাটফর্ম-নির্দিষ্ট executable-এ প্যাকেজ হয়। এই AOT compilation দ্রুত স্টার্টআপ ও উচ্চ পারফরম্যান্স নিশ্চিত করে।

### ২.২ নীলাং-এর কম্পাইলেশন লক্ষ্য

নীলাং-কে নিচের টার্গেট ট্রিপলেটগুলো সাপোর্ট করতে হবে:

```
aarch64-linux-android       (Android ARM64)
armv7-linux-androideabi     (Android ARM32)
x86_64-linux-android        (Android x86_64 — এমুলেটর)
aarch64-apple-ios           (iPhone ARM64)
x86_64-apple-ios            (iOS Simulator)
aarch64-unknown-harmonyos   (HarmonyOS ARM64)
```

## ৩. ধাপ ১ — কম্পাইলার সম্পূর্ণ করা

এটি সবচেয়ে গুরুত্বপূর্ণ ধাপ। একটি ভাষা তখনই মোবাইল অ্যাপ বানাতে পারে যখন তার কম্পাইলার **শিল্পমানের** হয়।

### ৩.১ লেক্সার ও পার্সার (Lexer & Parser)

বর্তমান নীলাং-এ `compiler/lexer/` ও `compiler/ast/` আছে। এগুলো আরও শক্তিশালী করতে হবে।

**লেক্সারের কাজ:**
```
নীলাং সোর্স (.nil) → টোকেন স্ট্রিম
```

লেক্সারে অবশ্যই থাকতে হবে:
- **ইউনিকোড সাপোর্ট** — বাংলা আইডেন্টিফায়ার (`ধরন ব্যবহারকারী = "জয়"`) সাপোর্টের জন্য
- **Multi-line string literals** — UI টেমপ্লেটের জন্য
- **Raw strings** — regex প্যাটার্নের জন্য
- **Interpolated strings** — `"নমস্কার ${নাম}!"`
- **Number literals** — `0xFF`, `1_000_000`, `3.14f32`

**পার্সারের কাজ:**

পার্সারকে Recursive Descent অথবা LALR(1) পদ্ধতিতে লিখতে হবে। নীলাং-এর ডিক্লারেটিভ UI সিনট্যাক্স পার্স করার জন্য বিশেষ মনোযোগ দিতে হবে:

```nil
component ব্যবহারকারীকার্ড(নাম: string, বয়স: int) {
    state সক্রিয়: bool = false

    render {
        Column {
            Text(নাম) { style: TextStyle.বড় }
            Button("ক্লিক করো") {
                on click: emit সক্রিয়Toggle()
            }
        }
    }
}
```

এই ধরনের নেস্টেড DSL সিনট্যাক্স পার্স করা অত্যন্ত জটিল। এর জন্য **Pratt Parser** পদ্ধতি সবচেয়ে কার্যকর।

### ৩.২ টাইপ সিস্টেম (Type System)

TypeScript-style static typing এবং স্পষ্ট গ্রামার নীলাং-এর লক্ষ্য। এই লক্ষ্য পূরণ করতে হলে একটি সম্পূর্ণ টাইপ সিস্টেম দরকার।

নীলাং-এর টাইপ সিস্টেমে থাকতে হবে:

**ক) প্রাইমিটিভ টাইপ:**
```nil
int8, int16, int32, int64    -- স্বাক্ষরিত পূর্ণসংখ্যা
uint8, uint16, uint32, uint64 -- অস্বাক্ষরিত পূর্ণসংখ্যা
f32, f64                      -- ফ্লোটিং পয়েন্ট
bool                          -- সত্য/মিথ্যা
rune                          -- ইউনিকোড কোডপয়েন্ট
string                        -- UTF-8 টেক্সট
byte                          -- raw byte
void                          -- কিছু নেই
never                         -- ফেরত আসে না
```

**খ) কম্পোজিট টাইপ:**
```nil
-- অ্যারে (স্থির আকার)
let সংখ্যা: [int32; 5] = [1, 2, 3, 4, 5]

-- ভেক্টর (পরিবর্তনযোগ্য আকার)
let তালিকা: Vec<string> = []

-- ম্যাপ
let অভিধান: Map<string, int32> = {}

-- টাপল
let যুগল: (string, int32) = ("জয়", 25)

-- ঐচ্ছিক (Optional)
let হয়তো: ?string = null
```

**গ) কাস্টম টাইপ:**
```nil
-- স্ট্রাকচার
struct ব্যবহারকারী {
    নাম: string
    বয়স: uint8
    ইমেইল: ?string
}

-- এনাম
enum রং {
    লাল
    সবুজ
    নীল
    কাস্টম(r: uint8, g: uint8, b: uint8)
}

-- ইন্টারফেস
interface আঁকাযোগ্য {
    fn আঁকো(ক্যানভাস: Canvas) -> void
    fn সীমানা() -> Rect
}
```

**ঘ) জেনেরিক্স:**
```nil
fn সর্বোচ্চ<T: তুলনাযোগ্য>(ক: T, খ: T) -> T {
    if ক > খ { return ক }
    return খ
}
```

**ঙ) টাইপ ইনফারেন্স:**
```nil
let x = 42          -- int32 অনুমান করা হলো
let y = "হ্যালো"   -- string অনুমান করা হলো
```

### ৩.৩ সিম্যান্টিক অ্যানালাইসিস

পার্সিং-এর পর সিম্যান্টিক অ্যানালাইসিস করতে হবে:

**স্কোপ রেজোলিউশন:**
```
গ্লোবাল স্কোপ → মডিউল স্কোপ → ফাংশন স্কোপ → ব্লক স্কোপ
```

**টাইপ চেকিং — হিন্ডলি-মিলনার অ্যালগরিদম:**

HM অ্যালগরিদম দিয়ে সম্পূর্ণ টাইপ ইনফারেন্স করা যায়। নীলাং-এর জন্য এটি অবশ্যই থাকতে হবে।

**বরোচেক / মালিকানা বিশ্লেষণ:**

Rust-এর মতো মেমোরি নিরাপত্তার জন্য বরো চেকার যোগ করা যায়, তবে প্রথম পর্যায়ে ARC (Automatic Reference Counting) দিয়ে শুরু করা বাস্তবসম্মত।

### ৩.৪ HIR ও MIR (ইন্টারমিডিয়েট রিপ্রেজেন্টেশন)

```
নীলাং AST → HIR (High-level IR) → MIR (Mid-level IR) → LLVM IR
```

বর্তমানে `compiler/hir/` — High-level IR ও constant folding optimizer এবং `compiler/codegen/` — NABC bytecode generator আছে। এই পাইপলাইনকে LLVM পর্যন্ত বিস্তৃত করতে হবে।

**HIR-এ অপ্টিমাইজেশন:**
- ধ্রুবক ভাঁজ (Constant Folding): `2 + 3` → `5`
- মৃত কোড অপসারণ (Dead Code Elimination)
- ইনলাইনিং (Function Inlining)
- লুপ আনরোলিং (Loop Unrolling)

## ৪. ধাপ ২ — LLVM ব্যাকএন্ড ও নেটিভ কোড জেনারেশন

এটি নীলাং-কে বাস্তব মোবাইল অ্যাপ বানাতে সক্ষম করার **সবচেয়ে গুরুত্বপূর্ণ প্রযুক্তিগত ধাপ**।

### ৪.১ কেন LLVM?

LLVM হলো Swift (iOS-এর প্রধান ভাষা), Rust, Julia, Halide, এবং Mojo সহ বহু গুরুত্বপূর্ণ ভাষার ভিত্তি।

Apple-এর মোবাইল অ্যাপগুলো দীর্ঘদিন ধরে LLVM IR আকারে App Store-এ পাঠানো হতো এবং শেষে ডিভাইসে কম্পাইল হতো। এটি Apple-কে 32-bit ও 64-bit ARM, Apple Watch এবং Apple TV — বিভিন্ন আর্কিটেকচার সাপোর্ট করতে সাহায্য করেছে।

### ৪.২ Go দিয়ে LLVM সংযোগ

নীলাং Go-তে লেখা, তাই `llvm-go` বা `llgo` বাইন্ডিং ব্যবহার করতে হবে:

```go
// compiler/codegen/llvm_backend.go

package codegen

import (
    "github.com/llir/llvm/ir"
    "github.com/llir/llvm/ir/types"
    "github.com/llir/llvm/ir/constant"
)

type LLVMBackend struct {
    module  *ir.Module
    builder *ir.Builder
    ctx     *CompileContext
}

func (b *LLVMBackend) EmitFunction(fn *hir.Function) *ir.Func {
    // নীলাং HIR → LLVM IR রূপান্তর
    params := b.buildParams(fn.Params)
    retType := b.mapType(fn.ReturnType)
    
    irFunc := b.module.NewFunc(fn.Name, retType, params...)
    block := irFunc.NewBlock("entry")
    
    b.emitBlock(block, fn.Body)
    return irFunc
}
```

**বিকল্প পদ্ধতি:** C FFI দিয়ে libLLVM সরাসরি কল করা — এটি সবচেয়ে স্থিতিশীল পদ্ধতি।

### ৪.৪ NABC বাইটকোড থেকে LLVM IR-এ রূপান্তর

বর্তমান নীলাং-এ `NABC` (NilLang Abstract Bytecode) আছে। এই বাইটকোড থেকে LLVM IR তৈরি করার পাইপলাইন তৈরি করতে হবে:

```
.nil সোর্স
    ↓ লেক্সার
টোকেন স্ট্রিম
    ↓ পার্সার
AST (Abstract Syntax Tree)
    ↓ সিম্যান্টিক অ্যানালাইসিস
HIR (High-level IR)
    ↓ অপ্টিমাইজার
MIR (Mid-level IR)
    ↓ LLVM ব্যাকএন্ড
LLVM IR (.ll)
    ↓ LLVM অপ্টিমাইজার (O1/O2/O3/Oz)
অপ্টিমাইজড LLVM IR
    ↓ LLVM কোড জেনারেটর
নেটিভ মেশিন কোড (.o)
    ↓ লিংকার (lld)
শেয়ার্ড লাইব্রেরি (.so/.dylib) বা স্ট্যাটিক (.a)
```

HarmonyOS-এ নেটিভ কোড চালানোর জন্য NAPI ব্যবহার করতে হয়:

```c
// src/platform/harmony/napi_bridge.c

#include "napi/native_api.h"
#include "nilabi.h"

// নীলাং ফাংশন → HarmonyOS NAPI Export
static napi_value NilInit(napi_env env, napi_callback_info info) {
    nil_runtime_init();
    
    napi_value result;
    napi_create_int32(env, 0, &result);
    return result;
}

static napi_value NilCallFunction(
    napi_env env, 
    napi_callback_info info
) {
    size_t argc = 2;
    napi_value args[2];
    napi_get_cb_info(env, info, &argc, args, NULL, NULL);
    
    char fn_name[256];
    size_t fn_len;
    napi_get_value_string_utf8(env, args[0], fn_name, 256, &fn_len);
    
    // নীলাং ফাংশন কল
    void *result = nil_call(fn_name, NULL, 0);
    
    napi_value ret;
    napi_create_int64(env, (int64_t)result, &ret);
    return ret;
}

// NAPI মডিউল রেজিস্ট্রেশন
EXTERN_C_START
static napi_value Init(napi_env env, napi_value exports) {
    napi_property_descriptor desc[] = {
        {"init", NULL, NilInit, NULL, NULL, NULL, napi_default, NULL},
        {"call", NULL, NilCallFunction, NULL, NULL, NULL, napi_default, NULL},
    };
    napi_define_properties(env, exports, 2, desc);
    return exports;
}
EXTERN_C_END

static napi_module nilModule = {
    .nm_version = 1,
    .nm_filename = NULL,
    .nm_register_func = Init,
    .nm_modname = "nil_runtime",
    .nm_priv = NULL,
    .reserved = {0},
};

extern void __attribute__((constructor)) RegisterNilModule(void) {
    napi_module_register(&nilModule);
}
```

নীলাং-এ Go-এর মতো concurrency — tasks, actors, এবং channels পরিকল্পিত আছে।

```nil
import nil.concurrent.*

// async/await
fn ডেটালোড() async -> Result<ব্যবহারকারী, Error> {
    try {
        let ব্যবহারকারী = await API.getUser("123")
        return .success(ব্যবহারকারী)
    } catch e {
        return .failure(e)
    }
}

// Task (Go goroutine সমতুল্য)
task {
    // ব্যাকগ্রাউন্ড কাজ
    await ভারীকাজ()
}

// Channel (Go channel সমতুল্য)
let চ্যানেল = Channel<int32>(buffer: 10)

task {
    for i in 1..=10 {
        await চ্যানেল.পাঠাও(i)
    }
    চ্যানেল.বন্ধ()
}

for সংখ্যা in চ্যানেল {
    println(সংখ্যা)
}

// Actor (নিরাপদ মিউটেবল স্টেট)
actor ব্যাংকঅ্যাকাউন্ট {
    var ব্যালেন্স: float64 = 0.0
    
    fn জমা(পরিমাণ: float64) {
        ব্যালেন্স += পরিমাণ
    }
    
    fn উত্তোলন(পরিমাণ: float64) -> bool {
        if ব্যালেন্স >= পরিমাণ {
            ব্যালেন্স -= পরিমাণ
            return true
        }
        return false
    }
}
```

### ১৩.২ মেমোরি অপ্টিমাইজেশন

**ARC (Automatic Reference Counting):**

```c
// nil_memory.c — রেফারেন্স কাউন্টিং

typedef struct NilObject {
    atomic_int refcount;
    NilType *type;
    void (*destructor)(struct NilObject*);
    uint8_t data[];
} NilObject;

void nil_retain(NilObject *obj) {
    if (obj) atomic_fetch_add(&obj->refcount, 1);
}

void nil_release(NilObject *obj) {
    if (obj && atomic_fetch_sub(&obj->refcount, 1) == 1) {
        if (obj->destructor) obj->destructor(obj);
        free(obj);
    }
}
```

```nil
// todo_app.nil — সম্পূর্ণ টু-ডু অ্যাপ

@app {
    আইডি: "com.example.todo"
    নাম: "আমার কাজের তালিকা"
    সংস্করণ: "1.0.0"
    সর্বনিম্নAndroid: 26
    সর্বনিম্নIOS: "16.0"
}

// --- ডেটা মডেল ---

struct কাজ {
    id: string
    শিরোনাম: string
    সম্পন্ন: bool
    তৈরির_সময়: DateTime
    
    static fn নতুন(শিরোনাম: string) -> কাজ {
        return কাজ {
            id: UUID.নতুন(),
            শিরোনাম: শিরোনাম,
            সম্পন্ন: false,
            তৈরির_সময়: DateTime.এখন()
        }
    }
}

// --- স্টোর ---

store কাজেরস্টোর {
    state কাজসমূহ: List<কাজ> = []
    state লোডিং: bool = false
    
    computed মোট: int { return কাজসমূহ.দৈর্ঘ্য() }
    computed সম্পন্নমোট: int {
        return কাজসমূহ.গণনা { it.সম্পন্ন }
    }
    computed বাকি: int { return মোট - সম্পন্নমোট }
    
    action নতুনকাজযোগ(শিরোনাম: string) {
        if শিরোনাম.ছাঁটো().খালি() { return }
        let নতুন = কাজ.নতুন(শিরোনাম)
        কাজসমূহ = কাজসমূহ + [নতুন]
        await স্টোরেজেসংরক্ষণ()
    }
    
    action সম্পন্নটগল(id: string) {
        কাজসমূহ = কাজসমূহ.ম্যাপ { কাজ in
            if কাজ.id == id {
                return কাজ.copy(সম্পন্ন: !কাজ.সম্পন্ন)
            }
            return কাজ
        }
        await স্টোরেজেসংরক্ষণ()
    }
    
    action মুছে_ফেলো(id: string) {
        কাজসমূহ = কাজসমূহ.ফিল্টার { it.id != id }
        await স্টোরেজেসংরক্ষণ()
    }
    
    action লোড() async {
        লোডিং = true
        let সংরক্ষিত = await DB.সব_কাজ_পাও()
        কাজসমূহ = সংরক্ষিত
        লোডিং = false
    }
    
    private fn স্টোরেজেসংরক্ষণ() async {
        await DB.সব_কাজ_সংরক্ষণ(কাজসমূহ)
    }
}

// --- UI কম্পোনেন্ট ---

component কাজআইটেম(কাজ: কাজ) {
    render {
        Row(
            mainAxisAlignment: .spaceBetween,
            crossAxisAlignment: .center,
            padding: EdgeInsets.symmetric(horizontal: 16px, vertical: 8px)
        ) {
            Row(spacing: 12px) {
                Checkbox(

                    onChange: { কাজেরস্টোর.সম্পন্নটগল(কাজ.id) }
                )
                Text(কাজ.শিরোনাম) {
                    style: TextStyle {
                        strikethrough: কাজ.সম্পন্ন
                        color: কাজ.সম্পন্ন ? Color.ধূসর : Color.কালো
                        fontSize: 16sp
                    }
                }
            }
            
            IconButton(
                icon: Icons.মুছো,
                color: Color.লাল,
                onPress: { কাজেরস্টোর.মুছে_ফেলো(কাজ.id) }
            )
        }
        .swipeToDelete {
            কাজেরস্টোর.মুছে_ফেলো(কাজ.id)
        }
    }
}

component নতুনকাজফর্ম {
    state ইনপুট: string = ""
    
    render {
        Row(
            padding: EdgeInsets.all(16px),
            spacing: 8px
        ) {

    }
}

component পরিসংখ্যানব্যানার {
```

নীলাং (nilLang) ইতিমধ্যে একটি শক্তিশালী ভিত্তির উপর দাঁড়িয়ে আছে — Tree-Walking Interpreter, Bytecode Compiler + Stack VM, HIR/MIR/WASM কোড জেনারেশন, Declarative UI মডেল, Package Manager এবং একটি AI Compiler Oracle — এই সবকিছু একসাথে রয়েছে [9]। কিন্তু এটিকে Android, iOS এবং HarmonyOS-এর জন্য প্রকৃত নেটিভ মোবাইল অ্যাপ তৈরির উপযোগী করতে হলে আরও বেশ কয়েকটি গুরুত্বপূর্ণ স্তম্ভ নির্মাণ করতে হবে।

এই প্রতিবেদনটি সেই পথচলাকে বারোটি প্রধান অধ্যায়ে বিভক্ত করে বিশ্লেষণ করে: (১) নীলাং-এর বর্তমান অবস্থার নিরপেক্ষ মূল্যায়ন, (২) আধুনিক মোবাইল ভাষার অপরিহার্য উপাদান, (৩) বিদ্যমান ক্রস-প্ল্যাটফর্ম পদ্ধতির তুলনা, (৪) সম্পূর্ণ কম্পাইলার পাইপলাইন রোডম্যাপ, (৫) টাইপ সিস্টেম ও মেমোরি ব্যবস্থাপনা, (৬) LLVM-নির্ভর নেটিভ কোড জেনারেশন, (৭) UI ফ্রেমওয়ার্ক ইন্টিগ্রেশন, (৮) FFI ও নেটিভ API অ্যাক্সেস, (৯) বাংলা কীওয়ার্ড ডিজাইনের চ্যালেঞ্জ, (১০) ArkUI-X ইন্টিগ্রেশন কৌশল, (১১) ডেভেলপার টুলচেইন, এবং (১২) দীর্ঘমেয়াদী রোডম্যাপ।

মূল কৌশলগত সিদ্ধান্ত: নীলাংকে LLVM-এর উপর ভিত্তি করে একটি নেটিভ AOT কম্পাইলার, একটি C FFI স্তর এবং ArkUI-X-এর সাথে UI ব্রিজ দিয়ে সমৃদ্ধ করলে তিনটি প্রধান মোবাইল প্ল্যাটফর্মে অ্যাপ তৈরি সম্ভব।

## অধ্যায় ১: নীলাং-এর বর্তমান অবস্থা — শক্তি, দুর্বলতা ও সুযোগ

### ১.১ বর্তমান আর্কিটেকচার

GitHub রিপোজিটরি অনুযায়ী, নীলাং নিজেকে Go-এর সরলতা, Rust-এর পারফরম্যান্স ও নিরাপত্তা এবং ArkTS-এর মতো ডিক্লারেটিভ UI প্যারাডাইমের সমন্বয় বলে বর্ণনা করে [9]। এটি Alap Framework এবং Onuron OS ইকোসিস্টেমের জন্য তৃণমূল থেকে তৈরি [9]।

বর্তমানে যা আছে তার কম্পোনেন্ট তালিকা:

### ১.২ কী নেই — মোবাইলের জন্য গুরুত্বপূর্ণ ঘাটতি

**ক) LLVM ব্যাকএন্ড:** নীলাং-এর MIR আছে কিন্তু LLVM IR-এ emit করার ব্যাকএন্ড নেই। এটি ছাড়া ARM64 (Android বা iOS)-এ নেটিভ কোড জেনারেশন সম্ভব নয়। Flutter/Dart এবং Swift উভয়ই LLVM ব্যবহার করে নেটিভ ARM64 কোড তৈরি করে [23][33]।

**খ) C FFI স্তর:** ক্যামেরা, GPS, ব্লুটুথ, সেন্সর — এই সবকিছু অ্যাক্সেস করতে নেটিভ API কল প্রয়োজন, যার জন্য একটি সুনির্দিষ্ট Foreign Function Interface দরকার।

**গ) মোবাইল UI রেন্ডারিং ইঞ্জিন:** Alap UI ইতিমধ্যে ANSI/HTML রেন্ডারিং করে [9], কিন্তু GPU-নির্ভর মোবাইল রেন্ডারিং (Metal/Vulkan/OpenGL ES) করার জন্য আলাদা ইন্টিগ্রেশন প্রয়োজন।

**ঘ) প্ল্যাটফর্ম এমবেডার:** Android-এর জন্য Java/Kotlin এমবেডার, iOS-এর জন্য Swift/Objective-C এমবেডার তৈরি করতে হবে।

**ঙ) LSP সার্ভার:** IDE সাপোর্টের জন্য Language Server Protocol বাস্তবায়ন করতে হবে [17]।

**চ) HarmonyOS বিল্ড সিস্টেম:** ArkUI-X-এর সাথে নীলাং কোডকে কীভাবে ইন্টিগ্রেট করবো সেই পথচিত্র নেই।

### ১.৩ তুলনামূলক বাংলা ভাষা ইকোসিস্টেম

বাংলা প্রোগ্রামিং ভাষার ক্ষেত্রে কয়েকটি প্রকল্প ইতিমধ্যে বিদ্যমান, যাদের কাছ থেকে শিক্ষা নেওয়া যায়:

- **পঙক্তি (Pankti):** Go-তে লেখা, ডায়নামিক টাইপড, Gomobile দিয়ে Android/iOS বাইন্ডিং পরীক্ষা করা হয়েছে [10][20]। সমস্যা: CLI-মুখী ডিজাইন GUI ফ্রন্টএন্ডে আউটপুট প্রদর্শনে সমস্যা তৈরি করেছে [20]।
- **Bnlang:** C++ ট্রি-ওয়াকিং ইন্টারপ্রেটার, libuv ইভেন্ট লুপ, FFI প্লাগইন সাপোর্ট (.dll/.so/.dylib) [11][22][41]। বাংলা/ইংরেজি দ্বৈত কীওয়ার্ড একই AST-তে নর্মালাইজ করা হয় [11][41]।
- **শুন্য (Shunno):** স্ট্যাটিক্যালি টাইপড, মেশিন কোডে কম্পাইল [12]।
- **ভাষা (Bhasa):** Go-তে লেখা কম্পাইলড ভাষা, ৩,২০০+ লাইন [31]।

এই প্রকল্পগুলির মধ্যে কেউই এখনো Android/iOS-এর জন্য সম্পূর্ণ নেটিভ অ্যাপ তৈরির ক্ষমতা প্রদর্শন করেনি। নীলাং সেই শূন্যতা পূরণ করতে পারে।

## অধ্যায় ২: আধুনিক মোবাইল ভাষায় কী কী উপাদান থাকা দরকার

### ২.১ মোবাইল-প্রথম ভাষার অপরিহার্য বৈশিষ্ট্য

বিদ্যমান সফল মোবাইল ভাষাগুলি বিশ্লেষণ করলে নিম্নলিখিত উপাদানগুলি অপরিহার্য:

**ক) স্ট্যাটিক টাইপ সিস্টেম:** ArkTS TypeScript-এর dynamic typing (`any`) সম্পূর্ণ নিষিদ্ধ করেছে কারণ AOT কম্পাইলেশনের জন্য স্থির টাইপ তথ্য প্রয়োজন [24]। Swift এবং Dart উভয়ই sound type checking করে [14][33]। নীলাং-এ ইতিমধ্যে Advanced Type System আছে [9], এটিকে আরও কঠোর করতে হবে।

**খ) Null Safety:** Dart-এ built-in sound null safety আছে যা compile-time-এ null exception ধরে [14]। ArkTS-তে সব টাইপ default-এ non-nullable [42]। নীলাং-এও এই বৈশিষ্ট্য যোগ করতে হবে।

**গ) Async/Concurrency মডেল:** মোবাইল অ্যাপে UI থ্রেড ব্লক করা মারাত্মক। Dart isolates ব্যবহার করে (মেমরি শেয়ার না করে বার্তা আদান-প্রদান) [14]। ArkTS async/await এবং actors ব্যবহার করে [2]। ArkCompiler TaskPool এবং Worker API দেয় [39]।

**ঘ) AOT কম্পাইলেশন:** iOS App Store নীতি রানটাইমে JIT নিষিদ্ধ করে [43]। অতএব নীলাং-এর জন্য AOT অপরিহার্য। ArkTS Ark Compiler দিয়ে AOT করে [1][2]। Swift LLVM দিয়ে AOT করে [33]।

**ঙ) ডিক্লারেটিভ UI:** Jetpack Compose (Android), SwiftUI (iOS), ArkUI (HarmonyOS) — সবগুলোই declarative paradigm অনুসরণ করে। নীলাং-এ Alap UI ইতিমধ্যে এই প্যারাডাইম অনুসরণ করে [9]।

**চ) Memory Management:** Swift ARC (Automatic Reference Counting) ব্যবহার করে [33]। Dart GC ব্যবহার করে [14]। Kotlin/Native নিজস্ব tracing GC ব্যবহার করে [27]। নীলাং-কে মোবাইলের সীমিত RAM-এ কার্যকর মেমরি ব্যবস্থাপনা নিশ্চিত করতে হবে।

**ছ) FFI/Interop:** Flutter dart:ffi দিয়ে C কোড কল করে [18]। Kotlin/Native C এবং Swift/Objective-C ইন্টারঅপ সমর্থন করে [27]। Bnlang .so/.dll/.dylib প্লাগইন সাপোর্ট করে [11][41]।

**জ) Hot Reload:** Dart VM ডেভেলপমেন্টে JIT দিয়ে incremental recompilation সমর্থন করে [14]। এটি ডেভেলপার প্রোডাক্টিভিটির জন্য গুরুত্বপূর্ণ।

## অধ্যায় ৩: Android, iOS ও HarmonyOS-এর জন্য ক্রস-প্ল্যাটফর্ম পদ্ধতি

### ৩.১ বিদ্যমান প্রযুক্তির ল্যান্ডস্কেপ

**Flutter/Dart:** ২০২৬ সালে মোবাইল ডেভেলপারদের মধ্যে প্রায় ৪৬% বাজার শেয়ার [3]। Dart AOT কম্পাইলার নেটিভ ARM বা x64 মেশিন কোডে কম্পাইল করে [14]। Flutter-এর তিন স্তর আছে: Embedder (প্ল্যাটফর্ম-নির্দিষ্ট ভাষায়), Engine (C++), এবং Framework (Dart) [23]। Flutter নিজেই GPU-তে Impeller রেন্ডারার দিয়ে UI রেন্ডার করে [5]।

**Kotlin Multiplatform:** মে ২০২৫-এ iOS স্ট্যাবল হয়েছে [3]। iOS-এ Kotlin/Native ব্যবহার করে native ARM binary তৈরি করে [5]। Google অফিসিয়ালি KMP সুপারিশ করে Android ও iOS-এর মধ্যে কোড শেয়ারের জন্য [3]।

**React Native:** Meta রক্ষণাবেক্ষণ করে। নতুন আর্কিটেকচারে Bridge সরানো হয়েছে, JSI দিয়ে সরাসরি native যোগাযোগ [19]।

**ArkUI-X (হুয়াওয়ে):** Android, iOS, OpenHarmony এবং HarmonyOS-এর জন্য একটি একক কোডবেস থেকে অ্যাপ তৈরি সম্ভব [36]। ডিসেম্বর ৩১, ২০২৫-এ ArkUI-X 6.0.0 রিলিজ হয়েছে [36]। ArkUI-X-এর কোর C++-এ লেখা পোর্টেবিলিটির জন্য [36]।

### ৩.২ নীলাং-এর জন্য কোন পদ্ধতি সবচেয়ে উপযুক্ত?

নীলাং-এর জন্য সবচেয়ে কার্যকর কৌশল হবে **হাইব্রিড অ্যাপ্রোচ**:

1. **নীলাং → LLVM IR → ARM64 নেটিভ কোড** (Flutter/Dart এবং Swift-এর মতো [23][33])
2. **C FFI স্তর** দিয়ে প্ল্যাটফর্ম API অ্যাক্সেস (Kotlin/Native cinterop-এর মতো [38])
3. **ArkUI-X ইন্টিগ্রেশন** তিন প্ল্যাটফর্মে UI শেয়ার করতে [36][37]
4. **প্ল্যাটফর্ম এমবেডার** Android-এ Kotlin/Java এবং iOS-এ Swift-এ লেখা (Flutter-এর মতো [13])

এই পদ্ধতিতে নীলাং প্রকৃত অর্থে নেটিভ পারফরম্যান্স পাবে এবং React Native-এর ব্রিজ ওভারহেড এড়ানো যাবে।

## অধ্যায় ৪: নীলাং-এর সম্পূর্ণ কম্পাইলার পাইপলাইন রোডম্যাপ

### ৪.১ কম্পাইলার পাইপলাইনের সামগ্রিক চিত্র

একটি আধুনিক কম্পাইলারের চারটি মূল পর্যায় আছে: lex (শব্দে বিভক্ত করা), parse (ব্যবহার বোঝা), type-check (শ্রেণীবদ্ধ করা ও ব্যাকরণগত সংগতি পরীক্ষা), এবং machine instruction-এ অনুবাদ [6]। কম্পাইলার পর্যায়গুলি frontend, middle-end এবং backend-এ সংগঠিত হয় [6]।

নীলাং-এর জন্য সম্পূর্ণ পাইপলাইন:

```
বাংলা/ইংরেজি সোর্স কোড
        ↓
    [লেক্সার] — Unicode-সচেতন টোকেনাইজেশন
        ↓
    [পার্সার] — AST জেনারেশন
        ↓
    [সিম্যান্টিক অ্যানালাইসিস] — স্কোপ, টাইপ রেজোলিউশন
        ↓
    [স্ট্যাটিক টাইপচেকার + Null Checker]
        ↓
    [HIR] — High-Level IR + কনস্ট্যান্ট ফোল্ডিং
        ↓
    [MIR/CFG] — Basic Blocks, SSA Form
        ↓
    [LLVM IR Emitter] ← নতুন কম্পোনেন্ট প্রয়োজন
        ↓
    [LLVM Optimizer] — -O2/-O3 অপ্টিমাইজেশন
        ↓
    ┌──────────────────┬──────────────────┐
    ↓                  ↓                  ↓
[ARM64 Android]  [ARM64 iOS]      [WASM] (বিদ্যমান)
    ↓                  ↓
[NDK Linker]    [LLVM Linker + XCFramework]
    ↓                  ↓
  .apk/.aab         .ipa
```

### ৪.২ লেক্সার (Lexer) — বাংলা Unicode চ্যালেঞ্জ

বাংলা সমর্থনের জন্য লেক্সারে সবচেয়ে জটিল সমস্যা হল UTF-8-এর পরিবর্তনশীল দৈর্ঘ্য। একটি বাংলা অক্ষর সনাক্ত করতে পরবর্তী এবং পরবর্তীর পরবর্তী অক্ষর চেক করতে হয় (যেমন `0xE0` দেখলে পরের দুটি বাইট একসাথে একটি বাংলা অক্ষর তৈরি করে) [21]।

Pankti ভাষার অভিজ্ঞতা থেকে শিক্ষা: UTF-32 ইন্টার্নালি ব্যবহার করলে কোড সহজ থাকে কিন্তু কিছুটা বেশি মেমরি খরচ হয় [21]। নীলাং-এর জন্য সুপারিশ: **ইন্টার্নালি UTF-32 ব্যবহার করুন**, ইনপুট/আউটপুটে UTF-8 রূপান্তর করুন।

Bnlang একটি ভিন্ন পদ্ধতি নিয়েছে: বাংলা ও ইংরেজি টোকেন একই AST-তে নর্মালাইজ করা হয়, lexer উভয় keyword set ম্যাপ করে একই syntax tree-এ [11][41]। নীলাং-ও এই পদ্ধতি অনুসরণ করতে পারে।

**লেক্সারের বাস্তবায়ন পদক্ষেপ:**
1. Unicode স্ক্যানার: UTF-8 → UTF-32 রূপান্তর
2. বাংলা কীওয়ার্ড টেবিল: `যদি`→`if`, `তাহলে`→`then`, `নাহলে`→`else`, `কাজ`→`fn`, `ফেরত`→`return`, `সত্য`→`true`, `মিথ্যা`→`false` ইত্যাদি
3. ইংরেজি কীওয়ার্ড টেবিলের সমান্তরাল ম্যাপিং
4. মিশ্র-ভাষা কোড সমর্থন (বাংলা ও ইংরেজি একসাথে)

### ৪.৩ পার্সার (Parser) এবং AST

নীলাং ইতিমধ্যে পার্সার রয়েছে [9]। মোবাইলের জন্য যোগ করতে হবে:

- **Alap Component Syntax:** `component`, `state`, `render`, `on`, `build`, `emit` কীওয়ার্ড [9]
- **Error Recovery:** পার্সার ত্রুটিতেও AST আংশিকভাবে তৈরি হওয়া উচিত যাতে LSP কাজ করে
- **Span Information:** প্রতিটি AST নোডে সোর্স লোকেশন (ফাইল, লাইন, কলাম) সংরক্ষণ করতে হবে ডিবাগিং ও LSP-র জন্য

### ৪.৪ টাইপ চেকার (Type Checker)

কম্পাইলার ফ্রন্টএন্ডে dude-checking এবং data-race checking আলাদা দুটি পর্যায়ে করা যায় [6]। নীলাং-এ ইতিমধ্যে Capability Sandbox আছে [9] যা data-race prevention-এর ভিত্তি হতে পারে।

মোবাইলের জন্য টাইপচেকারে যোগ করতে হবে:
1. **Null Flow Analysis:** প্রতিটি ভ্যারিয়েবলে null কি পারে কিনা তার flow-sensitive tracking
2. **Lifetime Analysis:** Rust-এর মতো নয়, বরং Swift ARC-এর মতো চক্রীয় রেফারেন্স সনাক্তকরণ
3. **Permission Type System:** কোন ফাংশন কোন হার্ডওয়্যার API অ্যাক্সেস করতে পারবে তার capability-based checking

### ৪.৫ HIR → MIR → LLVM IR ট্রান্সফর্মেশন

নীলাং-এ ইতিমধ্যে HIR এবং MIR আছে [9]। এরপর LLVM IR emit করতে হবে।

MIR থেকে LLVM IR রূপান্তরের ধাপ:
1. **SSA Form নিশ্চিত করা:** LLVM IR SSA (Static Single Assignment) ফর্মে থাকে; নীলাং-এর MIR ইতিমধ্যে SSA Temporaries সমর্থন করে [9]
2. **Type Mapping:** নীলাং টাইপ → LLVM IR টাইপ (`i64`, `f64`, `ptr`, `[N x T]` ইত্যাদি)
3. **GC Statepoints:** GC-সামঞ্জস্যপূর্ণ কোড জেনারেশনের জন্য LLVM-এর Statepoint সাপোর্ট ব্যবহার করা যায় [28]
4. **Call Convention:** ARM64 AAPCS64 (Android) এবং Apple ARM64 calling convention (iOS)

## অধ্যায় ৫: টাইপ সিস্টেম, মেমোরি ব্যবস্থাপনা ও কনকারেন্সি মডেল

### ৫.১ মোবাইলের জন্য টাইপ সিস্টেম ডিজাইন

নীলাং ইতিমধ্যে Generics, Union Types, Effect Types এবং Algebraic Data Types (ADT) সমর্থন করে [9]। মোবাইলের জন্য আরও যোগ করতে হবে:

**ক) Non-Nullable by Default:**
```
// নীলাং-এ প্রস্তাবিত সিনট্যাক্স
কাজ নামখোঁজো(নাম: পাঠ) → ব্যক্তি {  // non-nullable
    ...
}
কাজ নামখোঁজো(নাম: পাঠ) → ব্যক্তি? {  // nullable (Optional)
    ...
}
```

ArkTS-এ সব টাইপ ডিফল্টে non-nullable এবং null অনুমতি দিতে union type ব্যবহার করতে হয় [42]। Dart-এ ? suffix দিয়ে nullable ঘোষণা করতে হয় [14]।

**খ) Effect System:** নীলাং-এ Effect Type আছে [9]। এটি ব্যবহার করে IO, Network, Camera, GPS ইত্যাদির জন্য effect annotation যোগ করা যায়:
```
কাজ ছবিতোলো() → ছবি | প্রভাব[ক্যামেরা, স্টোরেজ] {
    ...
}
```

**গ) Platform Type:** প্ল্যাটফর্ম-নির্দিষ্ট টাইপ চিহ্নিত করতে:
```
টাইপ অ্যান্ড্রয়েড_বিটম্যাপ = প্ল্যাটফর্ম<Android, "android.graphics.Bitmap">
টাইপ iOS_UIImage = প্ল্যাটফর্ম<iOS, "UIImage">
```

### ৫.২ মেমোরি ব্যবস্থাপনা — মোবাইলের সীমাবদ্ধতা

মোবাইল ডিভাইসে RAM সীমিত (সাধারণত ৩-১২ GB) এবং প্রতিটি অ্যাপ-এর মেমরি কোটা আরও সীমিত। তিনটি প্রধান কৌশল:

**ক) Tracing Garbage Collector (GC):**
Kotlin/Native ট্রেসিং GC ব্যবহার করে Swift/Objective-C-এর ARC-এর সাথে ইন্টিগ্রেটেড [27]। একটি কাস্টম মেমরি অ্যালোকেটর হঠাৎ মেমরি বরাদ্দে বৃদ্ধি প্রতিরোধ করে [27]।

**খ) Reference Counting (ARC-style):**
Swift ARC ব্যবহার করে মেমরি স্বয়ংক্রিয়ভাবে পরিচালনা করে [33]। Bnlang C++ shared_ptr lifetime ব্যবহার করে [41]।

**গ) নীলাং-এর জন্য সুপারিশ: দুই-স্তরের কৌশল**
- **UI থ্রেড:** ARC-style reference counting (predictable latency, মোবাইল UI-এর জন্য গুরুত্বপূর্ণ)
- **ব্যাকগ্রাউন্ড থ্রেড:** Generational GC (throughput optimization)

LLVM Statepoint দিয়ে GC-সামঞ্জস্যপূর্ণ কোড জেনারেশন করা যায়, যদিও এটি জটিল [28]।

### ৫.৩ কনকারেন্সি মডেল

মোবাইল অ্যাপে কনকারেন্সি অপরিহার্য: নেটওয়ার্ক রিকোয়েস্ট, ডেটাবেস পড়া, ছবি প্রক্রিয়াকরণ — সবকিছু UI থ্রেড বাইরে করতে হয়।

**বিদ্যমান পদ্ধতির তুলনা:**

| পদ্ধতি | কে ব্যবহার করে | বৈশিষ্ট্য |
|---|---|---|
| Isolates | Dart | মেমরি শেয়ার না করে বার্তা আদান-প্রদান [14] |
| Actors | ArkTS | shared mutable state বিচ্ছিন্ন করে data race দূর করে [2] |
| TaskPool/Worker | ArkCompiler | instance memory বিচ্ছিন্ন করে [39] |
| Structured Concurrency | Swift | async/await + actor মডেল [33] |

**নীলাং-এর জন্য প্রস্তাবিত কনকারেন্সি:**
```
// নীলাং-এ প্রস্তাবিত সিনট্যাক্স
অভিনেতা ডেটাব্যবস্থাপক {
    অবস্থা ডেটা: [পাঠ: যেকোনো] = {}
    
    অপেক্ষা কাজ সংরক্ষণকরো(চাবি: পাঠ, মান: যেকোনো) {
        // স্বয়ংক্রিয়ভাবে সিরিয়ালাইজড
        এই.ডেটা[চাবি] = মান
    }
}

// কল করার সময়
অপেক্ষা ডেটাব্যবস্থাপক.সংরক্ষণকরো("ব্যবহারকারী", ব্যবহারকারীডেটা)
```

ArkTS-এর মতো actor মডেল data race নিরাপত্তা নিশ্চিত করে [2]।

## অধ্যায় ৬: LLVM দিয়ে নেটিভ ARM64 কোড জেনারেশন

### ৬.১ LLVM কেন অপরিহার্য

LLVM একটি মডুলার এবং পুনর্ব্যবহারযোগ্য কম্পাইলার টুলচেইন যা আধুনিক প্রোগ্রামিং ভাষার ভিত্তি [7]। Swift LLVM ব্যবহার করে optimized machine code তৈরি করে [33]। Flutter-এর iOS-এ C/C++ কোড LLVM দিয়ে কম্পাইল হয় [23]। Kotlin/Native LLVM-ভিত্তিক ব্যাকএন্ড ব্যবহার করে [27][38]। LLVM IR ভাষা-স্বাধীন প্রতিনিধিত্ব যা একাধিক আর্কিটেকচারের জন্য কোড জেনারেশন সক্ষম করে [7]।

### ৬.২ LLVM ব্যাকএন্ড তৈরির ধাপ

LLVM ব্যাকএন্ড তৈরির জন্য `TargetMachine` ক্লাসের সাবক্লাস তৈরি করে টার্গেট মেশিনের বৈশিষ্ট্য বর্ণনা করতে হয় [16]।

**ধাপ ১: LLVM প্রকল্পে নীলাং ব্যাকএন্ড যোগ করা**

```
lib/Target/
├── NilLang/
│   ├── CMakeLists.txt
│   ├── NilLangTargetMachine.cpp    # TargetMachine সাবক্লাস
│   ├── NilLangInstrInfo.td         # নির্দেশনার TableGen বিবরণ
│   ├── NilLangRegisterInfo.td      # রেজিস্টার সংজ্ঞা
│   ├── NilLangISelDAGToDAG.cpp     # Pattern matching
│   └── NilLangISelLowering.cpp     # SelectionDAG lowering
```

LLVM ব্যাকএন্ড কোড জেনারেশনের পর্যায়গুলি: Instruction Selection → Scheduling → SSA-ভিত্তিক Optimization → Register Allocation → Prolog/Epilog Code Insertion → Code Emission [16]।

**ধাপ ২: নীলাং MIR → LLVM IR Emitter**

নীলাং-এর Go বা Rust কম্পোনেন্ট `llvm-c` বাইন্ডিং বা `inkwell` (Rust LLVM wrapper) ব্যবহার করে LLVM IR তৈরি করতে পারে:

```rust
// Rust দিয়ে LLVM IR emit করার উদাহরণ কাঠামো
use inkwell::context::Context;
use inkwell::targets::{Target, TargetMachine, RelocMode, CodeModel, FileType};
use inkwell::OptimizationLevel;

fn emit_arm64_android(module: &Module) -> Vec<u8> {
    Target::initialize_aarch64(&InitializationConfig::default());
    let target = Target::from_name("aarch64").unwrap();
    let machine = target.create_target_machine(
        &TargetTriple::create("aarch64-linux-android29"),
        "generic",
        "",
        OptimizationLevel::Aggressive,
        RelocMode::PIC,
        CodeModel::Default,
    ).unwrap();
    machine.write_to_memory_buffer(module, FileType::Object).unwrap().as_slice().to_vec()
}

fn emit_arm64_ios(module: &Module) -> Vec<u8> {
    Target::initialize_aarch64(&InitializationConfig::default());
    let target = Target::from_name("aarch64").unwrap();
    let machine = target.create_target_machine(
        &TargetTriple::create("arm64-apple-ios15.0"),
        "apple-a14",
        "",
        OptimizationLevel::Aggressive,
        RelocMode::PIC,
        CodeModel::Default,
    ).unwrap();
    machine.write_to_memory_buffer(module, FileType::Object).unwrap().as_slice().to_vec()
}
```

**ধাপ ৩: Android NDK দিয়ে লিংক করা**

Android-এ Engine-এর C/C++ কোড Android NDK দিয়ে কম্পাইল করা হয় এবং Dart কোড ARM এবং x86 লাইব্রেরিতে AOT কম্পাইল হয় [23]। নীলাং-এর জন্যও একই পদ্ধতি:

```
nilc --target=aarch64-linux-android29 --output=libnilapp.so input.nil
# NDK সহ লিংক:
$NDK/toolchains/llvm/prebuilt/linux-x86_64/bin/aarch64-linux-android29-clang \
    -shared libnilapp.o -o libnilapp.so
```

**ধাপ ৪: iOS XCFramework তৈরি**

iOS-এর জন্য উভয় SDK (iphoneos এবং iphonesimulator) দিয়ে বিল্ড করে XCFramework তৈরি করতে হয় [18]:

```bash
nilc --target=arm64-apple-ios15.0 -o libnilapp-ios.o input.nil
nilc --target=arm64-apple-ios15.0-simulator -o libnilapp-sim.o input.nil

xcodebuild -create-xcframework \
    -library libnilapp-ios.o \
    -library libnilapp-sim.o \
    -output NilLang.xcframework
```

### ৬.৩ GC এবং LLVM সমন্বয়

LLVM Statepoint ফিচার GC সাপোর্ট প্রদান করে, যা moving এবং precise GC সক্ষম করে [28]। Dart-on-LLVM পরীক্ষায় দেখা গেছে এই পদ্ধতি কার্যকর, যদিও জটিল [28]। নীলাং-এর জন্য প্রাথমিকভাবে সহজ পদ্ধতি:
- **Shadow Stack:** GC root ট্র্যাকিংয়ের জন্য, সহজ কিন্তু কিছুটা ধীর
- পরে Statepoint-এ আপগ্রেড করা যাবে

## অধ্যায় ৭: মোবাইল UI ফ্রেমওয়ার্ক ইন্টিগ্রেশন

### ৭.১ তিনটি পদ্ধতির তুলনা

**পদ্ধতি A: সম্পূর্ণ নিজস্ব GPU রেন্ডারার (Flutter পদ্ধতি)**

Flutter নিজেই Impeller রেন্ডারার দিয়ে iOS-এ Metal এবং Android-এ Vulkan ব্যবহার করে রেন্ডার করে [5]। এর সুবিধা: সম্পূর্ণ নিয়ন্ত্রণ, সব প্ল্যাটফর্মে অভিন্ন UI। অসুবিধা: iOS-এ Metal shader compilation stall সমস্যা হয় [35], অনেক বেশি প্রকৌশল কাজ।

নীলাং-এ ইতিমধ্যে "GPU Renderer Foundation" এবং "60 FPS Animation Engine" আছে [9]। এটিকে Android-এর Vulkan এবং iOS-এর Metal API-তে সংযুক্ত করতে হবে FFI-এর মাধ্যমে।

**পদ্ধতি B: নেটিভ প্ল্যাটফর্ম UI ব্যবহার (React Native পদ্ধতি)**

React Native কম্পোনেন্ট নেটিভ Android/iOS ভিউ-তে রূপান্তরিত হয় [23]। নীলাং Alap UI কম্পোনেন্ট → Android View/Jetpack Compose এবং iOS UIKit/SwiftUI-তে ম্যাপ করা। সুবিধা: নেটিভ অনুভূতি। অসুবিধা: প্ল্যাটফর্ম পার্থক্য ব্যবস্থাপনা জটিল।

**পদ্ধতি C: ArkUI-X ইন্টিগ্রেশন (সবচেয়ে কৌশলগতভাবে সুবিধাজনক)**

ArkUI-X একটি ওপেন-সোর্স ক্রস-প্ল্যাটফর্ম ফ্রেমওয়ার্ক যা OpenHarmony, HarmonyOS, Android এবং iOS-এর জন্য একটি কোডবেস থেকে অ্যাপ তৈরি সক্ষম করে [36]। ArkUI-X-এর কোর C++-এ লেখা [36]। ArkUI-X ডিসেম্বর ৩১, ২০২৫-এ 6.0.0 রিলিজ হয়েছে [36]।

### ৭.২ নীলাং + ArkUI-X ইন্টিগ্রেশন পরিকল্পনা

নীলাং কোড থেকে ArkUI-X ব্যবহারের জন্য:

**স্তর ১: নীলাং Alap UI → ArkTS ট্রান্সপাইলেশন**

নীলাং-এর Alap UI সিনট্যাক্স ArkTS-এর UI সিনট্যাক্সের সাথে ধারণাগতভাবে সামঞ্জস্যপূর্ণ। উভয়ই ডিক্লারেটিভ [9][2]।

```
// নীলাং Alap UI
উপাদান স্বাগতপর্দা {
    অবস্থা নাম: পাঠ = "বিশ্ব"
    
    নির্মাণ {
        স্তম্ভ {
            পাঠ("হ্যালো, \(নাম)!")
            বোতাম("পরিবর্তন করুন") {
                এই.নাম = "নীলাং"
            }
        }
    }
}
```

↓ ট্রান্সপাইলড →

```typescript
// ArkTS (ArkUI-X-সামঞ্জস্যপূর্ণ)
@Component
struct WelcomeScreen {
    @State name: string = "বিশ্ব"
    
    build() {
        Column() {
            Text(`হ্যালো, ${this.name}!`)
            Button("পরিবর্তন করুন").onClick(() => {
                this.name = "নীলাং"
            })
        }
    }
}
```

ArkUI-X Android এবং iOS উভয়ের জন্য adaptation layer অফার করে [37]।

**স্তর ২: নীলাং → ArkTS কম্পাইলার মোড**

নীলাং কম্পাইলারে একটি নতুন ব্যাকএন্ড যোগ করতে হবে: MIR → ArkTS কোড emit। এটি ArkUI-X-এর সাথে পরিপূর্ণ সামঞ্জস্য নিশ্চিত করবে।

**স্তর ৩: C++ FFI ব্রিজ**

ArkUI-X-এর কোর C++-এ [36], নীলাং-এর নেটিভ রানটাইমও C/C++ expose করতে পারে, এবং ArkUI-X-এর সাথে সরাসরি C API দিয়ে যোগাযোগ করতে পারে।

### ৭.৩ প্রতিটি প্ল্যাটফর্মে UI শেয়ারিং কৌশল

ArkUI-X একটি "unified interface + dynamic adaptation" মডেল ব্যবহার করে [36]। উদাহরণ: @ARAdapter অ্যানোটেশন দিয়ে বিভিন্ন প্ল্যাটফর্মের AR ইঞ্জিন (Huawei AR Engine, ARKit, ARCore) ম্যাপ করা হয় [36]।

নীলাং-এর জন্য একই নীতি:
```
// নীলাং-এ প্রস্তাবিত প্ল্যাটফর্ম-নির্দিষ্ট অভিযোজন
@প্ল্যাটফর্ম_অভিযোজক
উপাদান মানচিত্র {
    #অ্যান্ড্রয়েড: GoogleMapsView()
    #iOS: AppleMapsView()
    #হার্মনি: HuaweiMapView()
}
```

Compose Multiplatform iOS-এ Skiko দিয়ে Metal-এ সরাসরি রেন্ডার করে UIKit এর লেআউট ইঞ্জিন বাইপাস করে [35]। Metal shader compilation stall এড়াতে splash screen-এ shader warmup করা উচিত [35]।

## অধ্যায় ৮: FFI — নেটিভ মোবাইল API অ্যাক্সেস

### ৮.১ FFI কেন গুরুত্বপূর্ণ

ক্যামেরা, GPS, ব্লুটুথ, সেন্সর, পুশ নোটিফিকেশন, বায়োমেট্রিক্স — এই সবকিছু প্ল্যাটফর্ম-নির্দিষ্ট নেটিভ API দিয়ে অ্যাক্সেস করতে হয়। Flutter `dart:ffi` লাইব্রেরি ব্যবহার করে নেটিভ API কল করে [18]।

### ৮.২ নীলাং FFI ডিজাইন

**স্তর ১: C ABI FFI (সর্বজনীন ভিত্তি)**

C ABI সবথেকে সার্বজনীন। Bnlang-ও .dll/.so/.dylib প্লাগইন C ABI দিয়ে লেখা যায় [11][41]।

```

    রেজোলিউশন_উচ্চতা: পূর্ণসংখ্যা
) → পূর্ণসংখ্যা  // handle ফেরত দেয়

// একটি বাইন্ডিং ফাইলে:
```

Android-এ Java/Kotlin API অ্যাক্সেস করতে JNI প্রয়োজন:

### ৯.১ বাংলা কীওয়ার্ড ডিজাইনের চ্যালেঞ্জ

**ক) Unicode সমস্যা:** বাংলা ভাষা ইউনিকোড ব্লক U+0980 থেকে U+09FF। পঙক্তি ভাষার অভিজ্ঞতা থেকে জানা যায় বাংলা সমর্থন প্রকল্পের সবচেয়ে কঠিন অংশ [21]।

UTF-8-এ বাংলা অক্ষর ৩ বাইট নেয়। একটি বাংলা অক্ষর সনাক্ত করতে পরের দুটি বাইটও চেক করতে হয় [21]। UTF-32 ইন্টার্নালি ব্যবহার করলে কোড সহজ থাকে কিন্তু কিছুটা বেশি মেমরি খরচ হয় [21]।

**খ) অনুরণন বনাম প্রোগ্রামিং রীতি:** পঙক্তির নীতি হল সিনট্যাক্স এমনভাবে ডিজাইন করা যা দৈনন্দিন বাংলা বাচনভঙ্গির সাথে সাদৃশ্যপূর্ণ এবং একই সাথে প্রোগ্রামিং রীতির সাথেও [10]।

**গ) দ্বৈত ভাষা সমর্থন:** Bnlang-এর পদ্ধতি সবচেয়ে পরিপক্ক: বাংলা ও ইংরেজি উভয় keyword set একই AST-তে ম্যাপ করা হয় [11]। শুধু `print` লিখলেও চলে, `লিখুন` লিখলেও চলে [11]।

### ১০.১ ArkUI-X আর্কিটেকচার

ArkUI-X OpenHarmony-র ArkUI native framework-এর extension যা Android এবং iOS-এ deploy করতে দেয় [36]। ArkUI-X-এর মূল বৈশিষ্ট্য:

- **একক কোডবেস:** একই ArkTS কোড Android, iOS, OpenHarmony এবং HarmonyOS-এ চলে [36]
- **Self-rendering:** নেটিভ প্ল্যাটফর্মের গ্রাফিক্স সিস্টেমে সরাসরি নির্ভরতা কমিয়ে নিজেই রেন্ডার করে [36]
- **Platform Adaptation Layer:** Android ও iOS-এর জন্য ডেডিকেটেড adaptation layer [37]
- **Cross-platform Plugins:** `@ohos.xxx` স্টাইল প্লাগইন Android ও iOS-এ কাজ করে [37]
- **6.0.0 রিলিজ:** SwipeRefresher, TreeView সহ উন্নত কম্পোনেন্ট [36]

### ১০.২ HarmonyOS NEXT-এ বিশেষ বিবেচনা

HarmonyOS NEXT সম্পূর্ণভাবে Android সামঞ্জস্যতা অপসারণ করেছে এবং নেটিভ DevEco Studio, Ark Compiler, ArkUI Framework এবং ArkTS-নির্মিত অ্যাপ প্রয়োজন করে [1]। HarmonyOS ৯০০ মিলিয়নেরও বেশি সক্রিয় ডিভাইসে চলে [24]।

HarmonyOS-এর জন্য বিশেষ বৈশিষ্ট্য:
- **Distributed Architecture:** ডিভাইসগুলির মধ্যে সহযোগিতা [25]
- **HMS (Huawei Mobile Services):** GMS প্রতিস্থাপন [1]
- **ArkUI Decorators:** @State, @Link, @Prop [24][42]
- **HarmonyOS NEXT → Android মাইগ্রেশন:** A2H Converter দিয়ে স্বয়ংক্রিয় XML→ArkUI মাইগ্রেশন [1]

### ১০.৩ নীলাং থেকে ArkUI-X ব্যবহারের তিনটি কৌশল

**কৌশল ১: নীলাং → ArkTS ট্রান্সপাইলার**

নীলাং কম্পাইলারে একটি ব্যাকএন্ড যোগ করুন যা ArkTS কোড emit করে। তারপর ArkUI-X টুলচেইন সেই কোড Android, iOS ও HarmonyOS-এর জন্য বিল্ড করবে।

সুবিধা: ArkUI-X-এর সমস্ত সুবিধা পাওয়া যায়, HarmonyOS-এর সাথে সম্পূর্ণ সামঞ্জস্য।
অসুবিধা: দুটি ভাষার কোডবেস রক্ষণাবেক্ষণ।

**কৌশল ২: নীলাং AOT বাইনারি + ArkUI-X রেন্ডারিং ইঞ্জিন**

নীলাং LLVM দিয়ে নেটিভ বাইনারি তৈরি করে এবং ArkUI-X-এর রেন্ডারিং ইঞ্জিন C++ API-এর মাধ্যমে ব্যবহার করে।

সুবিধা: নীলাং-এর নেটিভ পারফরম্যান্স + ArkUI-X-এর UI।
অসুবিধা: জটিল C++ ইন্টিগ্রেশন।

**কৌশল ৩: হাইব্রিড — UI স্তরে ArkUI-X, লজিক স্তরে নীলাং নেটিভ**

UI কোড ArkTS-এ লেখা হয় এবং ArkUI-X দিয়ে বিল্ড হয়। ব্যবসায়িক লজিক নীলাং-এ লেখা হয় এবং LLVM দিয়ে shared library হিসেবে কম্পাইল হয়। C FFI দিয়ে ArkTS → নীলাং native library কল করা হয়।

এটি সবচেয়ে বাস্তবসম্মত পদ্ধতি এবং Kotlin Multiplatform-এর "shared logic layer + platform UI" কৌশলের অনুরূপ [5]।

### ১০.৪ DevEco Studio ইন্টিগ্রেশন

HarmonyOS ডেভেলপমেন্টের জন্য DevEco Studio প্রাথমিক IDE [1]। নীলাং-এর জন্য DevEco Studio প্লাগইন তৈরি করা যেতে পারে যা:
- .nil ফাইল সিনট্যাক্স হাইলাইট করে
- ArkUI-X প্রকল্পে নীলাং কোড ইন্টিগ্রেট করে
- HarmonyOS HapBuilder-এ নীলাং বিল্ড স্টেপ যোগ করে

## অধ্যায় ১১: ডেভেলপার টুলচেইন

### ১১.১ Language Server Protocol (LSP) সার্ভার

LSP সংজ্ঞায়িত করে কীভাবে এডিটর/IDE এবং ভাষা সার্ভারের মধ্যে যোগাযোগ হয়, যা auto complete, go to definition, find all references ইত্যাদি সমর্থন করে [17]। LSP JSON-RPC ব্যবহার করে বার্তা বিনিময় করে [17]। LSP সর্বশেষ সংস্করণ 3.18 [17]।

নীলাং LSP সার্ভারের বৈশিষ্ট্যসমূহ:
- **সিনট্যাক্স হাইলাইটিং:** বাংলা ও ইংরেজি উভয় কীওয়ার্ড
- **অটো-কমপ্লিট:** টাইপ-সচেতন সমাপ্তি, বাংলা API নামসহ
- **ইনলাইন এরর:** নীলাং কম্পাইলারের এরর সরাসরি এডিটরে দেখানো
- **রিফ্যাক্টরিং:** ভ্যারিয়েবল নামকরণ, ফাংশন উত্তোলন
- **সিম্বল নেভিগেশন:** সংজ্ঞায় যাওয়া, রেফারেন্স খোঁজা
- **বাংলা ডকুমেন্টেশন:** Hover করলে বাংলায় API ডক দেখানো

একটি একক ভাষা সার্ভার একাধিক ডেভেলপমেন্ট টুলে পুনর্ব্যবহার করা যায় [17]। সুতরাং VS Code, JetBrains IDE, Neovim — সবগুলোতে নীলাং সমর্থন যোগ করা সম্ভব।

### ১১.২ ডিবাগার

মোবাইল অ্যাপ ডিবাগিংয়ের জন্য LLVM-ভিত্তিক LLDB ডিবাগার ব্যবহার করা যায়:

```
nil debug --device=android --app=com.example.nilapp
nil debug --device=ios --app=com.example.nilapp
```

LLDB-র জন্য নীলাং ডিবাগ তথ্য:
- **DWARF Debug Info:** LLVM কম্পাইলার স্বয়ংক্রিয়ভাবে DWARF তথ্য তৈরি করে
- **সোর্স ম্যাপিং:** মেশিন কোড → নীলাং সোর্স লাইন
- **ভ্যারিয়েবল ইন্সপেকশন:** নীলাং-এর কাস্টম টাইপ দেখানো
- **Breakpoints:** নীলাং সোর্সে ব্রেকপয়েন্ট সেট করা

### ১১.৩ Package Manager (nilpkg)

নীলাং-এ ইতিমধ্যে nilpkg প্যাকেজ ম্যানেজার আছে এবং Ed25519 সাইনিং সমর্থন করে [9]। মোবাইলের জন্য nilpkg-এ যোগ করতে হবে:

```
# প্যাকেজ সংস্থাপন
nilpkg যোগ নীল-ক্যামেরা
nilpkg যোগ নীল-মানচিত্র
nilpkg যোগ নীল-বিজ্ঞপ্তি

# প্ল্যাটফর্ম-নির্দিষ্ট নির্ভরতা
nilpkg যোগ --শুধু-অ্যান্ড্রয়েড নীল-গুগল-পে
nilpkg যোগ --শুধু-iOS নীল-অ্যাপল-পে
nilpkg যোগ --শুধু-হার্মনি নীল-হুয়াওয়ে-পে
```

Bnlang-এ BPM (Bangla Package Manager) lockfile, integrity verification এবং script সমর্থন করে [22]। nilpkg-এও একই বৈশিষ্ট্য যোগ করতে হবে।

প্রস্তাবিত `nil.প্রকল্প` (manifest ফাইল):
```toml
[প্রকল্প]
নাম = "আমার-প্রথম-নীলাং-অ্যাপ"
সংস্করণ = "1.0.0"
লেখক = ["জয়শ্রীরাম সরকার"]

[প্ল্যাটফর্ম]
সর্বনিম্ন_অ্যান্ড্রয়েড = "API 26"
সর্বনিম্ন_iOS = "15.0"
সর্বনিম্ন_হার্মনি = "3.0"

[নির্ভরতা]
নীল-নেট = "2.0"
নীল-ক্যামেরা = "1.5"

[অ্যান্ড্রয়েড]
প্যাকেজ = "com.example.nilapp"

[iOS]
বান্ডেল_আইডি = "com.example.nilapp"

[হার্মনি]
বান্ডেল_নাম = "com.example.nilapp"
```

### ১১.৪ Hot Reload সমর্থন

Dart VM ডেভেলপমেন্টে JIT মোডে hot reload সমর্থন করে [14]। নীলাং-এর জন্য:
- **ডেভেলপমেন্ট:** Tree-Walking Interpreter দিয়ে hot reload (ইতিমধ্যে আছে [9])
- **Android এমুলেটর:** Bytecode VM-এ incremental update
- **iOS সিমুলেটর:** একই পদ্ধতি (সিমুলেটরে JIT নিষেধ নেই [43])
- **প্রকৃত iOS ডিভাইস:** Apple নীতি অনুযায়ী hot reload সম্ভব নয় [43], বরং fast rebuild

### ১১.৫ বিল্ড সিস্টেম

```
nilc build --release --অ্যান্ড্রয়েড   → .apk / .aab
nilc build --release --iOS           → .ipa
nilc build --release --হার্মনি       → .hap

# একসাথে সব প্ল্যাটফর্ম
nilc build --release --সব-প্ল্যাটফর্ম
```

Kotlin/Native-এ iOS-এর জন্য macOS হোস্ট প্রয়োজন [34]। নীলাং-এ iOS বিল্ডের জন্যও macOS হোস্ট প্রয়োজন হবে (Apple toolchain-এর সীমাবদ্ধতা)।

### ১২.২ পারফরম্যান্স নিশ্চিতকরণের কৌশল

**ক) 60 FPS গ্যারান্টি:**
Compose Multiplatform iOS-এ 120fps ProMotion-এ ফ্রেম বাজেট 8.3ms [35]। নীলাং-এর Animation Engine-এ ৩০+ easing curve আছে [9]। GPU renderer-কে Metal শেডার pre-compilation করে shader compilation stall এড়াতে হবে [35]।

**খ) মেমরি নিরীক্ষণ:**
Kotlin/Native-এর কাস্টম মেমরি অ্যালোকেটর হঠাৎ মেমরি বরাদ্দে বৃদ্ধি প্রতিরোধ করে [27]। নীলাং-এও জেনারেশনাল GC সুপারিশ করা হয়।

**গ) AOT বনাম JIT:**
ART (Android Runtime) AOT কম্পাইলেশন ব্যবহার করে DVM-এর তুলনায় অ্যাপ দ্রুত চালায় [23]। iOS-এ প্রকৃত ডিভাইসে JIT নিষিদ্ধ [43]। নীলাং প্রোডাকশনে সর্বদা AOT ব্যবহার করবে।

**ঘ) App Size নিয়ন্ত্রণ:**
Flutter অ্যাপ Engine এবং Embedder প্যাকেজ করার কারণে প্রায় 5 MB আকার বৃদ্ধি পায় [23]। নীলাং-এর রানটাইম যতটা সম্ভব ছোট রাখতে হবে:
- মৃত কোড ছাঁটাই (DCE): LLVM-এর অপ্টিমাইজার ব্যবহার [26]
- লাইব্রেরি লিংকিং: শুধু ব্যবহৃত মডিউল include করা

## অধ্যায় ১৩: তিন প্ল্যাটফর্মের জন্য সম্পূর্ণ ডেভেলপমেন্ট কার্যপ্রবাহ

### ১৩.১ Android অ্যাপ তৈরির পূর্ণ প্রবাহ

```bash
# প্রকল্প তৈরি
nil init --অ্যান্ড্রয়েড আমার_প্রথম_অ্যাপ
cd আমার_প্রথম_অ্যাপ

# নীলাং কোড লেখা
cat > মূল.nil << 'EOF'
আমদানি নীল/UI
আমদানি নীল/নেট

উপাদান মূল_পর্দা {
    অবস্থা সংখ্যা: পূর্ণসংখ্যা = ০
    
    নির্মাণ {
        স্তম্ভ(মাঝে_সাজানো: সত্য) {
            পাঠ("আমার নীলাং অ্যাপ", ফন্ট_আকার: ২৪)
            পাঠ("গণনা: \(এই.সংখ্যা)")
            বোতাম("বাড়াও") {
                এই.সংখ্যা += ১
            }
        }
    }
}
EOF

# Android APK বিল্ড
nil build --অ্যান্ড্রয়েড --রিলিজ
# → output: build/android/app-release.apk

# Android এমুলেটরে চালানো
nil চালাও --এমুলেটর
```

**Android বিল্ড প্রক্রিয়ার ভেতরে:**
1. নীলাং কম্পাইলার: `.nil` → HIR → MIR → LLVM IR
2. LLVM: LLVM IR → `aarch64-linux-android29` অবজেক্ট ফাইল
3. Android NDK: অবজেক্ট ফাইল → `libnilapp.so`
4. Kotlin Embedder: `libnilapp.so` লোড করে Activity তৈরি
5. Gradle: সব একসাথে প্যাকেজ করে `.apk` তৈরি

Android কম্পাইলেশনে Java/Kotlin কোড `.class` ফাইলে রূপান্তর হয়, তারপর Dex compiler দিয়ে `.dex` হয়, তারপর `.apk` তৈরি হয় [23]। নীলাং এমবেডারের Kotlin অংশ এই একই প্রক্রিয়া অনুসরণ করবে।

### ১৩.২ iOS অ্যাপ তৈরির পূর্ণ প্রবাহ

iOS অ্যাপ ডিভাইসে ইনস্টল করার সময় সম্পূর্ণ মেশিন কোড থাকে [23]। Swift এবং Flutter উভয়ই শেষ পর্যায়ে Apple-এর নেটিভ linker (`ld`) দিয়ে ARM64 মেশিন কোড সহ standard iOS binary তৈরি করে [43]।

```bash
# iOS IPA বিল্ড (macOS-এ)
nil build --iOS --রিলিজ
# → output: build/ios/NilApp.ipa

# iOS সিমুলেটরে চালানো
nil চালাও --iOS-সিমুলেটর
```

**iOS বিল্ড প্রক্রিয়ার ভেতরে:**
1. নীলাং কম্পাইলার: `.nil` → HIR → MIR → LLVM IR
2. LLVM: LLVM IR → `arm64-apple-ios15.0` অবজেক্ট ফাইল
3. Swift Embedder: XCFramework লোড করে UIViewController তৈরি
4. Xcode Toolchain: সব একসাথে প্যাকেজ করে `.ipa` তৈরি

iOS কম্পাইলেশনে Swift compiler কোড AST-তে রূপান্তর করে → Swift Intermediate Language (SIL) → LLVM IR → অ্যাসেম্বলি কোড → `.ipa` [23]। নীলাং একই চূড়ান্ত পর্যায় ব্যবহার করবে।

Apple-এর নীতি অনুযায়ী runtime-এ JIT code generation নিষিদ্ধ [43]। অতএব নীলাং iOS অ্যাপ সর্বদা AOT কম্পাইলড হতে হবে।

### ১৩.৩ HarmonyOS অ্যাপ তৈরির পূর্ণ প্রবাহ

HarmonyOS NEXT-এ DevEco Studio, Ark Compiler, ArkUI Framework এবং ArkTS ব্যবহার করে অ্যাপ তৈরি করতে হয় [1]।

**কৌশল A: নীলাং → ArkTS ট্রান্সপাইলার পদ্ধতি**
```bash
# নীলাং কোড ArkTS-এ রূপান্তর
nil ট্রান্সপাইল --ArkTS মূল.nil → মূল.ets

# DevEco Studio দিয়ে বিল্ড
# (হুয়াওয়ে Ark Compiler স্বয়ংক্রিয়ভাবে .hap তৈরি করে)
```

**কৌশল B: নীলাং নেটিভ বাইনারি + ArkTS FFI পদ্ধতি**
```bash
# নীলাং → নেটিভ HarmonyOS লাইব্রেরি
nil build --হার্মনি --নেটিভ
# → libnilapp.so (HarmonyOS ARM64)

# ArkTS-এ FFI দিয়ে কল করা
```

ArkCompiler AOT কম্পাইলেশন মোড ব্যবহার করে স্ট্যাটিক টাইপ তথ্য দিয়ে bytecode → optimized machine code তৈরি করে [39]।

### ১৪.১ একটি সম্পূর্ণ সহজ নীলাং মোবাইল অ্যাপ

```nilang
// আবহাওয়া_অ্যাপ.nil — একটি সম্পূর্ণ নীলাং মোবাইল অ্যাপ উদাহরণ

আমদানি নীল/UI
আমদানি নীল/নেট
আমদানি নীল/হার্ডওয়্যার

// ডেটা মডেল
ধরন আবহাওয়া {
    তাপমাত্রা: দশমিক
    আর্দ্রতা: পূর্ণসংখ্যা
    বিবরণ: পাঠ
    শহর: পাঠ
}

// Networking কাজ
অপেক্ষাযোগ্য কাজ আবহাওয়া_আনো(শহর: পাঠ) → ফলাফল<আবহাওয়া, পাঠ> {
    ধরো ঠিকানা = "https://api.weather.example/v1?city=\(শহর)"
    ধরো সাড়া = অপেক্ষা নীল.নেট.পাঠাও(পদ্ধতি: .GET, ঠিকানা: ঠিকানা)
    
    যদি সাড়া.সফল {
        ধরো ডেটা = নীল.JSON.পার্স(সাড়া.শরীর) হিসেবে আবহাওয়া
        ফেরত .সাফল্য(ডেটা)
    } নাহলে {
        ফেরত .ব্যর্থতা("নেটওয়ার্ক সমস্যা: \(সাড়া.বার্তা)")
    }
}

// UI Component
উপাদান আবহাওয়া_পর্দা {
    অবস্থা শহরের_নাম: পাঠ = "ঢাকা"
    অবস্থা বর্তমান_আবহাওয়া: আবহাওয়া? = শূন্য
    অবস্থা লোড_হচ্ছে: বুলিয়ান = মিথ্যা
    অবস্থা ত্রুটি_বার্তা: পাঠ? = শূন্য
    
    নির্মাণ {
        স্তম্ভ(প্যাডিং: ১৬) {
            // শিরোনাম
            পাঠ("🌤 আবহাওয়া", শৈলী: .শিরোনাম)
            
            // ইনপুট ক্ষেত্র
            সারি {
                পাঠ_ইনপুট(
                    মান: $এই.শহরের_নাম,
                    স্থানধারক: "শহরের নাম লিখুন"
                )
                বোতাম("খুঁজুন") {
                    অপেক্ষা এই.আবহাওয়া_খুঁজো()
                }
            }
            
            // লোডিং অবস্থা
            যদি এই.লোড_হচ্ছে {
                লোডিং_চিহ্ন()
            }
            
            // ত্রুটি বার্তা
            যদি ধরো ত্রুটি = এই.ত্রুটি_বার্তা {
                পাঠ(ত্রুটি, রং: .লাল)
            }
            
            // আবহাওয়া তথ্য
            যদি ধরো আবহাওয়া = এই.বর্তমান_আবহাওয়া {
                কার্ড(উন্নীত: সত্য) {
                    স্তম্ভ(মাঝে_সাজানো: সত্য, ব্যবধান: ৮) {
                        পাঠ(আবহাওয়া.শহর, শৈলী: .উপশিরোনাম)
                        পাঠ("\(আবহাওয়া.তাপমাত্রা)°সে", ফন্ট_আকার: ৬৪)
                        পাঠ(আবহাওয়া.বিবরণ)
                        পাঠ("আর্দ্রতা: \(আবহাওয়া.আর্দ্রতা)%")
                    }
                }
            }
        }
    }
    
    // ঘটনা পরিচালক
    অপেক্ষাযোগ্য কাজ আবহাওয়া_খুঁজো() {
        এই.লোড_হচ্ছে = সত্য
        এই.ত্রুটি_বার্তা = শূন্য
        
        মিলাও অপেক্ষা আবহাওয়া_আনো(এই.শহরের_নাম) {
        .সাফল্য(ধরো ডেটা):
            এই.বর্তমান_আবহাওয়া = ডেটা
        .ব্যর্থতা(ধরো বার্তা):
            এই.ত্রুটি_বার্তা = বার্তা
        }
        
        এই.লোড_হচ্ছে = মিথ্যা
    }
}

// প্রবেশদ্বার

উপাদান অ্যাপ {
    নির্মাণ {
        আবহাওয়া_পর্দা()
    }
}
```

### ১৫.১ প্রযুক্তিগত ঝুঁকি

| বাংলা Unicode parser জটিলতা | উচ্চ | মাঝারি | UTF-32 ইন্টার্নাল ব্যবহার [21] |

### ১৫.২ ইকোসিস্টেম ঝুঁকি

- **HarmonyOS নীতি পরিবর্তন:** হুয়াওয়ে ArkUI-X API পরিবর্তন করলে adaptation layer আপডেট করতে হবে। ArkUI-X 6.0.0 সাম্প্রতিক আপডেট দেখায় [36]।
- **Apple নীতি পরিবর্তন:** App Store নীতি পরিবর্তন হলে নীলাং কম্পাইলার আপডেট প্রয়োজন।
- **LLVM সংস্করণ সামঞ্জস্যতা:** LLVM API প্রতিটি সংস্করণে পরিবর্তন হয়; একটি নির্দিষ্ট LLVM সংস্করণে পিন করুন।

### ১৫.৩ বাস্তবায়নযোগ্য ন্যূনতম পথ

যদি সম্পূর্ণ পথচলা অতিরিক্ত দীর্ঘ মনে হয়, একটি ন্যূনতম কার্যকর পথ:

1. **নীলাং → WebAssembly** (ইতিমধ্যে WASM generator আছে [9])
2. **WasmEdge Android-এ চালানো** [8]: `WasmEdge Runtime` Android-এ WASM চালাতে পারে
3. **Capacitor বা Ionic দিয়ে মোড়ানো**: WASM-ভিত্তিক নীলাং অ্যাপকে মোবাইল WebView-এ চালানো

এটি নেটিভ পারফরম্যান্স দেবে না, কিন্তু দ্রুত প্রোটোটাইপ করতে সাহায্য করবে।

### ১৬.২ নীলাং-এর অনন্য সুবিধা

নীলাং-এর একমাত্র বৈশিষ্ট্য যা কোনো প্রতিযোগী ভাষার নেই: **বাংলায় প্রোগ্রামিং করার ক্ষমতা।** এটি বাংলাদেশ ও পশ্চিমবঙ্গের ডেভেলপারদের জন্য একটি শক্তিশালী প্রস্তাব।

- **শিক্ষামূলক মূল্য:** মাতৃভাষায় প্রোগ্রামিং শেখা সহজ (পঙক্তি ভাষার অনুপ্রেরণা [10])
- **Distributed SoftBus:** Onuron OS ডিভাইসগুলির মধ্যে zero-config LAN discovery [9] — HarmonyOS-এর distributed architecture-এর অনুরূপ
- **AI Compiler Oracle:** AI মডেল এবং ডেভেলপারদের verified type ও symbol reflection [9]

## নির্বাহী সিদ্ধান্ত — কী করবেন এবং কোন ক্রমে

### অগ্রাধিকার ১ (সবচেয়ে জরুরি): LLVM ব্যাকএন্ড

নীলাং-এর MIR আছে কিন্তু LLVM IR emitter নেই [9]। LLVM ছাড়া নেটিভ মোবাইল কোড জেনারেশন সম্ভব নয়। **এটি সব কাজের আগে করুন।**

Rust-এ `inkwell` ক্রেট বা C++ LLVM API সরাসরি ব্যবহার করে নীলাং MIR → LLVM IR রূপান্তর লিখুন [16][27][38]।

### অগ্রাধিকার ২ (দ্বিতীয় জরুরি): C FFI স্তর

ক্যামেরা, GPS ছাড়া মোবাইল অ্যাপ অর্থহীন। Bnlang-এর মতো [11][41] C ABI FFI প্রথমে implement করুন।

### অগ্রাধিকার ৩: Android Embedder

নীলাং `.so` → Android APK — এই পথ খুলুন। Flutter-এর Kotlin embedder [13] এবং Dart AOT প্রক্রিয়া [23] অনুসরণ করুন।

### অগ্রাধিকার ৪: iOS Embedder

macOS-এ LLVM দিয়ে `arm64-apple-ios` বিল্ড [34] এবং Swift Embedder দিয়ে XCFramework তৈরি [18]।

### অগ্রাধিকার ৫: ArkUI-X ইন্টিগ্রেশন

নীলাং → ArkTS ট্রান্সপাইলার বা C FFI দিয়ে HarmonyOS সমর্থন [36][37]।

### অগ্রাধিকার ৬: LSP সার্ভার

ডেভেলপার সম্প্রদায় গড়ে তুলতে ভালো IDE সমর্থন অপরিহার্য [17]।

## সারসংক্ষেপ: নীলাং-এর মোবাইল যাত্রার সম্পূর্ণ চিত্র

নীলাং ইতিমধ্যে একটি উচ্চাকাঙ্ক্ষী এবং বিস্তারিত ভিত্তি তৈরি করেছে — Tree-Walking Interpreter, Bytecode VM, HIR/MIR, WASM, Declarative UI, Package Manager, AI Oracle এবং Distributed SoftBus সবকিছু একসাথে [9]। এটি নিঃসন্দেহে একটি পরিপক্ক ধারণার প্রকল্প।

মোবাইলের জন্য পরিপূর্ণ করতে যা লাগবে তার সংক্ষিপ্ত তালিকা:

1. **LLVM IR Emitter** (MIR → ARM64 নেটিভ কোড)
2. **C FFI Layer** (নেটিভ মোবাইল API অ্যাক্সেস)
3. **Android Embedder** (Kotlin/Java-এ)
4. **iOS Embedder** (Swift-এ, macOS থেকে বিল্ড)
5. **ArkUI-X Bridge** (HarmonyOS সমর্থন)
6. **Null Safety** (টাইপ সিস্টেমে)
7. **Async/Concurrency** (Actor মডেল)
8. **LSP Server** (IDE সমর্থন)
9. **বাংলা STD Library** (নীল/UI, নীল/নেট, নীল/হার্ডওয়্যার)
10. **বিল্ড টুলচেইন** (APK/IPA/HAP তৈরি)

এই পথচলা অনুসরণ করলে নীলাং বিশ্বের প্রথম বাংলা প্রোগ্রামিং ভাষা হবে যা Android, iOS এবং HarmonyOS — তিনটি প্রধান মোবাইল প্ল্যাটফর্মে নেটিভ অ্যাপ তৈরি করতে পারে।
